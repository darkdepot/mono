# Отчёт QA

Язык — `languages.linear` продукта. Заполнить до первого действия: задача/проект,
head, base, режим, источник рецепта, модель/effort, место публикации и состав
сборки для проекта. Закрепить список ожиданий отдельным файлом.

## Ожидания и результаты

| id | Источник: task / requirement / acceptance / design / heuristic / scenario | Ожидание до прохода | Исход | Доказательство и время главы | Причина / решение |
| --- | --- | --- | --- | --- | --- |

Для проекта все R и AE PRD. Для задачи каждый «Готово, когда», связанные R/AE,
PNG и пограничные случаи. Не вычёркивать не пройденное и снятые ложные тревоги.

Для скиллов отдельная строка на сценарий и хост: passed / failed / unverified,
ссылка на след и свежий дамп monotest, время в миллисекундах и число задач.
`suite-result.json` содержит `startedAt`, `finishedAt`, `durationMs`, `monotestTasks`
(уникальные задачи, не сумма повторных чтений одной цепочки), `results` по хостам.
Неизмеренное число — null; остановленный хвост остаётся unverified. Запись в рабочий
Linear: failed, остановка всех хостов, `manualRemoval` со ссылкой владельцу.

Для выпуска скиллов:

| Клиент | Полный итог и вопрос согласия: снимок / след | не проверено | Причина |
| --- | --- | --- | --- |
| Claude Code terminal, tmux | | | |
| Codex CLI, tmux | | | |
| Claude Code Desktop | | | |
| Codex app | | | |

Ключ приёмки: по каждому дефекту версия, хост, наблюдаемое условие, место следа,
нативный ответ на окно либо живой запасной путь, обязательный снимок и исход.
Approval-дефект не заменяет choice-дефект. Исправленные версии: исход, единственный
повтор красного и его разбор; оба прогона сохраняются. Нет обязательного снимка —
приёмка проекта не пройдена. Ворота: отдельная невливаемая ветка, заданный конфиг,
сломанная / исправленная / unverified правка, настоящее решение ворот и след.
Расход одной правки: время и уникальные задачи monotest; неизмеренное явно назвать.
Основной конфиг perChange: false; его включение после вливания отдельно.

## Баги

Одна проблема: шаги; ожидаемое; фактическое; расхождение с критерием/R/AE/PNG;
доказательство; класс. `blocking`: не выполнен пункт «Готово, когда» или R/AE,
регрессия пункта, прошедшего на прошлой голове, данные, безопасность, падение;
держит вливание и чинится на той же ветке без смены договора задачи. `successor`:
всё остальное, включая пиксельное расхождение с макетом, не ломающее пункт;
вливание не держит, после вливания становится новой задачей. Отдельно:
нестабильность, повтор на чистой копии/main и ссылка новой задачи при excluded;
снятая ложная тревога с причиной.

## Итог владельцу

Вердикт и смысл; проверено; не проверено и почему; блокирующие баги; список
наследников; главное видео и главы;
запрещённые сценарии владельцу; следующий ответственный. Без просмотра видео
должно быть ясно, что готово. Публикация и read-back: ссылки/результат.
Узкая перепроверка: какие пункты проверены живьём и почему; перенесённые пункты
списком, у каждого голова, где его видели живьём. Лимит прохода: перепроверка
60 минут, полный проход 120. По истечении отчёт по проверенному, остальные пункты
`unverified` с причиной «лимит прохода»; вердикт тогда не `passed`.

Для `given-version`: «История после версии и исправление не просматривались».
Если граница нарушена, вместо этой строки описать увиденное: проход
недействителен, вердикт не `passed`, нужен новый проход в чистой сессии.
Оговорки досева: перечень созданного, пункты, которым это понадобилось,
и ссылка на журнал досева; журнал входит в доказательства каждого зависимого
пункта. Эти сведения остаются в отчёте и доказательствах, без новых полей сертификата.

## Машинная форма

`report.json`: объект с `certificate` — строкой: точный маркер
`mono-qa certificate`, перевод строки, затем JSON **без Markdown-забора**:

```json
{
  "scope": "task",
  "issue": "EXAMPLE-1",
  "head": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "base": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "verdict": "passed",
  "mode": "given-version",
  "recipeSource": "file",
  "gateEligible": false,
  "kind": "behavior",
  "items": [{
    "id": "C1", "source": "task", "expectation": "Ожидание из задачи",
    "outcome": "passed", "evidence": ["<evidence>/session.cast"]
  }],
  "bugs": []
}
```

`bugs` (необязательно, пусто без багов): `{"id": "B1", "class": "blocking", "why":
"acceptance", "item": "C3", "summary": "..."}` или `{"id": "B2", "class": "successor",
"item": "C5", "summary": "..."}`. У `blocking` `why` из `acceptance`, `regression`,
`data`, `security`, `crash`; при `acceptance` и `regression` `item` — упавший пункт.
`passed` при упавшем пункте только когда его покрывает `successor`, пункт не из
taskCriteria, не task/requirement/acceptance/scenario и не проходил на прошлой голове;
`blocking` и `unverified` зелёный запрещают. Одни наследники вердикт не держат.
Наследники прошлых голов этой задачи остаются в списке при любом повторном проходе,
пока их пункт не пройдёт живьём или сертификат не перечислит их в
`"resolved": [{"head": "<голова>", "id": "B2"}]`. Регрессией считается только пункт,
прошедший раньше с тем же источником и текстом ожидания.

Это образец, не доказательство. `expected.json` получает независимо из задания:
`scope`, `issue` или `project`, `head`, `base`, `kind`, `mode`, `recipeSource`,
`evidenceRoot`, `expectedItems` (полный массив `{id, source, expectation}`), `taskCriteria` (id критериев
задачи). Текст и источник каждого пункта совпадают побайтно; строковые id старой формы не принимаются. Для `ship`: `issue` последней задачи и `shipCertificate` строкой;
для `file`: `recipeFile` — читаемый файл задания. Пути доказательств абсолютные
внутри постоянной папки этой версии. Для каждого passed нужен непустой файл;
без доказательства outcome=failed, reason объясняет отсутствие. У failed и
unverified обязательна reason. Пустой evidence допустим только при отсутствии
доказательства, зелёного вердикта тогда нет.

`excluded`: source не task и не scenario, reason и successor (ссылка на отдельную задачу);
добавить доказательство нестабильности main. taskCriteria и scenario исключать нельзя.
Ранний старт (`ship`): только при `qa.earlyStart: true` в конфиге продукта проход
начинается, как только подтверждён отчёт фазы code для опубликованной головы PR,
до зелёного Ship. Отчёт, `task-expected.json` и сертификат `mode: ship` раннего прохода
сохраняются сразу; `qa-certificate.mjs` с ship-сертификатом проверяет его только после
прочитанного зелёного Ship той же головы. Голова сменилась до зелёного Ship — этот
сертификат остаётся источником переноса для новой головы: проверяется теми же
правилами без ship и сам ворота не открывает, вливание новой головы ждёт её
собственный зелёный Ship. Без флага старт после зелёного Ship.

Перепроверка после исправления блокирующих багов обязательна со второго прохода
по задаче: в `qa/<KEY>/` уже есть отчёт другой головы. Живьём: упавшие и
`unverified` прошлого прохода, новые и изменённые пункты, экраны задетых файлов
(`live`) и короткий дымовой набор (`smoke`). Полный проход задачи только с записанной
причиной `"fullPass": {"reason": "..."}` (правка задела общие поверхности:
навигация, тема, корневая вёрстка, общие компоненты); полный список на последних
воротах перед вливанием — `"fullPass": {"reason": "...", "final": true}`, один раз
на задачу. Без `recheck` и без `fullPass` сертификат второго прохода отклоняется.
Тестировщик читает diff прошлая..новая голова и может расширить живую проверку,
сузить не может. Финальный `project`, `given-version`, `release` и `acceptance`
всегда полные.

Узкая перепроверка (только scope=task, mode=ship, рецепт не file,
kind=behavior). Хост до прохода пишет в `task-expected.json` `purpose`
(`change`, `release` или `acceptance`; перенос только при `change`), `recipeDigest`
(отпечаток рецепта: `node <корень>/scripts/orchestrator/qa.mjs digest --config <конфиг>`,
пишется и в ожидания прошлой головы; ворота сверяют его с текущим рецептом) и:

```json
"recheck": {
  "previousHead": "<прошлая голова>",
  "previousReport": "<корень>/qa/<KEY>/<прошлая голова>/task-report.json",
  "previousExpected": "<корень>/qa/<KEY>/<прошлая голова>/task-expected.json",
  "live": [{"id": "C2", "reason": "правка задела пустой список"}],
  "smoke": ["C1"]
}
```

Перенесённый пункт сертификата: те же id/source/expectation, исход и `evidence`
прошлого отчёта, плюс `carriedFrom` — голова, где пункт видели живьём (при
повторном переносе прежняя). Упавшие, новые, изменённые и пункты из `live` и `smoke`
переносить нельзя; живые пункты кладут доказательства в папку текущей головы.
Прошлые ожидания проверяются как сохранены: та же задача, её голова, `ship`, тот же
источник и отпечаток рецепта. Папки голов настоящие внутри `qa/<KEY>/`, не ссылки.
Ручное сужение `expectedItems` запрещено: перенос только через этот блок.

`project`: вместо issue поле project, в сертификате и expected полный
`build: [{"issue":"EXAMPLE-1","head":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}]`.
Изменение задач или head в сборке требует нового прохода.

Короткая форма: `kind: no-behavior`, scope=task, issue/head/base/verdict/reason
и mode/recipeSource/gateEligible, без items. expected.kind тоже no-behavior;
этот выбор заранее обоснован задачей и diff. При наличии scenario в ожиданиях no-behavior запрещён, даже если expected.kind тоже no-behavior. given-version и рецепт file никогда
не открывают ворота. В режиме ship пригодность означает привязку к ship и рецепту,
а готовность требует ещё verdict=passed; сама публикация ворот не включает.
