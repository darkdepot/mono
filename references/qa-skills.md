# Проверка скиллов

Читай при проверке этапов. Каталог и выбор по разнице: `evals/scenarios/README.md`.
Записи сверяет `scripts/skills-records.mjs`, сертификат получает заранее сохранённые
ожидания qa.skills. Живые прогоны выполняет оркестратор.

## Ответы словами

Все шесть этапов используют `hosts.<host>.expectedReplies`. Формат T1 доработан
по U7: роль, исход, якоря и обязательная рубрика вместо скрытых точных фраз.
`expectedWindows` и оконные политики отсутствуют в активном каталоге нынешних
этапов. Драйвер читает `VERSION` проверяемой копии: до 0.43.0 ключ приёмки
использует перенесённый оконный путь, с 0.43.0 только `expectedReplies`.
Форма сценария не включает старый режим; несовпадающая `testedVersion` при запуске
отвергается. Оффлайн-проверке следа передают сохранённую `testedVersion` явно.
Прежние нажатия действительны в записях; новые этапы окон не вызывают.

## Выпуск и ключ приёмки

Выбор `purpose: release` через `skills-select.mjs` сохраняет одну цепочку
`index.release.stages` на каждый хост: Idea → Research → Discovery → Design →
Tech Evaluation → Handoff. Это отдельный выпускной бриф с дизайном и размером
«проект»; обычные короткие цепочки правок не меняются. `index.release` входит
в digest каталога. Первый сценарий не имеет посева, каждый этап проходит ровно
один раз в одном свежем проекте monotest на хост. Потерянный указатель,
failed или unverified останавливают хвост; новый проект и посев не подставляются.

В запросе suite оркестратор задаёт `releaseStartReason` — причину разрешённого
старта полной выпускной цепочки. У Design нет вопроса о старте следующего этапа:
после passed разговора, рубрики и записей Tech Evaluation отдельно запускает
драйвер по этому заранее утверждённому плану, без приписывания владельцу
несуществующего согласия. Остальные переходы сохраняют проверку настоящего
разрешающего ответа и сигнала этапа. Память дизайна и Paper готовятся в тестовом
продукте; записи Linear для обхода пропущенного этапа не сеются.

`release-report.md` содержит цепочки, время, уникальные задачи monotest и четыре
клиента с колонкой «не проверено / причина». Фоновый драйвер не доказывает экран
и оставляет снимки непроверенными. Оркестратор дополняет отчёт живыми следами
и снимками в evidenceRoot вне репозитория и всех writable roots worker.
Терминал Claude Code и Codex CLI — настоящая сессия в tmux, ответ клавиатурой,
снимок и текст панели. Desktop и Codex app сначала проходят пробу: monotest виден,
рабочий Linear скрыт. Без изоляции допустим только показ Idea и ответ «Ещё
обсудить»; полноценный этап с записями запрещён. Пробел уходит владельцу через
оркестратора; владельца не просят снимать или прогонять. Обычные сессии обоих
хостов до, во время и после проверки видят основной Linear.

Условия ключа перечислены в `evals/scenarios/acceptance/key.json`. Проверяют
именно наблюдаемое условие каждого дефекта, а не любой failed: старый образец
дефекта утверждения Idea не заменяет дефект окна выбора. Claude получает
`can_use_tool` / AskUserQuestion и ответ `updatedInput.answers`; Codex получает
аргументы async-окна из rollout и продолжение `exec resume` с
`send_user_message_question_reply`. Подтверждение исполнения и фактический ответ
связываются нативными call id. Даже дефектное окно получает ответ; failed
проверки показа сохраняется. Нет ожидаемого окна или оно заменено текстом —
failed. Нативного ответа нет: запасной путь — настоящий терминальный клиент
этого хоста с ответом на окно и снимком; недоступен и он — unverified и стоп
вливания. С 0.43.0 любой вызов окна по-прежнему failed.

Ключ требует снимки Desktop и Codex app: без них приёмка проекта не пройдена.
На исправленных версиях с 0.40.0 красный повторяется один раз до признания
ложным; оба результата остаются в отчёте. Рубрика нынешней версии проверяет
разговор старых версий, включая одинаковые начала вопросов Discovery 0.36.0.
Оконный проверяющий по-прежнему проверяет суть, совет, варианты, последствия,
видимый полный итог и порядок хоста; два нецелевых вопроса могут получить
рекомендованные ответы, не съедая политику решающего окна.

Приёмку ворот оркестратор выполняет на отдельной невливаемой ветке с заданным
конфигом `perChange: true`: сломанный итог/согласие получает отказ, исправленный
проходит, unverified получает отказ. Сохраняются настоящие решения ворот,
а не только сертификат или цвет отчёта. Основной предприменённый конфиг остаётся
`perChange: false`; worker его не меняет. Включение после вливания — отдельное
действие оркестратора после успешной приёмки. Отдельно записывается измеренный
расход одной правки: время и уникальные задачи monotest. Выпуск дольше 8 часов
не сокращается: время остаётся в отчёте, оркестратор заводит задачу ускорения.

Фиксированный свежий дамп также читает `list_issue_statuses` каждой команды
задач, сохраняет сырой ответ `statuses/<teamId>.json` и связывает его с нативным
чтением после сценария. UUID статуса разрешается только в точное имя из списка
нужной команды; другой статус того же типа — расхождение. Имя в другом регистре или
тип статуса разрешаются по тому же списку и только в один статус. ToolSearch с точным
`select:mcp__monotest__…` — поиск инструмента, не команда хоста; другие команды
дампу запрещены. Синтетические тела скиллов Claude не задают порядок времени.
Записанный текст и его чтение сверяются по словам и числам по порядку: оформление, которое Linear меняет при
сохранении, не влияет. Ссылка считается подписью, адресом и заголовком, ссылка на собственную подпись один раз,
чип задачи своей меткой. Коды 137/143 нормализуются только после завершения и
фактической остановки драйвером; самостоятельный сбой хоста не становится зелёным.

```json
{
  "expectedReplies": [{
    "id": "research-start", "stage": "research", "role": "transition",
    "summary": ["Источник"],
    "question": {"anchors": [["Discovery"]], "forbidden": []},
    "presentation": "document", "driverStart": ["discovery"],
    "asksStart": true, "reply": "да, начинаем", "intent": "agree",
    "outcome": {"approval": false, "startNext": true},
    "response": {"anchors": [["Discovery"]], "forbidden": [], "question": false}
  }]
}
```

`id` уникален. `stage`: idea, research, discovery, design, tech-evaluation, handoff.
`role`: approval, transition или clarification; `asksStart`, `intent` и оба
`outcome` задаются автором сценария до запуска. Драйвер и рубрика их не выбирают
и не меняют, распознавателя намерения нет. `reply` доставляется дословно после
успешного завершения хода; отсутствие его нативного подтверждения не зелёное.
Claude включает `--replay-user-messages`, Codex связывает сообщение с продолжением.
Синонимы согласия задаются разными `reply`, а не словарём в скрипте.

`summary` — якоря итога. `question` и `response` содержат `anchors` и необязательные
`forbidden`. Для точных запрещённых реплик есть `forbiddenExact`: строки
сравниваются с целыми строками ответа, с обрезкой внешних пробелов и без учёта
регистра. Это не распознавание намерения: «Не начинаю Research» и «Research начнём
позже» не совпадают с запрещённой строкой «Начинаю Research.». Составное предложение,
непривычная формулировка или предложение перехода без имени проверяются обязательной
рубрикой; вызов старта независимо проверяется по нативному действию. Каждый якорь — строка или массив альтернатив; все группы обязательны,
внутри группы достаточно одной строки, регистр не важен. Фактический вопрос
сохраняется целиком из последней строки сообщения и связывается с доставленным
ответом. Он кончается одним `?`. Вопросы внутри полного артефакта Idea не являются
дополнительной репликой владельцу. Смысл вопроса и соответствие его роли проверяет
рубрика, якоря сами по себе ничего не доказывают.

Последний элемент требует `response` с якорями, запретами и `question: boolean`.
После реплики владельца допускается ровно один завершённый ход этапа, без
лишнего вопроса или хода. У unclear этот ход кончается вопросом с `?`.
Предложение старта там, где о старте не спрашивали, блокируют заданные до запуска
точные запреты реплик и рубрика; само имя этапа в отказе или откладывании
не является предложением старта: предложение без имени
тоже запрещено. Промежуточный response необязателен, когда следующий элемент
массива уже задаёт новый показ и вопрос. Дополнительная реплика владельца,
служебный ход или незавершённый хвост не пропускаются.

`stageStartLine` результата драйвера — строка настоящего успешного terminal
после подтверждения пространства или посева; она передаётся trace/probe/records,
чтобы отделить подготовку от разговора этапа. Все вопросы после неё идут
строго по порядку: лишний вопрос или ответ вне политики — провал. Проверяется
завершение всего следа, включая хвост после ожидаемых обменов, в обоих хостах.
Текстовые проверки не обрезают след по `endLine`.

Завершённость общая для основного разговора и каждого отдельного scout-следа,
включая скаутов без `expectedReplies`. Ход закрывается только успешным нативным
терминалом родителя; Codex связывает его с активным `task_started.turn_id`
и закрывает этот id: повторный терминал не завершает новое продолжение.
После появления `turn_id` на границе хода режим с ID сохраняется: терминал
без ID не может закрыть продолжение. Legacy-следы без ID остаются допустимыми.
Сессия завершена, только если последнее действие родителя — такой терминал.
Это отдельно от ожидания ответа на показанное: начало нового хода сбрасывает
только незавершённый итог, сохраняя ожидающий вопрос до фактического ответа.
Codex допускает `task_started` до или после пользовательского сообщения;
обе очередности проверяются с настоящими `turn_id` в драйвере и потребителях.
Сообщение, thinking/reasoning (включая `agent_reasoning_raw_content`), запрос разрешения, инструмент, его результат, init/start, ошибка
или отмена после успеха оставляют незавершённый хвост. Информационные события
(например `thinking_tokens` и `task_summary`) и вложенные child-envelopes
не меняют состояние родителя; отдельный дочерний след проверяется сам.
Claude user-сообщения с `isSynthetic: true` (тело Skill) и нативным
`origin.kind=task-notification` не являются репликами владельца. Только уведомление известной фоновой задачи
помечено ожидающим до нового init либо его доставки в parent-turn через
тот же нативный `origin.runId`; terminal при работающих скаутах не завершает этап.
Задача, которую родитель сам остановил через `TaskStop`, сообщает «stopped» в том же
ходе и ожидающей не остаётся: отдельного хода с уведомлением после неё не бывает.
Codex developer/system context на возобновлении не сбрасывает ожидающий ответ.
Для Claude сценарий задаёт `idleContinuation: "Продолжай."`: после успешного
завершения хода без фоновой работы/ожидающего уведомления и только с прогрессом
без вопроса и разделов итога драйвер ждёт короткую паузу хоста и отправляет
одно нейтральное продолжение. Оно записано как non-consent nudge, не расходует
политику ответа и не даёт права утверждать или начинать этап. Второй такой
простой или отсутствие политики — unverified, без ожидания полного тайм-аута.
Настоящий вопрос без полного итога по-прежнему failed.
Завершённый ход только с инструментами считается нативно завершённым, но
не удовлетворяет текстовой политике этапа.
Для historical дополнительных Codex-источников завершённый след без видимого
текста ассистента, окон и любых записей — helper: его native source-check passed,
а в рубрику разговора он не входит. Основной источник не получает исключения.
Окно, видимый текст, запись, собственная политика или неполный след сохраняют
обычную проверку; helper не может скрыть failed/unverified другого источника. Матрица `completeness matrix`
в `skills-records.test.mjs` задаёт исходы обоих хостов и обоих типов сессий
до запуска проверок; незавершённость даёт `unverified`, а нарушение текстовой
политики — `failed`.


Idea, Discovery, Design и Tech Evaluation утверждают показанное. Research
документ не утверждает, только разрешает Discovery. Handoff записывает старт
работы. `defer` утверждает без старта; согласие на clarification ничего не
утверждает и не запускает. Истинный approval требует настоящей записи, связанной
с показом и ответом: словесное подтверждение и заранее существующая запись её
не заменяют. Мелкая поправка:

```json
{
  "correction": {
    "before": "Фильтр и сортировку не добавляем.",
    "anchors": ["экспорт", ["не добавляем", "исключ"]],
    "descriptionAnchors": ["экспорт"]
  }
}
```

`before` находит ровно один фрагмент показанной версии. Проверяется фактический
новый фрагмент по якорям и рубрике; весь префикс и суффикс остаются дословными.
Дословные after и description не требуются. Этап называет поправку в ответе;
вне заборов записи обязательна одна строка `Поправка: …`, также проверенная по
якорям и смыслу. Отказ внести поправку при сохранённых якорях — failed.
Поправка картинки Design или пакета Handoff означает новый показ, а не замену
фрагмента; такой сценарий задаёт следующий expectedReplies.

### Показ и версия

Проверяющий получает `approvalBindings`:
`{recordId, replyId, shownLine, text, currentLine, shownReadLine?, documentId?, currentRecordId?}`.
Для показов без записи, в том числе Research, используются `presentationBindings`
с теми же полями показа; это отдельный массив всех показов, а не замена привязок записей.
Если он отсутствует, берутся approvalBindings.

`presentation: document` разрешает итог со ссылкой вместо полного тела в чате.
Проверка нативно читает связанный результат get_document перед последним сообщением
и свежий результат после разрешающего ответа, до записи и финального ответа этапа.
При вопросе, отказе или неясном ответе без утверждения и старта повторное чтение
не требуется: показ всё равно связан с первоначальным нативным документом.
Канонический идентификатор берётся из нативного ответа, а не из lookup id/slug
запроса. Другой канонический документ или его изменённое тело не проходят.
Идентификатор и SHA-256 тела задают основную версию; updatedAt вспомогателен:
его изменение без правки тела не подменяет документ. У записи пакета допустимы
get_project/list_comments с currentRecordId; ссылка относится к прочитанной записи.
У строки списка комментариев адреса нет, её ссылка — `#comment-<id>`. Итог Design
ссылается на `canvas` записи утверждения; PRD из этой записи сверяется чтениями.
Старт пакета несёт sha256 содержимого блока `mono-package`, равный заголовку записи.
`text` совпадает с полным нативным телом, ссылка и якоря находятся в последнем
сообщении. Свежая версия и финальный независимый дамп равны показанной плюс только
названная поправка. Подмена документа, версии, итога, цитаты или ранняя запись
по-прежнему проваливаются. Для PRD/Tech Spec поправка уже внесена перед записью.
Машинные строки и idea-gate остаются прежними.

`presentation: inline` требует полный показ артефакта: обязательно для Idea,
допустимо для целиком показанной страницы технического решения. Tech Evaluation
заранее допускает оба вида показа: presentation=["inline","document"], в binding
тогда обязательно указать фактически наблюдаемый presentation; ожидаемый исход не меняется. По умолчанию
сообщение равно text плюс перевод строки и фактический вопрос. Для отдельно
сформулированного совета binding может задать artifactEnd — точную границу полного
артефакта в нативном сообщении; весь префикс совпадает с text, в хвосте остаётся
совет и фактический вопрос. Граница входит в digest рубрики: проверяющий обязан
отвергнуть усечённый артефакт, даже если в нём сохранились все якоря. Сценарий может
заранее задать буквальное `framing: {before, after}`; binding не задаёт рамку.
У Idea и у страницы Tech Evaluation binding может также задать абсолютный artifactStart
вместе с artifactEnd: между границами точно весь text (четыре раздела Idea, страница
техлида); вводная и заключительная проза остаются в полном сообщении для рубрики. Снимок утверждения по-прежнему полный.
У Idea показаны все четыре раздела, запись хранит согласованный снимок, тело
проекта выводит прежний idea-gate record. Фрагмент вместо полного артефакта
не проходит. Вне заборов — `Владелец: ответил «<дословный reply>»`, без точки после кавычки.
После потери временных файлов восстановление только из разговора, иначе новый показ.

Делегированный ответ задаёт by=orchestrator и дословную reason в reply и записи.
Idea дополнительно требует ownerEvidence={host,trace,shownLine,replyLine,text,question,reply}
и собственный expectedReplies исходного следа владельца. Оркестратор передал
всю показанную версию, настоящий вопрос и дословный ответ раньше своего согласия;
пересказ и отсутствие слов владельца не проходят. Scout не наследует родительские
ожидания, но все его вызовы, завершённость и запрет окон проверяются.

### Старт через драйвер

`driverStart` — null или список допустимых следующих этапов, сохранённый в сценарии
до запуска. Он не выводится из outcome.startNext. Сам этап следующий этап в тесте
не исполняет: драйвер добавляет локальный MCP stage_driver только с разрешёнными
назначениями. `mcp__stage_driver__start_stage({stage,projectId})` перехватывает вызов
и возвращает нативную квитанцию без запуска. Альтернатива — настоящий переход
проекта; собственная запись mono-package: start остаётся сигналом Handoff.

Проверка требует разрешение сценария, подходящий фиксированный исход, реальный
ответ владельца и сигнал этапа после него. Упоминание в прозе, нет сигнала, ранний
сигнал, defer или clarification не дают старта. Вызов должен относиться к тому же
проекту и допустимому следующему этапу. Неперехваченный вызов Skill/Agent/Task
запрещён. Делегированный этап имеет startNext=false и не вызывает следующий;
его запускает оркестратор. Исключение — собственная запись старта Handoff.
Suite выполняет следующий сценарий в том же проекте только после passed текущего
этапа, включая рубрику, и проверенного сигнала starts; failed и unverified блокируют
следующий вызов, даже если нативный сигнал уже получен. Рубрика обязательна для приёмки; отсутствие разрешения или сигнала оставляет хвост
непроверенным. Design заканчивает собственную сессию: его цепочка заканчивается
на Design; соседний Handoff остаётся отдельным обязательным сценарием каталога.

## Драйверы

`node scripts/skills-run.mjs <request.json>` запускает один сценарий;
`node scripts/skills-trace.mjs <request.json>` и
`node scripts/skills-probe.mjs <request.json>` проверяют нативный текстовый след.
Поля запроса: host, абсолютные cwd/packRoot/outputDir, authFile для Codex,
mcpServers.monotest, workspaceProof и scenario={prompt,brief,expectedReplies,allowedTools}.
Пример подключения: monotest={url:"https://example.test/mcp"}; proof задаёт
mcp__monotest__get_workspace, input={}, path=["name"], equals="Mono Test".
outputDir должен отсутствовать. Подключения задаются url или command/args.
Paper при Design проходит через файловый guard. stage_driver создаёт только
драйвер; его нативная квитанция не является записью в Linear или доказательством
уже выполненного следующего этапа.

Codex получает новый дом с явно переданным authFile, отключёнными приложениями,
remote plugin и рабочим Linear, тестовые MCP default_tools_approval_mode=approve.
Claude использует strict-mcp-config, plugin-dir проверяемой копии, permission-prompt-tool=stdio;
установленный Mono отключён в настройках прогона. Перед этапом обязательны
нативное чтение пространства и связанный успешный результат. Для Codex exec
закрытая форма: `const r = await tools.<имя>(<JSON>); text(r);`.
Драйвер допускает один повтор startup-read только после аудита всего неудачного
хода и его успешного завершения; чужой MCP, ранняя запись и незавершённость
не становятся основанием для повтора. Локальные сценарии с синтетическим хостом
не доказывают видимость в приложении или поведение настоящей модели.

Полный stdout и отдельный native rollout сохраняются. Тайм-аут или ошибка хоста
не зелёные; endLine не обрезает текстовые проверки. Все действия основного и
дочерних следов проверяются; unknown native forms дают unverified.
Коды CLI: 0 — механический проход, 1 — failed, 2 — unverified.

## Точки чтения следа

runScenario → runClaude/runCodex → finishRun → checkTrace. Probe, trace и records
используют общие auditRows, parentTurns и nativeProof. Ни окно, ни текст результата
инструмента, ни child-итог не заменяют пользовательское сообщение.

## Проверка разговора

Драйвер доставляет только заранее заданный reply. Утверждение связывает последнее
сообщение этапа, дословный фактический ответ и записанную версию. Запрещены все три
оконных инструмента, включая попытку с ошибкой; разные этапы не повторяют концовки.
Нативная завершённость, полные записи и отдельная рубрика обязательны одновременно.

## Рубрика разговора

Сценарий до запуска содержит rubric.md. Проверяющий читает весь след и нативные
документы, не самооценку этапа; не выбирает и не меняет ожидаемый исход.
Результат verifyRecords содержит rubricInput и rubricDigest: SHA-256 полного входа
(рубрика сценария, след, заданные ожидания, настоящий вопрос/ответ, границы
показа, документы и записи).
В bindings-файле поле rubric содержит {digest,reviewer,checks}; checks идут строго
summary, question, response, correction. У каждого status=passed|failed|unverified,
непустые evidence с точными файл:строка и reason. Без рубрики или при смене следа,
документа либо исхода — unverified. Любой failed блокирует приёмку. Одни якоря
не позволяют подписать passed.

Suite сохраняет `<этап>-records-evidence.json`: вход сверки, rubricInput,
rubricDigest и хеши нативных следов, записей и свежего дампа. Проверяющий использует
именно эти сохранённые данные. В существующем bindings-файле он добавляет rubric
для данного digest; в обычном resume approvalBindings, presentationBindings и gates не меняются.
Отсутствующая привязка версии остаётся unverified и не заменяется рубрикой.
Если привязки требуют разметки или исправления уже завершённого следа,
заполни их по сохранённым нативным данным и запусти тот же suite с `resume: true`
и `prepareReview: true`. Это только подготовка рубрики по прежнему следу и дампу:
цель — единственный ещё не прошедший проверку элемент в recordBindings. Рубрики
завершённых предыдущих этапов не меняются. Для явной цели вместо true укажи её
полный id, например `prepareReview: "release:research/approve:codex"`.
она не запускает ни одного этапа. Suite сохраняет отдельный .prepared.json с
полным входом и digest. После проверки этого digest убери prepareReview и продолжи
обычным resume. Подготовка разрешена и после прежнего digest: новые привязки
пересчитывают вход и digest, прежняя rubric удаляется и не подтверждает новый
вход. Без prepareReview изменение привязок по-прежнему запрещено. Исходный
файл evidence остаётся неизменным; повторная подготовка идёт от нового prepared.
Нативная ошибка patch с явным «nothing was saved» не считается записью только
после успешного повторного save_document того же id и свежего get_document.
Неизвестный исход, другой объект или отсутствие повторного чтения — unverified.

Для продолжения запусти `node scripts/skills-suite.mjs <request.json>` с теми же
selectionFile, runId, outputDir, cwd, packRoot и остальными параметрами, добавив
`resume: true`. recordBindings указывает на файлы с проверенными рубриками.
Suite читает свой suite-state.json и заново сверяет сохранённые нативные данные,
не выполняя завершённый этап или новый сбор дампа. Состояние и доказательства не
редактируют: изменённый след, дамп, вход, привязка или rubricDigest запрещает
продолжение. Результаты возобновлений пишутся отдельно как suite-result-N.json;
первый suite-result.json сохраняется.

После passed рубрики для того же digest драйвер может выполнить следующий этап,
если исходный сценарий разрешал старт и сохранённый след содержит действие этапа
после ответа владельца. failed и unverified по-прежнему блокируют старт. Если
следующий этап тоже ждёт рубрику, проверяющий повторяет этот шаг для его нового
сохранённого набора доказательств; предыдущие этапы заново не запускаются.

- summary: итог соответствует нативно прочитанному документу; в чате видны результат,
  позиция и причина. Idea показана целиком, ссылка не заменяет её четыре раздела.
- question: настоящий последний вопрос соответствует заданной роли, спрашивает
  один конкретный вопрос под ситуацию; нет скрытого утверждения или старта на уточнение.
- response: ответ этапа соответствует фиксированному исходу и записи. Неясный ответ
  получает уточнение. Запрещено предложение перехода без разрешения, даже без имени этапа.
- correction: фактическая правка и её описание соответствуют просьбе, отказ внести
  поправку не замаскирован якорями, остальной текст не изменён. Без поправки проверяется
  её отсутствие; после существенной правки новый показ.

Отрицательные варианты сохраняют допустимые якоря, но меняют смысл итога или
поправки либо предлагают переход без имени. Рубрика обязана их отвергнуть.
Полнота нативного хода, отсутствие лишних вопросов/реплик, ранних записей,
подменённой цитаты и окон проверяются отдельно и не заменяются рубрикой.

## Свежий дамп и сверка записей

Текущий путь использует текстовые approvalBindings из раздела «Ответы словами».
Ниже также сохранено описание legacy windowCallId для старых следов;
это чтение исторических доказательств, не путь запуска новых сценариев.

После каждого этапа suite запускает отдельный read-only прогон через тот же хост,
с новым тестовым домом Codex либо strict MCP Claude, только с monotest (без Paper).
Окон и посева в нём нет. Закрытый перечень задаёт `dumpPrompt` в
`scripts/skills-records.mjs`, модель не сокращает список: project.json; все страницы
комментариев проекта; все страницы документов и get_document каждого; все страницы
задач, включая архив, get_issue каждой со статусом и метками и все её комментарии.
Имена: comments-N.json, documents-N.json, issues-N.json, соответствующие
*-N.request.json, documents/<id>.json, issues/<id>/issue.json и
issues/<id>/comments-N.json. Первая request — {}, остальные {cursor} из предыдущего
ответа; последняя страница hasNextPage:false без cursor. У комментариев проверяются
уникальные id, даты, тело и убывающий updatedAt, как в idea-gate. Неизвестная форма
API, пропущенный документ, страница или поле даёт unverified, а не пустой зелёный дамп.

Каждый сырой файл связывается со свежим успешным нативным чтением того же проекта,
документа или задачи. Сверяются payload записи, успешный ответ и свежий объект.
Дубли и расхождения failed. expectedRecords считает заголовки записей через разбор блоков idea-gate: mono-idea: approved, mono-prd: approved, mono-design: approved, mono-tech: approved и mono-package: start — только в комментариях проекта; mono-research — по fenced-блокам документов. Сокращённый входной тип сопоставляется точно с именем полной записи. Упоминания в прозе и журналы задач не считаются. Тот же разбор применяется к forbidden и выбору гейта; настоящий дубль остаётся failed. Допустимы только адреса monotest. Рабочий MCP либо
рабочий адрес записи останавливает все оставшиеся хосты/цепочки; результат содержит
manualRemoval содержит лишь ссылки успешных мутаций: чтение, ошибка или отсутствие результата ссылку не добавляют. Удаления нет. Ошибка дампа не скрывает уже
наблюдаемую рабочую запись. Для отказа Idea без указателя проекта отдельный
полный list_projects по имени прогона доказывает отсутствие проекта; одного
отсутствующего локального файла недостаточно.

Codex сохраняет MCP-запрос через точную форму `const r = await tools.<имя>(<JSON>);
text(r);` (одна строка, один MCP на exec, буквальный JSON аргументов). Прямые
нативные MCP также принимаются. Произвольный JS не разбирается: без связи input,
успешного output и dump запись остаётся unverified. Claude использует связанные
tool_use/tool_result. Все оболочки ошибок сохраняют неуспех.

Проверяющий подаёт `recordBindings` в запросе suite: карта id ожидаемого пункта
в абсолютный JSON-файл. Это доказательства из следа, не новый список ожиданий:

```json
{
  "approvalBindings":[{"recordId":"<written-id>","windowCallId":"<native-id>",
    "shownLine":12,"currentLine":26,"text":"<exact shown content>","documentId":"<optional-document-id>"}],
  "gates":[{"command":"verify","recordId":"<idea-comment-id>"}]
}
```

shownLine — последний видимый текст владельцу в ходе решения: у Claude перед вызовом окна, у Codex после async-вызова перед терминалом хода. Ранний текст, заменённый последним сообщением, не утверждён. currentLine — свежий нативный
get_* после ответа и до записи; его тело должно совпасть с показанным. Для list_comments можно указать currentRecordId. У самодостаточного снимка Idea/Tech допустима currentLine самой записи: точные исходящие байты сравниваются с показанными, затем idea-gate независимо сверяет сохранённую текущую версию. Новому
проекту вместо чтения ещё не существующего объекта сверяется description запроса
создания. Запись обязана быть после подтверждённого нативного ответа «Утвердить»;
пустой ответ, отказ и «Ещё обсудить» его не заменяют. Для привязки документа
проверяются его id и updatedAt в записи. Привязки готовит независимый тестировщик по следу; при первом suite без этих файлов запись остаётся unverified. После разбора он вызывает skills-records.mjs на сохранённом дампе и включает проверенный результат в отчёт/сертификат, сохраняя первоначальный исход. Отсутствующая привязка — unverified,
изменённая версия или ранняя запись — failed. У native McpToolCall начало записи доказывает единственный содержащий его exec с тем же буквальным JSON-вызовом и связанным output; completion сам по себе не начало. Без такого доказательства порядка — unverified. Аргументы каждого чтения страниц ограничены фиксированным набором инструмента и неизменны в цепочке курсоров; query у документов/задач и другие фильтры полноты не доказывают. У list_projects только точное имя прогона; прежний list_documents без optional includeArchived остаётся допустимым, но флаг нельзя менять между страницами. Сверка запускает idea-gate из
проверяемого пака: verify для Idea, tech для Tech Evaluation (prd.json и tech-spec.json
копируются из дампа), design для mono-design, route для остальных утверждений.
Наличие PRD с next=design не подтверждает Design: нужны новая запись mono-design
и успешный design, который проверяет версию PRD и утверждённые изображения. Проверяющий не может
заменить результат ворот текстовым заявлением. Research без утверждения проверяет
свои свежие записи, переход отдельно проверяется следом. Рубрика разговора остаётся
обязательной: suite-result сам по себе не сертификат QA.

`node scripts/skills-records.mjs <request.json>` проверяет сохранённые доказательства
без хостового запуска: host, trace, sent (Claude), dumpDir, dumpTrace, project,
expectedRecords из сценария, approvalBindings, gates, packRoot и configFile.
Exit 0 — passed, 1 — failed, 2 — unverified. Suite публикует результат каждого
сценария/хоста, время, число уникальных задач monotest и незапущенный хвост.

Посев сохраняет `seedEndLine` настоящего успешного нативного терминала и
проверенный seedRoute.project. Посев требует успешных нативных записей и ожидаемого
состояния проекта/маршрута. Форма вызова, промежуточные поля и окна владельца для
него не сверяются строго. Строгая сверка payload и истории применяется к собственным
записям сценария; посев не заменяет его ожидаемые записи.
Граница без успешного терминала или с чужим проектом не принимается. Рабочая
запись до границы всё равно останавливает весь проход.
При нескольких правках одного объекта каждая проверяется по связанному ответу
(или промежуточному чтению до следующей записи), а последние значения полей —
по финальному свежему дампу. Недоступное промежуточное значение unverified;
поздняя поправка не скрывает ошибочную первую запись. `state` связывается со
статусом задачи, метки сравниваются как множества имён/id, а не по порядку ответа.

CommandExecution и другие не-MCP элементы не являются записями. Неуспешное чтение
не подтверждает дамп; каждый файл требует успешного свежего MCP-чтения. Недоступный
результат фиксированного чтения даёт hostFailure/unverified и один изолированный повтор дампа.
Нативный CommandExecution внутри связанного exec доказывает, что буквальная строка
команды — данные: имена tools.mcp__monotest внутри неё не считаются вызовами записи.
Настоящий monotest-вызов в неподдерживаемой форме остаётся unverified; нативный
McpToolCall сохраняется независимо от внешнего exec. Исходник JavaScript не выполняется.

Нативный Codex `event_msg/item_completed/McpToolCall` связывает arguments и
result своим id и status=completed; внешний exec не считается второй записью.
Сырые MCP-обёртки в файлах раскрываются перед проверкой страниц и сопоставлением
с нативным чтением. Алиас MON-… допустим только вместе с UUID того же get_issue.
UUID статусов и меток связываются по нативному справочнику своей команды;
обновление статуса — также по stateHistory той же задачи. Сокращённый ответ записи
не заменяет полный get: последняя версия сверяется с полным дампом, промежуточная
требует чтения до следующей записи. Текст сверяется по словам и числам по порядку;
изменённое, пропавшее или лишнее слово, число или адрес ссылки даёт отказ, оформление нет.
Остальные расхождения красные; повтор курсора не доказывает полноту дампа.

У Codex shownLine указывает последний текст хода окна до ответа владельца;
у Claude — текст до окна. Если полная версия дана ссылкой на документ, привязка
содержит documentId и shownReadLine нативного чтения до окна: ссылка обязана быть
в показанном тексте, а content и updatedAt — совпасть до окна, после ответа и в дампе.
Чтение должно предшествовать и показу, и окну. Для версионируемых документов
оно требуется и при полном тексте в итоге; без него привязка unverified.
Поля документа, версии и снимка берутся из штатной записи утверждения, не из
пояснений рядом. Ручная привязка не заменяет последнее решающее окно.
Файлы для idea-gate строятся во временной копии;
исходный дамп, включая MCP-обёртки, не перезаписывается.

Проверки запуска действуют на главный след, все `additionalTraces` и все следы
дампа (`dumpTrace`, `dumpAdditionalTraces`). Везде нужны успешный терминал и
отсутствие записи после границы; запрещённый переход в дочернем следе не может
скрыться за неполным главным. Посев исключает только явно связанную часть
главного следа; окна и записи дочернего проверяются по его собственному хосту,
линиям и журналу `sent`, если он нужен Claude.

Каждое чтение сохранённого файла обязано начаться после завершения всех записей
сценария, включая дочерние. При отсутствии записей оно идёт после терминалов
сценария. Порядок связывают нативные линии одного следа или timestamps запроса
и ответа разных следов. Время завершённого McpToolCall не доказывает время
начала: используется консервативная граница начала его нативной сессии.
Claude без timestamps использует интервал процесса в штатном `result.json`:
`process.traceTiming` содержит имя и SHA-256 сырых байтов, начало и конец.
Драйвер сохраняет его сам, сырые события не меняет. Копия без совпадающего хеша,
mtime файла и времена из запроса проверки порядок не доказывают. Нет доказанного
порядка — unverified. Равные или перекрывающиеся времена не считаются «после».
Для нескольких версий объекта в разных следах также нужен доказанный порядок;
чтение текущей версии обязано закончиться до записи утверждения.

Дампом управляет `scripts/skills-dump.mjs`: очередь фиксированных MCP-вызовов,
курсор каждого следующего запроса, имена файлов и запись сырых нативных ответов.
Хост получает ровно одно чтение на ход. Shell, окна, чужие MCP и записи не нужны
для сохранения и запрещены. Нет полного ответа или терминала — unverified;
драйвер не достраивает ответ из текста модели. Префикс без имени MCP-инструмента
в строке кода не считается вызовом; реальные McpToolCall проверяются всегда.

Обязательные idea-gate выбираются скриптом по типу реально записанного утверждения
и выполняются даже без approvalBindings. Недостающие привязки собираются после
остальных проверок: только если записи, окна и ворота не дали другого сбоя,
результат содержит bindingOnly:true. Suite сохраняет этому пункту unverified,
и продолжает цепочку. Это правило действует для любого unverified, включая неполный
дамп и недоступное доказательство хоста: поздние этапы дают дополнительные сведения,
но исходный пункт остаётся unverified и вливание стоит. Только реальный failed
останавливает цепочку; рабочая запись по-прежнему останавливает весь проход.
При сбое после посева дамп всё равно читает подтверждённый seedRoute.project;
его существование не является запрещённым созданием проекта сценария.

После последнего целевого discuss/empty/refuse драйвер завершает сценарий на
успешном терминале, включая вопрос «Что обсудим?». Лишний ответ персоны не посылается.
Настоящее следующее окно не скрывается этой остановкой. Без полученного ответа
окно остаётся unverified, а его вопросы и роль сохраняются в отчёте.
Сокращённый save/get_project не сравнивается как полное описание. Markdown допускает
наблюдённое преобразование списка «- » в «* » и скобок ссылок; текст, адреса,
подписи ссылок, fenced- и indented-код и проверка дублей сохраняются.

Отказ хоста фонового дампа (в том числе native error/turn.failed Codex при capacity) — hostFailure/unverified, не ложная запись failed. Сбор повторяется один раз в новом каталоге `-retry-1`; `attempts` сохраняет оба результата и сырые следы. Нарушение read-only/monotest проверяется до повтора и остаётся failed. После двух отказов исходный пункт остаётся unverified, а suite продолжает цепочку. Нормализация Linear удаляет пустые строки после Markdown-заголовка и в конце обычного текста; содержимое абзацев, inline/fenced code и реальные изменения текста остаются значимыми.
