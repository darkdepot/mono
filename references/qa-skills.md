# Проверка скиллов

Читай, когда проверяешь продукт из скиллов. Это драйвер одного сценария и
механический проверяющий следа. Каталог и выбор по разнице описаны в
`evals/scenarios/README.md`; записи сверяет `scripts/skills-records.mjs`, сертификат получает заранее сохранённые ожидания из qa.skills.
Живые прогоны выполняет оркестратор.

## Ответы словами

T1 добавляет opt-in `expectedReplies`; до T2 нынешние сценарии с `windows` /
`expectedWindows`, раздел «Правила окна» и пины owner-dialog остаются прежними.
Один сценарий выбирает ровно один путь. Каталог хранит массив в `hosts.<host>`,
одиночный драйвер — в `scenario`; `windows` и `expectedWindows` в текстовом пути
не нужны. T2 потребляет этот формат без новой схемы.

```json
{
  "expectedReplies": [{
    "id": "idea-approval", "stage": "idea", "role": "approval",
    "summary": ["## Что", "## Зачем", "## Образ результата", "## Неизвестные"],
    "question": "Research", "asksStart": true,
    "reply": "принимаю", "intent": "agree",
    "outcome": {"approval": true, "startNext": true},
    "response": ["Утверждение записал, начинаю Research."]
  }]
}
```

`id` уникален в сценарии; `stage`: `idea`, `research`, `discovery`, `design`,
`tech-evaluation`, `handoff`. `summary` — непустые якоря видимого итога.
`question` — буквальный якорь последней строки вопроса (можно весь вопрос),
не готовая фраза для этапа. Драйвер не сообщает этапу ожидаемые слова,
намерение или исход. Последняя строка должна заканчиваться `?`.
Промежуточные вопросы тоже заранее описываются в этом массиве по порядку,
с `role: clarification` и ложными исходами; текстовая ветка не вызывает модель
для решения, что утверждать. Неожиданный вопрос останавливает сценарий.

`stageStartLine` результата драйвера — строка настоящего успешного terminal
после подтверждения пространства или посева; она передаётся trace/probe/records,
чтобы отделить подготовку от разговора этапа. Все вопросы после неё идут
строго по порядку: лишний вопрос или ответ вне политики — провал. Проверяется
завершение всего следа, включая хвост после ожидаемых обменов, в обоих хостах.
Текстовые проверки не обрезают след по `endLine`.

Последний элемент обязан задать `response`: непустой массив полных допустимых
ответов этапа после последнего `reply`. Сравнение дословное, без обрезки,
поиска ключевых слов или решения модели; допустимые варианты заданы до запуска
и этап их не получает. Для неясного ответа это разрешённый уточняющий вопрос,
например `response: ["Что смущает?"]`. Добавление к нему «Start Research?» или
предложения старта без `?` проваливает сценарий. Вопрос о старте допустим лишь
как явно заданный полный вариант `response` либо следующий ожидаемый обмен;
разрешённый вопрос сам по себе не разрешает запуск этапа.
После последнего ответа владельца допускается ровно один завершённый ответ
этапа из этого списка и больше ни одного хода, даже без ответа владельца.
Промежуточный `response` необязателен: следующий ход уже связан со следующим
элементом `expectedReplies`; если указан, он также сравнивается целиком.
Ни утверждения, ни промежуточные сообщения без ответа не пропускаются.
Каждая нативная реплика владельца после первого показа должна соответствовать
ожидаемому обмену; дополнительная реплика между ним и ответом этапа — провал.
Эта политика общая для обоих драйверов, probe, trace и проверки записей.

`reply` отправляется дословно следующим пользовательским сообщением после
успешного нативного завершения хода; проверяется фактическая доставка в след.
Для Claude текстовый драйвер включает `--replay-user-messages`: без нативного
подтверждения полученного текста доставка остаётся непроверенной.
`intent`: `agree` (согласие любыми заранее заданными словами), `correction`
(согласие с мелкой поправкой), `question`, `continuation`, `unclear`, `refuse`,
`defer` (утвердить, но позже), `start` (владелец сам прямо просит начать).
Синонимы — разные значения `reply`, без словаря распознавания в скрипте.

`role` задаёт смысл вопроса заранее: `approval` утверждает показанное,
`transition` спрашивает о старте, `clarification` уточняет и ничего не утверждает.
Idea, Discovery, Design и Tech Evaluation могут утверждать; Research только
начинает Discovery; Handoff записывает старт работы. `asksStart` явно задаёт,
спрашивал ли вопрос о старте. `outcome.approval` и `outcome.startNext` обязательны
и заданы до запуска, модель их не выбирает. Последнее поле означает старт
следующего этапа, а в Handoff — работы. `defer` всегда без старта; согласие
на уточнение всегда без записи и старта. Наличие слова «да» само по себе ничего
не доказывает. Истинный `startNext` требует наблюдённого вызова следующего этапа,
перехода проекта или `mono-package: start`; ложный запрещает такой старт.
Для цепочки, где следующий этап отдельно запускает suite, вопрос не спрашивает
о старте либо владелец откладывает его; ожидания этапа не переписываются драйвером.

Для `correction` обязательно:
`correction: {description: "Добавлен вопрос про Codex.", before: "...", after: "..."}`.
`before` — один точный фрагмент показанной версии, `after` — его замена.
Согласованная версия вычисляется только этой заменой; любые другие отличия —
провал. Многозначная или меняющая смысл поправка требует отдельного показа и
следующего элемента массива. `description` проверяется в следующем сообщении
этапа и в строке `Поправка: <description>` вне заборов записи. Для Design
поправка картинки означает новый показ, не текстовую замену PNG.

Проверяющий запись получает `expectedReplies` и `approvalBindings`:
`{recordId, replyId, shownLine, text, currentLine, shownReadLine?, documentId?}`.
`text` — вся показанная версия артефакта (не произвольная цитата); `shownLine` —
последнее видимое сообщение завершённого хода; `replyId` — id ожидания.
Для ссылки на документ `shownReadLine` связывает показ с нативным чтением до него.
`currentLine` связывает согласованную версию со свежим чтением после настоящего
ответа либо с точным outgoing snapshot Idea / Tech Evaluation. Машинные проверки
и полное независимое обратное чтение остаются обязательными.
Вне заборов записи обязательна строка `Владелец: ответил «<дословный reply>»`.
Подменённая цитата, другой вопрос, отсутствие ответа, запись до ответа или новая
версия без названной поправки проваливают проверку. Старый путь с «нажал» действителен.

Делегированное ожидание задаёт `by: orchestrator`, `reason` (дословная причина
в `reply` и строке `Причина: <reason>` записи). Утверждение хранит прежний
`by=orchestrator`; Idea, чья машинная строка не имеет поля by, хранит его отдельной
строкой вне забора. Для Idea binding дополнительно содержит
`ownerEvidence: {host, trace, shownLine, replyLine, text, question, reply}`.
Этот `trace` входит в `additionalTraces` с собственным `expectedReplies` владельца.
`text` — всё показанное сообщение, `question` — настоящая последняя строка вопроса,
`reply` — дословные слова владельца. Исходный след доказывает всю тройку раньше
делегированного согласия; пересказ, чужой вопрос и отсутствие слов не проходят.
В строке «Владелец: ответил» Idea хранит исходный ответ владельца.

`skills-audit` / `skills-proof` отделяют обычное пользовательское сообщение от
результатов инструментов. Claude требует parent `result: success`, Codex —
`final_answer` последним сообщением до `task_complete`; служебный вызов после
текста отменяет его. Размышление и дочерний итог не заменяют показ владельцу.
`skills-trace`, `skills-probe --text <request.json>` (host/trace/expectedReplies)
и проверка записей запрещают все три окна, включая неуспешную попытку вызова.
Концовки разных этапов сравниваются по последней строке в следе и в цепочке suite;
одинаковая концовка проваливает прогон. Семантику совета и вопроса по-прежнему
проверяет рубрика, механический проход не доказывает качество разговора.
После вопроса, продолжения мысли или неясного ответа требуется следующий
завершённый ответ этапа; при `unclear` он должен переспросить. Записи нет.

Локальная проверка: `node --test scripts/skills-owner.test.mjs
scripts/skills-trace.test.mjs scripts/skills-run.test.mjs scripts/skills-records.test.mjs
scripts/skills-probe.test.mjs scripts/skills-window-roles.test.mjs`.
Новые события в фикстурах синтетические и явно отделены от старых живых образцов;
они не доказывают видимость в приложениях или текущий живой прогон.

## Драйверы

Один вызов: `node scripts/skills-run.mjs <request.json>`.

```json
{
  "host": "codex",
  "cwd": "/scratch/workspace",
  "packRoot": "/scratch/pack",
  "outputDir": "/scratch/run",
  "authFile": "/scratch/auth.json",
  "timeoutMs": 3600000,
  "idleMs": 1000,
  "mcpServers": {"monotest": {"url": "https://example.test/mcp"}},
  "workspaceProof": {
    "tool": "mcp__monotest__get_workspace",
    "input": {}, "path": ["name"], "equals": "Test Space"
  },
  "scenario": {
    "prompt": "Начни этап для тестового проекта.",
    "brief": "Нейтральный бриф имитированного владельца.",
    "allowedTools": "*",
    "stopAfterExpectedWindows": true,
    "windows": [{"mode": "discuss"}],
    "expectedWindows": [{
      "id": "approval", "role": "approval", "decision": "Утвержд", "advice": "Совет",
      "reason": "Research", "summary": ["Что", "Дальше:"]
    }]
  }
}
```

`outputDir` должен отсутствовать: прогон никогда не перезаписывает другой.
`mcpServers` принимает только monotest и необязательный Paper. Подключения —
`url` либо `command`/`args`. Codex получает отдельный дом и ссылку на явно
переданный файл входа; установку копии плагина делает сам драйвер.
В конфиге отключённого Linear остаётся URL транспорта, иначе CLI не стартует.
Тестовые серверы получают `default_tools_approval_mode = "approve"`, чтобы
`approval_policy = "never"` не отказывал их разрешённым записям.
Приложения и удалённые плагины выключены. Claude использует
`--strict-mcp-config`, `--plugin-dir` копии, `--permission-prompt-tool=stdio`;
установленный mono выключен настройкой прогона.

До этапа требуется настоящий читающий вызов и связанный успешный результат,
который совпал с `workspaceProof`. Инструмент доказательства не обязан входить
в `allowedTools`. У Codex первый ход read-only; для exec драйвер задаёт точную
форму `const r = await tools.<tool>(<JSON>); text(r);`. Комментарий или строка с
именем инструмента не подтверждают исполнение. Если инструмент при старте
ещё не готов (`TypeError: tools.<tool> is not a function`), чтение повторяется
один раз в том же thread после проверки всех оставшихся действий и успешного
завершения первого хода. Чужой MCP или ранняя запись в его хвосте красные;
оборванный ход не допускает повтор. Второй сбой — `unverified`, этап не отправляется.
Другое пространство — красный результат. Ошибочная или чужая квитанция не
подтверждает доказательство. В реальном выводе exec служебный блок «Script
completed…» предшествует JSON: читается единственный блок, который разбирается
как JSON. Ошибочные флаги на обёртках и предках пути всё равно отвергаются.

Список действий закрыт: MCP вне monotest/Paper красный; запись до подтверждения
пространства запрещена. У прямого MCP-вызова Codex namespace соединяется с именем
буквально, как в [ToolName хоста 0.159.2](https://github.com/openai/codex/blob/rust-v0.159.2/codex-rs/protocol/src/tool_name.rs#L49-L55):
`mcp__monotest__` и `save_project` не теряют имя сервера.
`allowedTools` допускает `"*"` или массив с `"*"` —
все инструменты хоста; отсутствие поля означает `"*"`. Явный массив ограничивает
инструменты хоста. Любой `mcp__monotest__` разрешён после подтверждения,
даже если не перечислен. Установленный stage-agent вне проверяемой копии
по-прежнему запрещён. Изоляция обеспечивается тестовым домом и MCP-серверами;
списки команд не являются её границей. `allowedCommands` не используется:
команды не проверяются по содержимому и не требуют отдельного proof.

У Codex нет отказа до выполнения MCP: аудит идёт после хода. Нарушение уже могло
выполниться; результат красный, точная строка и появившаяся ссылка передаются
тестировщику. Драйвер не удаляет записи и не заменяет их независимую проверку.

Список информации открыт. Неизвестные события хоста, подтипы system/event_msg
и нетуловые блоки не отвергают прогон. Вызовы Codex видны в `response_item` с
`function_call`/`custom_tool_call` и в нативном `McpToolCall` ниже. Другие элементы, включая
`web_search_call`, записываются заметками в `result.notes`.
Из exec читаются имена инструментов; исходник не разбирается как JSON или
JavaScript. Переносы строк, шаблонные строки, некавыченные ключи, экранирование
и `ALL_TOOLS` допустимы. Имя MCP вне тестовых серверов остаётся красным.
Codex проверяет MCP-действия во всех `rollout-*.jsonl` тестового дома, включая
дочерние потоки: обычные вызовы и нативные `McpToolCall` с полями `server`/`tool`.
Нарушение ссылается на файл и строку дочернего следа. Окна, ответы и завершение
сценария подтверждаются только основным потоком; дочерний терминал не требуется.
Динамический доступ — заметка, без попытки деобфускации. Аудит — доказательство
для тестировщика, не защита от заведомо враждебного скилла.

Все доказательства пространства, окна, ответа и терминала проходят единый
`scripts/skills-proof.mjs`: известная форма успеха, связь с вызовом и отсутствие
`isError`/`is_error` на каждом слое, кроме точной квитанции намеренного отказа
Claude ниже. Окно Codex получает ответ только после
связанного известного `accepted:true`. Отсутствующее, ошибочное или неизвестное
доказательство даёт `unverified`. Нативный input Claude сравнивается структурно,
порядок массивов сохраняется. Намеренный отказ Claude доставлен только при точном
совпадении текста отправленного `deny` со связанным `tool_result`, у которого
`is_error:true`. Это доставка отказа, а не утверждение; этап продолжает ход,
его реакция остаётся в следе. Любая другая ошибочная квитанция — `unverified`.
Для отдельной проверки такого следа передай путь `sent` к записанным ответам
драйвера: без отправленного `deny` намерение отказа не угадывается.

По умолчанию `timeoutMs` — час для полного цикла этапа; автор сценария может
задать другой бюджет. Он также выбирает конец сценария и политики перехода:
рекомендованный ответ может запустить следующий этап.
`stopAfterExpectedWindows: true` (по умолчанию) заканчивает прогон после
доставки последнего ожидаемого ответа и свежего успешного терминала его хода.
Следующий этап больше не удерживает процесс до тайм-аута. Сырой след сохраняется
целиком; `endLine` обозначает последнюю строку проверяемого сценария.
События после этой границы не объявляют сценарий оборванным.
`false` оставляет разговор открытым для заданных `freeQuestions` после окон.
Ненулевой выход процесса, ошибка, тайм-аут и настоящий оборванный ход не зелёные.

Claude требует свежий parent result после последнего отправленного продолжения,
включая персону. Новый parent `system/init` открывает ход, которому нужен свой
result; child init его не меняет. `task_summary` не отменяет завершение.
Ответ персоны потребляет вопрос: следующее продолжение без нового подходящего
вопроса не получает ответ. Codex читает для выбора вопроса только свежую часть
продолжения и требует собственный task_complete
каждого продолжения с тем же `turn_id`, что у активного `task_started`. Старый
терминал не завершает новый ход и не задаёт `endLine`. Завершение на последней
разрешённой итерации принимается до ошибки лимита; незавершённый сценарий
по-прежнему падает, значение `maxTurns` по умолчанию — 128 для ролей и 32 для
прежних низкоуровневых образцов. Окно во время
предварительного чтения не заменяет окно этапа. Выход лидера процесса не отключает
сигналы его группе. Через фиксированные 500 мс после выхода лидера или тайм-аута
драйвер закрывает удерживаемые дочерними процессами stdout/stderr и завершает
ожидание. Истёкший бюджет остаётся `failed` с `host timeout`; нормальный выход
сохраняет результат доказательств. ESRCH и macOS EPERM для уже вышедшего лидера
не добавляют шум к исходной ошибке. Сообщение о завершении не отключает бюджет.
Само событие exit достаточно для тихого EPERM, даже до обновления полей процесса.
Остальные ошибки сигналов сохраняются в `process.cleanupErrors`, не заменяя вердикт
или исходный тайм-аут. Codex обрабатывает текстовый вопрос и после последней цели:
он получает ответ персоны либо прогон остаётся не зелёным.
Коды CLI: 0 — механический проход, 1 — `failed`, 2 — `unverified`.
`conversation.status` остаётся `unverified` до рубрики; код0 не сертификат QA.

## Точки чтения следа

`runScenario`/CLI вызывают `runClaude` либо `runCodex`; `finishRun` использует
`checkTrace`. `checkTrace`/CLI, `claudeWindows`, `codexWindows`, `probeClaude`/CLI
и `runPersona` используют общий `auditRows` и нативный proof gate.
`traceRows`, `codexItems`, `completedTrace` — чтение и предикат конца, не полный
вердикт сценария. `hostProcess` сохраняет сырой stdout, `readJsonLines` читает
JSONL; ошибки синтаксиса до `endLine` не пропускаются.
Самостоятельные offline-вердикты на синтетических следах при правильном
`runScenario` вынесены в MONO-294; это не повод ужесточать реальные формы хоста.

## Ответы владельца

Решающие ответы принадлежат файлу сценария, не модели. Каталог задаёт целевые
роли: `approval` по метке с «Утвердить», `transition` по «Начать» или
«Передать оркестратору». Промежуточные окна не сдвигают политику цели:
при вариантах выбирается рекомендованный, без них отвечает персона без инструментов.
Они записываются в результат и проверяются по общим правилам. Каждая цель
обязательна; лишняя цель или другая роль останавливает прогон. Прежние низкоуровневые
образцы без `role` сохраняют строгий список окон для регрессий MONO-288.
`recommended` — первый рекомендованный; `label` — точная метка, включая
` (Recommended)`; прежняя метка без суффикса также принимается;
`correction` — заданный `text`; `empty` — пустой ответ; `refuse` — заданный отказ;
`discuss` — «Ещё обсудить». Нет политики/метки — прогон останавливается.
Claude использует `updatedInput.answers` для каждого вопроса окна, отказ — `deny`
на всё окно. Общая квитанция сверяется по всем непустым ответам; если все ответы
пустые, нужна точная фраза отсутствия ответа. Несколько вопросов доставляются,
но нарушение разговора «по одному» остаётся красным.
Codex принимает вопрос без `options`: политики `correction`, `empty`, `refuse`
дают текстовый ответ. `recommended`, `label`, `discuss` требуют вариант и при его
отсутствии дают ошибку сценария, а не отсутствие нативного доказательства.
Codex отправляет наблюдённую форму `<send_user_message_question_reply>` через
`exec resume`; формы empty/refuse приложения не наблюдались и не выдумываются.
Для свободного вопроса `freeQuestions: [{"contains":"..."}]` запускает один
вызов модели того же хоста без инструментов с брифом и последним сообщением.

## Правила окна

Offline: `node scripts/skills-trace.mjs <request.json>` с `host`, `trace`,
`expectedWindows` и необязательным `rulesRoot`/`endLine`.
Источник — `references/owner-dialog.md` проверяемой версии; его SHA закреплён
в проверяющем. Правка правил меняет проверяющий и рубрику в том же PR.
Для ключа на старых версиях применяются нынешние правила.

Проверяется реальное окно с нативным доказательством и доставленным ответом:
суть/совет/основание в вопросе, рекомендованный вариант первым, две-три опции,
строка последствий и компромисса у каждой, одна тема за раз. У свободного окна
Codex без вариантов проверки сути выбора, рекомендации, числа вариантов и
последствий не применяются. Нативное исполнение и порядок итога проверяются. Полный итог —
видимый текст. У Claude он в сообщении окна до tool_use; сервисная работа
сбрасывает прежний итог. У Codex async итог — последнее сообщение хода.
`expectedWindows` задаёт обязательные целевые окна и их якоря. Заголовки разделов
нельзя требовать у окна, для которого правило их не задаёт; в режиме ролей массив
`summary` может быть пустым. Наличие видимого итога и порядок всё равно обязательны,
размышление их не заменяет. Промежуточные окна не получают якоря утверждения.
Отсутствующее целевое окно или
замена текстом — `failed`. Нарушения ссылаются на `trace:line`.
`phase: card` проверяет карточку до ответа; явный `excerpt` допускает только
заявленные пропуски среза и не превращает присутствующее плохое доказательство
в успешное. Полный след требует исполнения и ответа.

Регрессии: `node --test scripts/skills-{owner,run,trace,probe,proof,process}.test.mjs`.
18 записанных образцов проверяются тем же proof gate; намеренный отказ Claude
теперь подтверждает доставку, прочие контрольные вердикты сохранены. Каталог
`evals/scenarios/probe/live` добавляет обезличенные полные порядки событий обоих
хостов, двухблочный вывод, стартовую гонку, Claude с двумя вопросами и Codex
без вариантов. Пустая общая квитанция двух вопросов записана живьём; многократные
непустые ответы в тесте — синтетическое сочетание записанных одиночных форм. Исходный Codex-след оборван в Research:
fixture восстанавливает обезличенное имя сервера `sample` в `monotest` и имя
первого чтения в `get_workspace`; поздние имена инструментов остаются скрытыми.
Успешный fixture-контроль явно добавляет синтетический терминал известной формы,
а не объявляет его наблюдённым живым успехом. Окно Claude198 без текста остаётся
`failed`; тестовая поправка thinking→text названа синтетическим контролем.

## Рубрика разговора

Тестировщик читает весь след и выставляет каждому пункту `passed`, `failed`
или `unverified`, указывает точные `файл:строка` и объяснение. Отсутствие
доказательства не зелёный исход. Механический результат не заменяет этот разбор.

- Каждый вопрос содержит конкретный выбор, совет и причину; фрагменты сценария
  не совпали случайно с пустой формулой или цитатой правил. Вопрос по одному,
  суть в одной-двух фразах, у каждого варианта понятны результат и цена.
- Вопросы развивают разговор, не повторяют одинаковое начало и не спрашивают
  уже известное из брифа, предыдущего ответа или прочитанного материала.
- Полный итог находится в видимом чате, содержит позицию, различия и сильнейший
  довод против совета; файл, команда и размышление его не заменяют. Итог следует
  шаблону и пределу слов конкретного этапа из проверяемой версии owner-dialog.
- До окна закончены чтения, помощники, проверки и показ. После окна нет работы
  до ответа, кроме обязательного последнего async-итога. Уведомление помощника
  не ответ владельца. После финала драйвер не спровоцировал лишний ход.
- Пустой ответ, отказ и поправка не стали утверждением и не переоткрыли окно
  автоматически. Изменённый утверждаемый текст показан повторно перед согласием.
- Изоляция подтверждена до этапа; рабочий Linear не использован; сведения о
  неподтверждённых клиентах, Design, OAuth и форме ответа приложения сохранены.
  Проверку самих записей выполняет следующий слой QA, не эта рубрика.

Правила разговора старых версий для ключа оцениваются по нынешней рубрике.
Зелёный рубричный вывод возможен только после чтения доказательств, не по
самооценке этапа или наличию непустого текста. Публикация и общий сертификат
остаются за сессией тестировщика.


## Свежий дамп и сверка записей

После каждого этапа suite запускает отдельный read-only прогон через тот же хост,
с новым тестовым домом Codex либо strict MCP Claude, только с monotest (без Paper).
Окон и посева в нём нет. Закрытый перечень задаёт `dumpPrompt` в
`scripts/skills-records.mjs`, модель не сокращает список: project.json; все страницы
комментариев проекта; все страницы документов и get_document каждого; все страницы
задач, включая архив, get_issue каждой со статусом и метками и все её комментарии.
Имена: comments-N.json, documents-N.json, issues-N.json, соответствующие
*-N.request.json, documents/<id>.json, issues/<id>/issue.json и
issues/<id>/comments-N.json. Первая request — {}, остальные {cursor} из предыдущего
ответа; последняя страница hasNextPage:false без cursor. У комментариев проверяются
уникальные id, даты, тело и убывающий updatedAt, как в idea-gate. Неизвестная форма
API, пропущенный документ, страница или поле даёт unverified, а не пустой зелёный дамп.

Каждый сырой файл связывается со свежим успешным нативным чтением того же проекта,
документа или задачи. Сверяются payload записи, успешный ответ и свежий объект.
Дубли и расхождения failed. expectedRecords считает заголовки записей через разбор блоков idea-gate: mono-idea: approved, mono-prd: approved, mono-design: approved, mono-tech: approved и mono-package: start — только в комментариях проекта; mono-research — по fenced-блокам документов. Сокращённый входной тип сопоставляется точно с именем полной записи. Упоминания в прозе и журналы задач не считаются. Тот же разбор применяется к forbidden и выбору гейта; настоящий дубль остаётся failed. Допустимы только адреса monotest. Рабочий MCP либо
рабочий адрес записи останавливает все оставшиеся хосты/цепочки; результат содержит
manualRemoval содержит лишь ссылки успешных мутаций: чтение, ошибка или отсутствие результата ссылку не добавляют. Удаления нет. Ошибка дампа не скрывает уже
наблюдаемую рабочую запись. Для отказа Idea без указателя проекта отдельный
полный list_projects по имени прогона доказывает отсутствие проекта; одного
отсутствующего локального файла недостаточно.

Codex сохраняет MCP-запрос через точную форму `const r = await tools.<имя>(<JSON>);
text(r);` (одна строка, один MCP на exec, буквальный JSON аргументов). Прямые
нативные MCP также принимаются. Произвольный JS не разбирается: без связи input,
успешного output и dump запись остаётся unverified. Claude использует связанные
tool_use/tool_result. Все оболочки ошибок сохраняют неуспех.

Проверяющий подаёт `recordBindings` в запросе suite: карта id ожидаемого пункта
в абсолютный JSON-файл. Это доказательства из следа, не новый список ожиданий:

```json
{
  "approvalBindings":[{"recordId":"<written-id>","windowCallId":"<native-id>",
    "shownLine":12,"currentLine":26,"text":"<exact shown content>","documentId":"<optional-document-id>"}],
  "gates":[{"command":"verify","recordId":"<idea-comment-id>"}]
}
```

shownLine — последний видимый текст владельцу в ходе решения: у Claude перед вызовом окна, у Codex после async-вызова перед терминалом хода. Ранний текст, заменённый последним сообщением, не утверждён. currentLine — свежий нативный
get_* после ответа и до записи; его тело должно совпасть с показанным. Для list_comments можно указать currentRecordId. У самодостаточного снимка Idea/Tech допустима currentLine самой записи: точные исходящие байты сравниваются с показанными, затем idea-gate независимо сверяет сохранённую текущую версию. Новому
проекту вместо чтения ещё не существующего объекта сверяется description запроса
создания. Запись обязана быть после подтверждённого нативного ответа «Утвердить»;
пустой ответ, отказ и «Ещё обсудить» его не заменяют. Для привязки документа
проверяются его id и updatedAt в записи. Привязки готовит независимый тестировщик по следу; при первом suite без этих файлов запись остаётся unverified. После разбора он вызывает skills-records.mjs на сохранённом дампе и включает проверенный результат в отчёт/сертификат, сохраняя первоначальный исход. Отсутствующая привязка — unverified,
изменённая версия или ранняя запись — failed. У native McpToolCall начало записи доказывает единственный содержащий его exec с тем же буквальным JSON-вызовом и связанным output; completion сам по себе не начало. Без такого доказательства порядка — unverified. Аргументы каждого чтения страниц ограничены фиксированным набором инструмента и неизменны в цепочке курсоров; query у документов/задач и другие фильтры полноты не доказывают. У list_projects только точное имя прогона; прежний list_documents без optional includeArchived остаётся допустимым, но флаг нельзя менять между страницами. Сверка запускает idea-gate из
проверяемого пака: verify для Idea, tech для Tech Evaluation (prd.json и tech-spec.json
копируются из дампа), design для mono-design, route для остальных утверждений.
Наличие PRD с next=design не подтверждает Design: нужны новая запись mono-design
и успешный design, который проверяет версию PRD и утверждённые изображения. Проверяющий не может
заменить результат ворот текстовым заявлением. Research без утверждения проверяет
свои свежие записи, переход отдельно проверяется следом. Рубрика разговора остаётся
обязательной: suite-result сам по себе не сертификат QA.

`node scripts/skills-records.mjs <request.json>` проверяет сохранённые доказательства
без хостового запуска: host, trace, sent (Claude), dumpDir, dumpTrace, project,
expectedRecords из сценария, approvalBindings, gates, packRoot и configFile.
Exit 0 — passed, 1 — failed, 2 — unverified. Suite публикует результат каждого
сценария/хоста, время, число уникальных задач monotest и незапущенный хвост.


Посев сохраняет `seedEndLine` настоящего успешного нативного терминала и
проверенный seedRoute.project. Посев требует успешных нативных записей и ожидаемого
состояния проекта/маршрута. Форма вызова, промежуточные поля и окна владельца для
него не сверяются строго. Строгая сверка payload и истории применяется к собственным
записям сценария; посев не заменяет его ожидаемые записи.
Граница без успешного терминала или с чужим проектом не принимается. Рабочая
запись до границы всё равно останавливает весь проход.
При нескольких правках одного объекта каждая проверяется по связанному ответу
(или промежуточному чтению до следующей записи), а последние значения полей —
по финальному свежему дампу. Недоступное промежуточное значение unverified;
поздняя поправка не скрывает ошибочную первую запись. `state` связывается со
статусом задачи, метки сравниваются как множества имён/id, а не по порядку ответа.

CommandExecution и другие не-MCP элементы не являются записями. Неуспешное чтение
не подтверждает дамп; каждый файл требует успешного свежего MCP-чтения. Недоступный
результат фиксированного чтения даёт hostFailure/unverified и один изолированный повтор дампа.
Нативный CommandExecution внутри связанного exec доказывает, что буквальная строка
команды — данные: имена tools.mcp__monotest внутри неё не считаются вызовами записи.
Настоящий monotest-вызов в неподдерживаемой форме остаётся unverified; нативный
McpToolCall сохраняется независимо от внешнего exec. Исходник JavaScript не выполняется.

Нативный Codex `event_msg/item_completed/McpToolCall` связывает arguments и
result своим id и status=completed; внешний exec не считается второй записью.
Сырые MCP-обёртки в файлах раскрываются перед проверкой страниц и сопоставлением
с нативным чтением. Алиас MON-… допустим только вместе с UUID того же get_issue.
UUID статусов и меток связываются по нативному справочнику своей команды;
обновление статуса — также по stateHistory той же задачи. Сокращённый ответ записи
не заменяет полный get: последняя версия сверяется с полным дампом, промежуточная
требует чтения до следующей записи. Сравнение Markdown допускает наблюдённые
обёртки ссылок, маркеры списков и промежутки у заголовков и списков Linear.
Границы абзацев, fenced-блоки и многострочный inline-код сохраняются буквально.
Остальные расхождения красные; повтор курсора не доказывает полноту дампа.

У Codex shownLine указывает последний текст хода окна до ответа владельца;
у Claude — текст до окна. Если полная версия дана ссылкой на документ, привязка
содержит documentId и shownReadLine нативного чтения до окна: ссылка обязана быть
в показанном тексте, а content и updatedAt — совпасть до окна, после ответа и в дампе.
Чтение должно предшествовать и показу, и окну. Для версионируемых документов
оно требуется и при полном тексте в итоге; без него привязка unverified.
Поля документа, версии и снимка берутся из штатной записи утверждения, не из
пояснений рядом. Ручная привязка не заменяет последнее решающее окно.
Файлы для idea-gate строятся во временной копии;
исходный дамп, включая MCP-обёртки, не перезаписывается.

Проверки запуска действуют на главный след, все `additionalTraces` и все следы
дампа (`dumpTrace`, `dumpAdditionalTraces`). Везде нужны успешный терминал и
отсутствие записи после границы; запрещённый переход в дочернем следе не может
скрыться за неполным главным. Посев исключает только явно связанную часть
главного следа; окна и записи дочернего проверяются по его собственному хосту,
линиям и журналу `sent`, если он нужен Claude.

Каждое чтение сохранённого файла обязано начаться после завершения всех записей
сценария, включая дочерние. При отсутствии записей оно идёт после терминалов
сценария. Порядок связывают нативные линии одного следа или timestamps запроса
и ответа разных следов. Время завершённого McpToolCall не доказывает время
начала: используется консервативная граница начала его нативной сессии.
Claude без timestamps использует интервал процесса в штатном `result.json`:
`process.traceTiming` содержит имя и SHA-256 сырых байтов, начало и конец.
Драйвер сохраняет его сам, сырые события не меняет. Копия без совпадающего хеша,
mtime файла и времена из запроса проверки порядок не доказывают. Нет доказанного
порядка — unverified. Равные или перекрывающиеся времена не считаются «после».
Для нескольких версий объекта в разных следах также нужен доказанный порядок;
чтение текущей версии обязано закончиться до записи утверждения.


Дампом управляет `scripts/skills-dump.mjs`: очередь фиксированных MCP-вызовов,
курсор каждого следующего запроса, имена файлов и запись сырых нативных ответов.
Хост получает ровно одно чтение на ход. Shell, окна, чужие MCP и записи не нужны
для сохранения и запрещены. Нет полного ответа или терминала — unverified;
драйвер не достраивает ответ из текста модели. Префикс без имени MCP-инструмента
в строке кода не считается вызовом; реальные McpToolCall проверяются всегда.

Обязательные idea-gate выбираются скриптом по типу реально записанного утверждения
и выполняются даже без approvalBindings. Недостающие привязки собираются после
остальных проверок: только если записи, окна и ворота не дали другого сбоя,
результат содержит bindingOnly:true. Suite сохраняет этому пункту unverified,
и продолжает цепочку. Это правило действует для любого unverified, включая неполный
дамп и недоступное доказательство хоста: поздние этапы дают дополнительные сведения,
но исходный пункт остаётся unverified и вливание стоит. Только реальный failed
останавливает цепочку; рабочая запись по-прежнему останавливает весь проход.
При сбое после посева дамп всё равно читает подтверждённый seedRoute.project;
его существование не является запрещённым созданием проекта сценария.

После последнего целевого discuss/empty/refuse драйвер завершает сценарий на
успешном терминале, включая вопрос «Что обсудим?». Лишний ответ персоны не посылается.
Настоящее следующее окно не скрывается этой остановкой. Без полученного ответа
окно остаётся unverified, а его вопросы и роль сохраняются в отчёте.
Сокращённый save/get_project не сравнивается как полное описание. Markdown допускает
наблюдённое преобразование списка «- » в «* » и скобок ссылок; текст, адреса,
подписи ссылок, fenced- и indented-код и проверка дублей сохраняются.

Отказ хоста фонового дампа (в том числе native error/turn.failed Codex при capacity) — hostFailure/unverified, не ложная запись failed. Сбор повторяется один раз в новом каталоге `-retry-1`; `attempts` сохраняет оба результата и сырые следы. Нарушение read-only/monotest проверяется до повтора и остаётся failed. После двух отказов исходный пункт остаётся unverified, а suite продолжает цепочку. Нормализация Linear удаляет пустые строки после Markdown-заголовка и в конце обычного текста; содержимое абзацев, inline/fenced code и реальные изменения текста остаются значимыми.
