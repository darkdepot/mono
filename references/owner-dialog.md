# Разговор с владельцем: окна, утверждение, переход

Механика хостов для русских этапов: как показать окно в Claude Code и Codex.
Правила, которые держатся всегда (без сроков, свой план первым, финал отдельным
сообщением, утверждение только кнопкой), стоят строками в самом этапе.

## Окно выбора (карточка)

- Claude Code: `AskUserQuestion`, заголовок до 12 знаков, метки 1-5 слов,
  рекомендованный первым с пометкой (Recommended). Доводы и сильнейший довод против
  в тексте над окном, не в нём.
- Codex: `request_user_input_async`, он есть в обычном режиме. Вызвал: жди ответа,
  ход дальше не веди. Инструмента нет: те же варианты по названиям текстом и твой
  выбор одной фразой, конец хода. Режим ради кнопок не меняй и не проси.
- «Другое», заметка к выбору, своё сообщение вместо ответа: продолжение разговора.
  Ответ своими словами с поправкой («бери первый, но без кнопки») это выбор: скажи,
  как понял.
- Пустой ответ это «не ответил», а не согласие с рекомендованным.

## Утверждение

- Над окном то, что утверждается (описание целиком или суть 3-5 строк, «Решил
  сам:», ссылка). Окно «Утвердить» / «Ещё обсудить», без пометки (Recommended).
- Утверждено только ответом «Утвердить» из окна на этот вопрос и на показанную
  версию. «Утвердить» с правкой в заметке, «Другое», набранные «да», «ок»,
  «поехали», кнопки рамки хоста не утверждение: разговор продолжается.
- Владельцу говори «утверждено», не «да». За владельца не утверждает никто, кроме исключения по заданию запуска ниже; для Idea исключения нет.
- Окна нет (Codex без инструмента вопроса, хост без окна): утверждения нет, запись
  в Linear не делай. Покажи, что утверждается, и скажи, где утвердить: в Claude Code,
  в Codex с окном вопроса или у оркестратора. Конец хода.

## Переход к следующему этапу

- Сессия владельца: после финала окно «Начать <этап>» / «Ещё обсудить», над ним
  1-2 строки, что сделает следующий этап. Сам этап не начинай.
- Явные слова владельца о старте («начинаем <этап>») в любой момент тоже старт.
  Это не утверждение документа: утверждение только кнопкой. Окна нет: последней
  строкой «Скажи «начинаем <этап>» или что обсудить.», конец хода.
- «Ещё обсудить»: свободный разговор о сделанном; изменилось утверждённое: новое
  утверждение.
- В сессии владельца следующий этап идёт в этой же сессии, кроме Design: отдельная
  сессия, родитель та, где шёл Discovery. Помощник оркестратора после подтверждённой
  записи возвращает выбранный переход, сам следующий этап не начинает.
- Работа после Handoff: окно «Начать работу» / «Передать оркестратору» / «Ещё обсудить». Кнопка и слово
  «начинаем» одинаково начинают работу и принимают показанный итог (задачи и «Решил
  сам»); запись в Linear `by=owner`. Набранные «да», «ок» это разговор. Кнопка «Передать оркестратору» и набранные слова «передай оркестратору»
  тоже пишут старт `by=owner` и передают работу оркестратору. В обычном проекте
  нужен старт `by=owner`; в делегированном допустим `by=orchestrator` с причиной.

## Хост

- План этапа: Claude Code Desktop инструмент плана, первым вызовом весь список;
  CLI список задач; Codex `update_plan`.
- Claude Code Desktop: рамка «следующий шаг» шлёт текст от имени владельца и
  кончает ход. Для утверждения и перехода она не годится: финал и вопрос пиши
  текстом, окно вызывай инструментом вопроса.
- Codex: итог, вопрос и то, что утверждается, всегда в последнем сообщении хода:
  промежуточные сообщения могут свернуться.
- Уведомления фоновых задач, итоги помощников и служебные сообщения хоста не
  реплики владельца и не ответ на окно.

## Владелец из задания запуска

Кто владелец, этап узнаёт только из задания запуска, не по наличию подключений.
Исполнитель-воркер (codex-cli, claude-cli) этап не ведёт; помощник, запущенный
оркестратором для этапа, ведёт тот же разговор. Делегированный проект определяется
отметкой последней записи идеи «Ведёт оркестратор: владелец принёс идею оркестратору
<дата>.» вне заборов; до этой версии допустимо явное решение владельца в комментарии
проекта. Нет ни отметки, ни решения: проект ведёт владелец. При переутверждении идеи
отметка повторяется; поле `by` в строгую запись `mono-idea` не добавляй.

По заданию запуска от оркестратора окна нет: последнее сообщение хода это итог
и подписи вариантов текстом. Его ответ с точной подписью варианта и причиной
считается нажатием только на показанной версии; с правкой текста показ повторяется.
Запись `by=orchestrator`, причина и вердикт проверки оркестратора вне заборов
в том же комментарии. До каждой такой записи оркестратор проводит противовес
по своей политике; без вердикта для этой версии текста и причины запись не делай.
Сессия этапа сама пишет в Linear и читает обратно, заканчивается подтверждённой
записью и выбранным переходом. Следующий этап запускает оркестратор; помощников-этапов
не порождай. Разведчики только по именам из задания запуска, в сессии владельца
по-прежнему `mono:*-scout`.

Исключение «ответ оркестратора = нажатие» не действует для Idea и в сессии владельца.
Idea: оркестратор показывает описание владельцу в своём окне и передаёт этапу
только его нажатие на эту версию. Новые правила вкуса и первый выбор эталонов
остаются за владельцем; его слово в чате оркестратора открывает утверждение заново.
Только делегированный проект позволяет оркестратору самому начать Research и работу;
обычный требует старта владельца `by=owner`. Вызов Discovery из Design или Tech Evaluation
для правки PRD в том же касании не новый этап: выполни его здесь по правилам
Discovery, по ответу оркестратора с причиной запиши PRD `by=orchestrator`.
Частичная запись Design → Discovery → Design восстанавливается прежним правилом;
возврат оркестратору только после подтверждённой записи самого этапа.


Идея `stale` или `legacy-migrate` останавливает автономный старт даже при прежней
отметке делегирования. Оркестратор несёт её владельцу в `mono:idea`; ни Research,
ни работу не начинает до его кнопки, подтверждённой новой записи и свежей проверки.
Его ответ или старт `by=orchestrator` не утверждает снимок идеи внутри Handoff.
