# PRD, утверждение, записи, финал

## PRD

Документ Linear `PRD: <проект>`, один на проект, по шаблону и контракту. Это
выбранное решение на двух страницах, а не стенограмма: разговор и невыбранные
решения живут в комментарии решений. Длинный PRD значит, что решение не сложилось.

- «Кратко»: до 5 строк: решение словами владельца, кому, что меняется; строка
  «Размер: мелочь | обычное | проект», бюджет только если владелец его назвал.
- «Сценарии»: до трёх; первый это показ, который владелец видел до выбора.
- Требования `R`: мелочь 1-3, обычное до 6, проект до 10. Больше десяти: режь
  или дели проект. Примеры приёмки `AE` только для условного поведения, до 4.
- Акторы только реально разные; процессы по 3-5 строк или опусти, если их
  покрывают сценарии. Пустые и повторяющие соседей разделы опускай.
- «Допущения»: первым главное, что должно быть правдой.
- «Что не входит в MVP»: то, что отверг владелец или ушло из невыбранных решений.
  Из разговора, а не догадкой ради строки.
- «Критерии успеха»: признак успеха для владельца и для следующих этапов, что
  не должно ухудшиться, когда смотрим. Число из слов владельца, Research со ссылкой
  (`[Ф<n>]`) или «Решил сам:».
- «Что решили по неизвестным Research»: строка `Н<n> <словами>: <решение>` на
  каждое: решено (как), принимаем риск (какой), проверяем параллельно (как, где
  результат), сначала проверить (только если без ответа строить нельзя), не делаем.
- «Открытые вопросы»: у каждого, кто решает: Design, Tech Evaluation или владелец.
  Продуктовое закрой здесь, остальное явно оставь следующим этапам.
- «Связи»: «Исследование» и задача этапа.

Источник держи в комментарии решений; в PRD ссылку ставь только у чисел, пределов
и «не должно». Отменённая в разговоре формулировка заменяется, а не остаётся рядом.

## Комментарий решений

Один в задаче этапа: заведи после выбора, дополняй, закончи после утверждения;
по нему продолжают после перерыва. Строку `Исследование:` не убирай.

```markdown
**Решения Discovery: <проект>**
Постановка: <словами владельца> → <наша | оставили>, потому что <…>.
Совет Research: <совет>; решили: <…>, потому что <…>.
Выбрано: <решение>; кем: <владелец | оркестратор>, потому что <…>.
Не взяли: <решение>: <причина>; …
Опасения: <словами владельца> → <ход>; … | нет.
Вторая модель: <2-4 строки> | без второго мнения.
Решил сам: <пункты> | нет.
Исследование: <ссылка>
PRD: <ссылка>
```

## Утверждение

По `owner-dialog.md`: итог до 120 слов, вывод; «Тебе решить» по условию;
главное; «Не берём» с причиной; «Дальше» и ссылка на PRD. При правке
«Было / Стало». Решение про опыт владельца сначала обсуди, не прячь в технику.

PRD, комментарий решений, строитель, проверки и подготовка передачи до итога.
Запомни `document` и `updatedAt`, заранее вычисли `design=` и `next=` по правилам
ниже. В том же ответе прямо под итогом, без вызовов между ними, одно окно:
«Утвердить и начать <этап>» / «Утвердить, продолжу позже» / «Ещё обсудить».
Окна нет: итог и подписи, где утвердить, без записи утверждения. Помощник
оркестратора даёт тот же итог и подписи последним сообщением хода.

## Запись утверждения

Комментарий на проекте: первая строка в заборе `text` байт в байт, вторая вне забора
причина решения о дизайне; затем «Владелец: нажал «<выбранный вариант Утвердить…>»» или
«Оркестратор: <почему>».

```text
mono-prd: approved project=<uuid проекта> document=<uuid PRD> updatedAt=<updatedAt PRD> design=needed|not-needed next=design|tech-evaluation|handoff by=owner|orchestrator
```

## Маршрут и повторное утверждение

При первом и каждом повторном утверждении, включая старую запись без
`design=`, сначала заново реши, нужен ли макет, затем размер PRD. Решение
меняет то, что пользователь видит (Research `interface: true` или затронутый
экран/окно): `design=needed next=design`. Иначе `design=not-needed` и по
«Размер»: обычное/проект `next=tech-evaluation`, мелочь `next=handoff`.
Новая первая запись всегда с `next=`. Только повторная `design=not-needed`
после прежней записи без `next=` сохраняет отсутствие поля; прежняя запись
должна существовать. Отдельной записи «дизайн не требуется» нет.

Решение и маршрут пиши одной `mono-prd: approved`, причину строкой ниже;
частичного состояния и временного маршрута нет. Неизвестные значения и
`design=needed` без `next=design` — `bad-record`. Просьба владельца о Design
на старом пути или после `not-needed` означает повторное утверждение PRD с
`design=needed next=design`, а не отдельную пометку.

Сменился размер у записи с `next=`: пересчитай маршрут; размер дизайнера его
не меняет. Маршрут изменился: нижние `mono-design` и `mono-tech` не действуют,
этапы проходят заново с показом по режиму. Тот же маршрут: следующий этап сам
решает, изменились ли экраны/страница; прежние получают новую запись без показа,
новые — новый показ. Даже при прежнем `updatedAt` новая запись нижнего этапа
должна идти после последнего утверждения PRD.
Старая запись без `design=` до повторного утверждения идёт прежним путём по
своему `next=` или его отсутствию; записи решают, не дата выпуска.

## Отложить по странице техлида

По вызову Tech Evaluation после утверждения страницы со строкой «отложить»
перенеси только названный пункт в «Что не входит в MVP», прочитай PRD обратно
и запиши новое `mono-prd: approved` с его `updatedAt`. Заново реши дизайн, затем размер по правилам выше;
на запрошенном старом пути без дизайна запиши `next=tech-evaluation` (U5).
Ведёт владелец: `by=owner` и строка «по нажатию на странице техлида <дата>»;
ведёт оркестратор: `by=orchestrator` и причина. Второй карточки владельцу нет:
страница уже утверждена. Допиши строку в комментарий решений своей закрытой
задачи, не открывая её. Это исключение из повторного входа задач этапов в
`<корень>/references/lifecycle.md`. Tech Evaluation получает новую версию PRD
и только затем пишет Tech Spec и запись `mono-tech`; PRD сам он не меняет.

### С макетом

Если есть годная `mono-design: approved`, техлид сначала проверяет картинки.
Пункт PRD на утверждённых экранах не переносится в «Что не входит в MVP» по
строке техлида: он до показа страницы возвращает проект в Design с причиной
«предлагаю убрать: …, потому что …». Это новый круг по R8/R11; дизайнер
показывает новый макет и «Было / Стало», одно утверждение вызывает Discovery
в том же касании. Только Discovery правит PRD и пишет его утверждение
`design=needed next=design`, затем дизайнер новую запись с новым `prd-updatedAt`.
Записана только первая: повторяется вторая по тому же согласию.

Пункт, которого на утверждённых экранах нет, откладывается строкой на странице
как выше. После «Утвердить» в том же касании Discovery правит только его и
обновляет запись PRD, Design сам проверяет экраны: не меняются — новая запись
с теми же картинками без показа (U12), затем Tech Spec и `mono-tech` с id новой
записи дизайна. Второй карточки нет. Чужая правка PRD вместе с отложенным
пунктом не покрывается этим согласием. Контракт PRD и отпечаток не меняются.

## Порядок

1. Найди PRD (`run.md`, «Повторный вход»): есть, обнови; нет, создай. Подготовь
   передачу и проверки черновика до итога и окна.
2. Покажи итог и окно на запомненные `document` и `updatedAt`, без вызовов между ними.
3. После нажатия молча перечитай: версия та же, запиши утверждение, прочитай его
   обратно. Другая: «Было / Стало», обновлённый итог и окно снова, без записи.
4. Обнови сырые проект и все страницы комментариев в `<папка>/linear/` по `run.md`.
   Выполни `node <корень>/scripts/idea-gate.mjs route --mode fresh --dump <папка>/linear --config <конфиг>`.
   Только exit 0, «Готово», JSON `pass`: закончи комментарий решений, закрой
   задачу этапа и прочитай Done обратно. Статус проекта не меняй.
5. `mono:check discovery` по свежим входам и закрытой задаче; без PASS перехода нет.
6. Одна строка о записи и выбранный переход. «Продолжу позже» без старта;
   позднее «начинаем <этап>» после свежей сверки и проверки без нового утверждения.

Запись или проверка не удалась: один повтор, уже записанное утверждение той же
версии переиспользуй без дубля. Снова не вышло: скажи, что именно не сделано,
следующий этап не стартует. Комментарий к PRD тоже сдвигает `updatedAt`:
«устарело» требует нового итога с окном.

## Передача

Второго итога и окна после записи нет. Маршрут из утверждения: `next=design`
Design, `next=tech-evaluation` Tech Evaluation, `next=handoff` или без поля Handoff.
«Утвердить и начать <этап>» и есть явный старт; отдельное «начинаем» не нужно.
«Ещё обсудить» после записи: разговор; PRD изменился, новое утверждение.

Для Design до итога подготовь `$TMPDIR/mono-design/<проект>/brief.md`: ссылки
на проект, PRD и исследование, пути к памяти владельца и продукта, размер.
После успешной записи добавь проверенную ссылку утверждения в задание.
Claude Code Desktop открывает свежую сессию дизайнеру через
`mcp__ccd_session__start_session`; Codex/терминал получает тот же файл и запуск:
`$mono:design <путь к brief.md>` в Codex, `/mono:design <путь к brief.md>` в Claude Code.
Сам чужую задачу этапа не создавай. Помощник возвращает подтверждённую запись и
переход оркестратору, сам следующую сессию не порождает.
