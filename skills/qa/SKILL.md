# Mono QA

Тестировщик проверяет поведение на хосте, вне песочницы исполнителя. Вызов только
`mono:qa`: короткое `qa` может означать другой скилл. Не исправляй код продукта,
не вливай и не принимай самооценку исполнителя за доказательство.
Модель: [role:qa](<корень>/references/model-policy.md#roles); разреши роль через
`resolveRole` с конфигом продукта, запиши модель и effort до прохода. Нет нужного
хоста или роли — остановись с «не проверено», не заменяй исполнителем.

Прочитай сразу:
1. `<корень>/references/model-policy.md`

Прочитай, когда:
- `<корень>/templates/qa-output.md` — перед записью списка ожиданий и отчёта.
- `<корень>/references/qa-recipes.md` — выбор рецепта, запуск копии и запись доказательств.

## Вход

Задание даёт задачу и её «Готово, когда», риск, текущие PRD с R и AE, PNG
утверждённого макета (если есть экран), head и base, конфиг продукта, корень
оркестратора и место публикации в Linear. Для `project` нужны проект и полный
состав сборки: задачи с их head. Последняя задача требует собственного прохода
`task` и отдельного `project`; запуск финального прохода принадлежит оркестратору.

Обычный режим `ship`: восстанови настоящий `mono-ship green certificate` из
Linear и проверь `validateShipCertificate` для задачи/head. Создай тестовое
слияние head с base текущего main в отдельной копии; сохрани head, base и SHA
слияния. Проверяй слияние, а не только ветку. Позднейший сдвиг main сам по себе
не требует повтора; смена head требует ship и всего списка заново.

Режим `given-version`: для пилота или ручного задания достаточно точной версии
head и base без ship-сертификата. Отчёт, полный список и доказательства те же;
`gateEligible: false` обязателен. Не называй это разрешением вливания.

Рецепт выбирай по порядку: блок `qa` конфига, затем запись **этого продукта** в
справочнике рецептов. Примеры вымышленного продукта подключением не являются.
Если подключения нет, принимай рецепт файлом задания (прочитай файл целиком,
`readQaRecipeFile` проверяет доступность); `recipeSource: file` всегда даёт
`gateEligible: false`, даже при наличии ship-сертификата. Нет рецепта — пункты
`unverified` с причиной, не зелёный. `workflows.qa` и `qaAuth` сами рецептом не являются.

## Ожидания до первого действия

До установки, старта и первого действия в приложении сохрани список по шаблону
в постоянную папку доказательств. Включи каждый критерий задачи, связанные R и AE
PRD, сверку PNG и эвристики: границы, пусто, один, много, ошибочный ввод,
прерывание, повтор, смена состояния. У каждого устойчивый id, источник и
проверяемое ожидание. Для `project` включи **все R и AE PRD** и состав сборки.
Оркестратор хранит этот список как `expectedItems` и `taskCriteria` для проверки
сертификата; не извлекай ожидаемые id из готового сертификата.

Молчание или противоречие задачи/PRD: `unverified`; оркестратор принимает решение,
видимое пользователю изменение передаёт владельцу. Решение записывается в задаче
или PRD до повторного прохода. Нельзя подогнать ожидание под увиденное.
Правка без поведения: обоснуй это по diff и задаче, закрепи `kind: no-behavior`
во входе проверки и выдай короткий сертификат с причиной; не используй его,
чтобы пропустить критерии наблюдаемого поведения.

## Копия и данные

Создай копию вне worktree исполнителя: для пака detached worktree; для продукта,
в чей репозиторий писать нельзя, независимый клон без remote. Убедись в точном
head до первого скрипта. Выполняй только рецепт: установка, сборка, необходимые
заглушки. Запиши начальный статус и разрешённые рецептом изменения; в конце
сверь дерево, включая новые/игнорируемые файлы. Любая иная правка делает вердикт
недействительным, нужен чистый проход. Не исправляй продукт ради запуска.

У защищённой копии до первого скрипта и после каждой смены версии: пустой обычный
`.env`, нет remote и ссылок на общие настройки; OTA выключены, адрес API только
на одноразовый стенд с синтетическими данными, если этого требует рецепт.
Нет стенда у данной версии или появилась общая ссылка — остановись, пункты
`unverified`. Настоящие данные только на чтение либо тестовый вход по `qaAuth`;
если задание разрешает лишь синтетику, настоящие данные не используй вообще.
Подставные ответы не доказывают поведение, зависящее от формы ответа бэкенда.

Стартуй на выданном свободном порту. Готовность должна доказать личность копии:
PID слушателя, cwd, маркер именно её сборки (и отказ для чужого маркера).
Для терминала запиши cwd и полный SHA. Нет запуска или подтверждения личности —
`unverified`, не зелёный. Останавливай только свои процессы и симуляторы.

## Проход и исходы

Глубину выбирай по риску и критериям: экран — живая копия с видео и трассой,
терминал — живые команды с записью asciinema, без поведения — короткая проверка
с причиной. Для экрана проверь и основной путь, и границы по составленному списку.
Проверки скриптов исполнителя не заменяют независимого прохода.

Веб: свой безголовый Playwright CLI, выданный порт проверенной копии, свой конфиг
без чужого webServer/reuseExistingServer, WebM и trace; глава/время на каждый пункт.
Мобильное: локальная сборка, свой симулятор, запись `simctl recordVideo`, остановка
SIGINT; тап должен менять экран со снимками до/после. Наблюдённый рецепт работает
на iOS 26.5; запуск на iOS 27 не подтверждён, нельзя переносить успех между версиями.
Нет управления или записи — мобильные «не проверено» с причиной.

Исходы: `passed`, `failed`, `unverified`. Без доказательства — `failed`, не успех.
Нестабильность — `unverified` и повтор на чистом состоянии. Нестабильно и на main
без изменений задачи: отдельная задача, `excluded` с причиной и ссылкой на неё;
критерий «Готово, когда» исключать нельзя. Снятая ложная тревога остаётся в отчёте
с причиной; спорный пункт перепроверяет оркестратор, исполнитель вердикт не меняет.

Запрещённое внешнее действие не выполняй: дай владельцу одну строку сценария.
До его выполнения владельцем и проверки результата оркестратором — `unverified`;
после запиши исход с доказательством. Молчание не согласие.

Каждый баг — одна проблема: шаги, ожидаемое/фактическое, критерий или R/AE/макет,
с которым расходится, доказательство. Передай оркестратору для исполнителя
(ship-fix); после исправления новый ship/head и **весь** список заново.
В финальном `project` баг становится новой задачей, выпуск ждёт её исправления
и полного повторного прохода. Сменился состав сборки — сертификат недействителен.

## Отчёт и сертификат

Доказательства: `<корень оркестратора>/qa/<KEY>/<head>/`, не временная папка.
Открой видео/трассу/запись, проверь воспроизведение и читаемость файлов;
зелёный запрещён, если файл нельзя открыть. Сохрани отчёт языком Linear продукта:
что проверено, что не проверено и почему, баги, ссылки на главное видео;
вердикт должен быть понятен без просмотра. Для `project` один отчёт по проекту
с видео главных сценариев и полным R/AE списком.

Сформируй `mono-qa certificate` по шаблону и проверь
`node <корень>/scripts/qa-certificate.mjs <report.json> <expected.json>`.
Ожидаемые scope/задача/проект/head/base/kind/mode/recipeSource, список пунктов и
состав сборки берутся из задания, не из сертификата. Для `ship` передай проверяемый
ship-сертификат, для файла — путь рецепта. Скрипт проверяет файлы, не доказывает
содержимое видео: открытие и смысловая сверка остаются обязанностью тестировщика.

Публикует и читает обратно сертификат, отчёт, главное видео вложением и отчёт
проекта **сессия mono:qa** (оркестратор или владелец), не исполнитель. Уважай
место публикации задания: при проверке сторонней копии не пиши в её Linear,
репозиторий и корень оркестратора. WebM вложением наблюдался играющим по ссылке
в Chrome; встроенный плеер карточки и MP4 мобильного в Linear не подтверждены.
Верни ссылки и результат read-back. Публикация не удалась — явно скажи, что
не опубликовано; локальный зелёный результат публикацией не становится.
Ворота, очередь посадки и автоматический вызов отсюда не включай.
