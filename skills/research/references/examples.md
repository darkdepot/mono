# Примеры сообщений этапа Research

Образцы на настоящем прогоне: проект «Этап Handoff: тимлид сверяет готовое и режет
на задачи», 19.10.2026. Это образец тона и формы, а не текст для копирования.
Совет говорит, что делать со следующим шагом, а не какое решение строить.

## План в списке задач

```text
Как резать проект на задачи
Когда спрашивать тебя и что теряем
Когда нужен Tech Evaluation
Как быть с проектами на старом пути
Свести ответ и совет
```

В окне «Начать исследование» первые четыре: последний пункт добавляет сам Research.

## Старт

После входа, вместе с разведчиками:

```text
Исследую, каким будет новый Handoff: как резать на задачи, когда спрашивать тебя, когда нужен Tech Evaluation и как быть с проектами на старом пути.
Учитываю твои решения из разговора: режет Handoff, без Tech Spec, утверждение пакета только при конфликтах. Твоё сомнение про последний взгляд перед стартом проверяю во втором вопросе.
```

## Итог направления

```text
Когда нужен Tech Evaluation: сейчас Handoff сам пишет Tech Spec, а правило пака разрешает работу без него только для мелких изменений, сквозные и релизные без него не стартуют.
Тут подвох: твоё «без Tech Spec» упирается в это правило. Решение оно не отменяет, но правило придётся менять явно, это пойдёт в совет.
```

```text
Как резать: у других режут по поведению, которое можно проверить: у каждой задачи «готово, когда» и явные зависимости, задачи с общими файлами не идут параллельно. Общего размера задачи нет, мерки у всех разные.
У нас по умолчанию одна задача на проект, так что правило нарезки придётся менять в любом случае.
```

```text
Как резать, по нашей истории: пакет Research сначала порезали на 7 задач, после твоего «не переусложнять» осталось 3. Потом пакеты Research и Discovery пересобирали по 2-3 раза, но из-за правок PRD и Tech Spec, а набор задач не менялся.
Значит, нарезку ломает не форма задач, а то, что меняется выше. Для Handoff это довод сверять вход тщательнее, а нарезку держать простой.
```

Пусто:

```text
Когда спрашивать тебя: что считать конфликтом между проектом, исследованием и PRD, у нас нигде не записано, смотрел прошлые пакеты, ревью и решения по Handoff. Пункт в работе: не хватает того, где эту границу проводят другие.
```

Два итога разом: те же абзацы одним сообщением, без вводной строки.

## Добор пробела

```text
Добираю одно: по каким признакам решают, что нужен отдельный технический дизайн. От этого зависит, когда новый Handoff будет звать Tech Evaluation.
```

## Фактов не хватило, по ходу

```text
Насколько хуже выполняются задачи без Tech Spec, не измерял никто: ни у нас, ни у других, а по старым проектам это не восстановить. Ответа в рамках исследования не будет.
Дешевле всего проверить на первом живом проекте через новый Handoff: посчитать остановки и переделки исполнителя. Больше, чем у последних пакетов, значит нужен порог для Tech Evaluation.
```

## Владелец пишет по ходу

```text
Учёл: добавил в план, как Handoff будет брать документы Design, когда этап появится. Остальное не меняется.
```

## Поправка

Шаг поменял вывод, который владелец уже видел. Одна строка, обычно в финале:

```text
Поправка к тому, что писал по коду: старый путь закрывается только для новых проектов. Три проекта с уже одобренными пакетами остаются на нём, новый Handoff им понадобится, только если пакеты придётся чинить.
```

## Финал: готово

Финалы ниже для проекта не на старом пути. На старом пути (одобренный пакет
прежнего Handoff) на месте Discovery стоит Handoff (`run.md`, «Следующий этап»).

```text
Исследование по новому Handoff: <ссылка>.
Искал, как резать на задачи, когда спрашивать тебя, когда нужен Tech Evaluation и как быть со старым путём.
Ответ: резать по проверяемому поведению с «готово, когда» и явными зависимостями. Спрашивать тебя, только если выбор меняет то, что получит пользователь, или ведёт к необратимому; остальное Handoff решает сам и записывает.
Твоё сомнение про последний взгляд перед стартом фактами не закрыть: сколько вопросов даст новая сверка, видно только на живом проекте, посчитаем на первом.
Неожиданное: твоё «без Tech Spec» требует явно поменять правило пака. Нарезку у нас ломали правки выше по цепочке, а не сама нарезка.
Совет: делать. Нарезку и сверку берём готовыми у практиков, мешает только правило Tech Spec, его решаем первым.
Дальше Discovery: первым решим, как Handoff режет без Tech Spec и когда спрашивает тебя.
```

## Финал: не делать

```text
Исследование по напоминаниям клиентам: <ссылка>.
Искал, читают ли клиенты напоминания и снижают ли они неявки.
Ответ: онлайн-запись уже шлёт напоминание за 2 часа, а неявки после её запуска не изменились, около 9%.
Совет: не делать в таком виде: само напоминание неявки не снижает.
Дальше Discovery: первым решим, идём ли дальше или ищем другую причину неявок.
```

## Финал: фактов не хватило

```text
Исследование по новому Handoff: <ссылка>.
Главный вопрос без ответа: насколько хуже выполняются задачи без Tech Spec. Измеренного сравнения нет ни у нас, ни у других.
Совет: сначала проверить: провести через новый Handoff один живой проект и посчитать остановки и переделки. Больше, чем у последних пакетов, значит нужен порог для Tech Evaluation.
Дальше Discovery: решим, делать ли такую проверку первым шагом.
```

## Не требуется

```text
Исследование не требуется: правка текста одной кнопки, вернуть можно одной правкой.
Записал это в документе: <ссылка>. Дальше Discovery.
```

## Техника

Последней строкой финала, только если владельцу стоит знать:

```text
Техника (можно не читать): разведчик по коду не ответил, факты собрал сам.
```

## Дальше

Сессия владельца, после финала отдельным ходом окно перехода. Над ним 1-2 строки,
что сделает следующий этап, без совета и пересказа итога:

```text
Discovery решит вместе с тобой, как Handoff режет без Tech Spec и когда спрашивает тебя.
```

- Claude Code: `AskUserQuestion`, заголовок «Дальше», вопрос «Начинаем Discovery?»,
  кнопки «Начать Discovery» и «Ещё обсудить», без пометки (Recommended).
- Codex: то же окно через `request_user_input_async`. Окна нет: последней строкой
  «Дальше Discovery: скажи «начинаем Discovery» или что обсудить.»
- «Ещё обсудить»: отвечай по документу; новый поиск только по просьбе; вывод
  поменялся: поправь документ и скажи, что поменял. Затем снова окно.
- Оркестратор: окна нет, следующий этап он начинает сам.

## Бриф (в `<папка>/brief.md`, при записи в журнал; не владельцу)

```text
Решение: каким будет новый Handoff.
Вопросы: 1) как резать на задачи; 2) когда спрашивать владельца и что теряем без утверждения пакета (его сомнение); 3) когда нужен Tech Evaluation; 4) как быть со старым путём.
Уже знаем: решения владельца 19.10.2026 в разговоре на Idea: режет Handoff, без Tech Spec, утверждение пакета только при конфликтах.
Допущения: без Tech Spec задачи исполнимы (самое рискованное, опоры нет: проверяю как вопрос).
Глубина: большая, плюс круг по пробелам: меняется этап, через который идёт каждый проект.
Где искать: Linear и код по всем; практики по 1-3. Стоп: опоры совета сверены, противоречие с правилом Tech Spec показано.
```

## Если нет доступа к Linear

```text
Этап не начат: в этой сессии нет записи в Linear, а без неё результат исследования негде сохранить. Ничего не создано.
Чтобы продолжить: открой сессию, где подключён Linear, и скажи «исследуй <проект>».
```

## Идея не утверждена

```text
Исследование не начал: описание проекта «Напоминания» ещё не утверждено.
Сначала этап Idea: скажи «идея: <проект>», и начнём с описания.
```
