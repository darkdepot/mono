# Утверждение, запись, повторный вход

Запись — комментарий проекта, а не документ и не вложение задачи.

## Вход для исправления записи

`route` вернул `bad-record` с `stage=mono:design`: войди только для замены своей
негодной записи. Сохрани исходный отказ; полный `mono:check discovery` остаётся
FAIL, его PASS для этого входа не требуется. Отдельно проверь входы Discovery:
утверждённые идею и выбранное Research, последнюю запись PRD, свежий документ
с совпадающими id/updatedAt и годные поля маршрута PRD. Повреждение, устаревание
или неизвестный писатель выше по цепи — стоп к владельцу; нехватка данных тоже
стоп. Вход исправления не добавляет Design в маршрут.

Негодная запись не доказывает прежнее утверждение макета. Восстанови точную
утверждённую версию по независимому подтверждению, включая макет в его инструменте и PNG, либо
пройди обычную проверку картинок и новое утверждение по режиму. Старый комментарий
и PNG не переписывай, поля и хеш под несогласованные картинки не подгоняй.
После старта работы — Handoff/ремонт пакета или принятый дрейф Ship, а не тихая
замена входов.

Запиши новый результат по порядку ниже; на свежих сырых ответах повтори `route`,
`design` и полную проверку Discovery. Только их успешный результат завершает
исправление. До него нет выхода из этапа, Handoff, Ready или старта работы;
отказ другого писателя передай ему, не пропуская этап цепи.

## Правка PRD в том же касании

Макет нашёл расхождение: рядом «Было / Стало» ровно затронутого PRD.
Согласие с показанным макетом и правкой утверждает их вместе. Design сам PRD
не меняет. После согласия вызови Discovery в том же касании: он меняет PRD,
читает обратно и пишет `mono-prd: approved` с `design=needed next=design`, затем
ты `mono-design` с новым `prd-updatedAt`. Контракт PRD и его отпечаток не меняются.
Записалась только первая: повтори вторую по тому же утверждению, не проси ещё
одно согласие и не делай дубликат первой. Посторонняя правка после показа требует
нового утверждения.

## Снимок и запись

До итога закончи служебное, проверки и показ макета картинкой. По `drawing.md`
сверь соседние экраны и состояния главного файла; в итоге назови расхождения
или «не сверено» с причиной. Для ещё не выпущенного раздела —
«раздел ещё не выпущен, сверять не с чем»; сверка только с выпущенными соседями,
если они есть. Утверждение не обновляет главный файл: эта версия
остаётся в песочнице до выпуска, обновление принадлежит Live QA Deploy. По
`<корень>/references/owner-dialog.md` итог до 120 слов со ссылкой, позиция и один
вопрос под ситуацию последним сообщением хода. Картинка текст не заменяет.
После согласия сверяй PRD и макет; посторонняя смена — новый показ без записи.
Поправка картинки всегда новый показ. Вне заборов записи дословный ответ
владельца и названная поправка, если была.

Запись или проверка не удалась: один повтор; сохранившуюся часть той же версии
переиспользуй без дубля. Снова отказ: скажи, что не сделано, возврата об успехе нет.

1. Артборды оставь на странице задачи выбранного инструмента без страницы
   «Утверждено»; отметку утверждения и порядок выполни по его справке.
   Утверждённые узлы неизменяемы. Получи проверенные PNG по справке инструмента,
   по порядку показа: `NN-<название>.png`, только латиница, цифры и дефисы.
   У секций имя называет экран и секцию. Новая версия сверху внутри той же
   страницы с подписью, PNG в новой папке. Без проверенных файлов записи нет;
   ручную выгрузку у владельца не проси.
2. Выгрузи в новую временную папку, посчитай `images` из неё:
   `LC_ALL=C ls *.png | LC_ALL=C sort | xargs shasum -a 256 | shasum -a 256`.
   Только имена файлов в UTF-8, запуск внутри папки. Перенеси целиком в
   `~/.mono-agent-workflow/design/<slug>/approved/<uuid проекта>/<первые 12 знаков images>/`.
   Прошлые версии не перезаписывай; существующая папка допустима только с точно
   теми же файлами и пересчитанным хешем. Считай хеш ещё раз из конечной папки.
3. Перечитай PRD и последнюю запись его утверждения: id и `updatedAt` совпадают.
   Новый PRD без согласованной правки — новый круг, не подмена поля под старый показ.
4. Комментарий проекта, первая строка в заборе `text`, только ключи без пробелов
   внутри значений; ниже список PNG, ссылка на согласие и причина повторного входа:

```text
mono-design: approved project=<uuid> prd=<uuid PRD> prd-updatedAt=<ISO> canvas=<https-ссылка> tool=paper|wonder images=<sha256> next=tech-evaluation|handoff by=owner|orchestrator
```

`next=` по «Размер» утверждённого PRD: «обычное» и «проект» → `tech-evaluation`,
«мелочь» → `handoff`. Глубина работы дизайнера это поле не меняет. Действует
последняя запись по `createdAt`; повреждённую новую нельзя заменить старой.
Отдельной записи «дизайн не требуется» нет.

`canvas` — ссылка на страницу задачи в инструменте, где утверждён макет;
для Wonder пиши `tool=wonder`, для Paper — `tool=paper`. Старый вид с
`paper=<https-ссылка>` без `canvas`/`tool` читается как `canvas` с `tool=paper`.
Смесь двух видов, неполная пара `canvas`/`tool` и неизвестный `tool` дают
`bad-record`. Новую запись всегда пиши с `canvas` и `tool`.

5. Прочитай комментарий обратно байт в байт; обнови бриф по разделу
   «Бриф после утверждения». Сохрани все свежие ответы Linear
   без переделки: `project.json`, `comments-N.json`, `comments-N.request.json`,
   `prd.json`. Запусти `node <корень>/scripts/idea-gate.mjs design --mode fresh --dump <папка>/linear --config <конфиг>`.
   Только exit 0, «Готово», JSON `pass`, затем `mono:check design` PASS завершают
   запись. `no-record`, `stale-prd`, `stale-images`, `bad-record` — стоп с причиной;
   чтение вместо команды не годится. Годность: PRD соответствует последнему
   утверждению, папка версии есть, `images` пересчитан и совпал.

## Бриф после утверждения

Если запись Idea содержит «Бриф:», по общей справке брифа после обратного чтения
записи согласия внеси утверждённое решение и повороты: суть на месте, история
со ссылкой на эту запись, устаревшее в «Отброшено». Без согласия суть не меняй,
предложение оставь в «Открыто». Новые мысли владельца из своего разговора
перескажи в «Как это видит владелец» со ссылкой на запись; ответы оркестратора
туда не идут. Прочитай бриф обратно до завершения этапа. Без строки «Бриф:»
этот шаг пропусти. Расхождение назови строкой в итоге или вопросе, без отдельной
остановки; в делегированном проекте отвечает оркестратор.

## Повторный вход

До старта: дизайнер сверяет новый PRD, предыдущие картинки и замечания
выбранного инструмента. Маршрут и инструмент те же, экраны не меняются: сам
зафиксируй причину, новая запись с новым `prd-updatedAt` и теми же `canvas` и
`images`, без показа. Смена инструмента после утверждения всегда новый круг
по `drawing.md`. Старое `paper` сравнивай как `canvas` с `tool=paper`. В журнале прежнее
утверждение и вызвавший этап. Не меняй прежние PNG. Экраны меняются: новый круг
с показом и утверждением; сними отметку утверждения по справке инструмента, старые узлы
и PNG сохрани. Сменился маршрут PRD: записи этапов ниже не действуют,
этапы проходят заново с показом по режиму, исключение неизменённых экранов не
применяй. После старта — ремонт пакета, не тихое обновление записи.

Tech Evaluation вернул технически неподходящий макет или «предлагаю убрать:
…, потому что …» о пункте на утверждённых экранах: новый круг, правка PRD через
Discovery в том же касании, затем новая запись и возврат к техлиду. Пункт не на
экранах отложен на утверждённой странице техлида: Discovery меняет только его;
при неизменных экранах новая запись с теми же картинками и новым `prd-updatedAt`
без показа, затем Tech Spec и `mono-tech` с id этой записи в `design=`.

## Финал

После успешной команды и `mono:check design` закончи журнал, закрой
`Design: <проект>`, прочитай Done обратно. Одна строка закрытия: «Утверждение
записал, дизайн закончил». В этой сессии нет вопроса о старте следующего этапа; Tech
Evaluation и Handoff здесь не начинаются.

В проекте владельца Claude Code запиши отметку круга из задания:
`.claude/session-views/design-<ключ проекта>-round-<n>.done` в каталоге продукта.
До записи проверь `git check-ignore`; если путь не игнорируется, допиши
`.claude/session-views/` в локальный файл исключений (`git rev-parse --git-path info/exclude`,
то есть `.git/info/exclude` продукта). `.gitignore` не меняй. В отметке
«Дизайн закончил», итог по общему шаблону до 120 слов и ссылка на запись/макет:
что утверждено, проверенные состояния, непроверенное, согласованные правила,
«Не берём» с причиной и «Дальше» по `next=`. Не сообщай успех до записи
и проверок; не используй папку PNG или межсессионный `send_message` как сигнал.
Отказ записи отметки после одного повтора: скажи, что возврат не записан.

Codex: отметка не заменяет возврат владельца — финал «Дизайн закончил», итог
со ссылкой и просьба вернуться в родительскую сессию; она сверяет запись на
первом сообщении. Это согласованное отступление от автоматического возврата.
В делегированном проекте отметку не пиши: итог и подтверждённая запись
последним сообщением хода возвращаются оркестратору, который запускает следующий этап.
