# Запись «да» и проверка

Справка для раздела 7 скилла. Команды запускай из папки продукта:
`node <корень>/scripts/idea-gate.mjs …`, где `<корень>` это две папки вверх от папки
скилла, а `<конфиг>` это `.agents/mono-workflow.config.json` продукта. Рабочая папка:
`<папка>` = `$TMPDIR/mono-idea/<короткое имя идеи>/`; в продукт ничего не кладёшь.
Это единственное место, где описаны шаги записи.

## Чеклист

```text
- [ ] сохранить одобренную версию в <папка>/approved.md
- [ ] сохранить факты со ссылками и старый текст в <папка>/notes.md до замены тела
- [ ] record: тело проекта
- [ ] Linear: создать проект в Idea или обновить тело без смены статуса
- [ ] record --project: комментарий
- [ ] Linear: опубликовать комментарий без правок
- [ ] Linear: прочитать проект и все страницы комментариев, сохранить ответы как есть
- [ ] verify: ответ «Готово»
- [ ] Linear: только из Idea статус Discovery, прочитать обратно
- [ ] вызвать mono:check idea
```

## Проект вернулся со следующего этапа

Неизвестные сформулируй из описания и фактов разведчиков; покажи владельцу все
четыре раздела до «да». Сравни одобренные «Что», «Зачем», «Образ результата»
с текущим телом (неизвестные могут быть новыми):

- Три раздела есть и не изменились: тело, пакет и статус не меняй. Сохрани факты
  разведчиков в `notes.md`: однострочный факт + ссылка, как в обычном пути. Четыре
  одобренных раздела сохрани в `approved.md`, сразу шаг 2 (`record --project`), публикация, шаг 3
  (`verify`), после «Готово» вызови `mono:check idea`.
- Владелец изменил эти разделы, одобренного пакета нет: после «да» начни с шага 1.
  Старый текст сохрани в `notes.md` до замены, тело запиши из одобренной версии;
  после «Готово» статус меняется только из Idea.
- Владелец изменил эти разделы, пакет уже одобрен: остановись до записи и передай
  исправленное описание в `mono:handoff`. Тело проекта с пакетом меняет владелец
  artifact repair. После этой правки вернись к записи и проверке Idea.

Трёх разделов нет: обычный этап с владельцем, а не возврат. После «да» шаг 1:
старый текст в `notes.md`, тело из одобренной версии; пакет не меняй,
после «Готово» статус меняется только из Idea.

## 1. Подготовить тело

`<папка>/approved.md`: четыре раздела одобренной версии ровно как их видел владелец,
без строк «что меняется» и «Решил сам:» над ними. Заголовки второго уровня на языке
Linear продукта (`languages.linear` или `ideaGate.headings`); по-русски
`## Что`, `## Зачем`, `## Образ результата`, `## Неизвестные`.
Другие разделы `##` и текст вне этих четырёх не добавляй: `record` откажет с
`unsupported-format` до создания файлов. Ссылки и старые границы идут в `notes.md`.

```bash
node <корень>/scripts/idea-gate.mjs record --draft <папка>/approved.md --config <конфиг> --out <папка>
```

Появится `<папка>/body.md`: три раздела без неизвестных. Это тело проекта.
При создании проекта назначь владельцем действующего пользователя (`lead: "me"`).
При обновлении существующего проекта его владельца не меняй.

## 2. Подготовить комментарий

После того как проект создан или обновлён, возьми его UUID из поля `uuid`, а не
человекочитаемый `id`. В командах `<id>` означает этот UUID:

```bash
node <корень>/scripts/idea-gate.mjs record --project <id> --draft <папка>/approved.md \
  --notes <папка>/notes.md --config <конфиг> --out <папка>
```

`<папка>/notes.md` пишет агент этапа. Каждая строка заметок: однострочный факт и ссылка
на источник, а не голая ссылка: «Клиенты получают напоминание за 2 часа — <ссылка>».
Так Research читает, что уже известно. Старые «Что входит / Что не входит», а при
отсутствии трёх разделов весь старый текст, сохрани отдельно в этих заметках до
замены тела, со ссылкой на исходный проект. Скрипт кладёт заметки в комментарий
отдельным блоком для Research и Handoff; в проверку «да» они не входят.

Появится `<папка>/comment.md`: строка `mono-idea: approved project=<uuid> sha256=<64 hex>`,
точная копия одобренной версии и блок заметок. Опубликуй его на проекте целиком.
Ничего в этих файлах руками не правь.

## 3. Проверить

Прочитай проект и все страницы его комментариев. Каждый ответ Linear сохрани
в `<папка>/linear/` как есть: `project.json`, `comments-1.json`, `comments-2.json`…
Рядом с каждой страницей сохрани фактически переданный cursor в
`comments-N.request.json`: `{}` для первой, `{"cursor":"…"}` для следующих.
Продолжай cursor предыдущего ответа; последняя страница имеет `hasNextPage: false`
и не содержит cursor. Переименование файлов не заменяет чтение всех страниц.

```bash
node <корень>/scripts/idea-gate.mjs verify --project <id> --dump <папка>/linear \
  --expect <папка>/comment.md --config <конфиг>
```

Скрипт сам берёт нужные поля, проверяет, что прочитаны все страницы, находит именно
комментарий из `--expect` и прогоняет ту же проверку, что оркестратор перед запуском
работы: запись относится к этому проекту, а тело проекта совпадает с одобренной
версией. Ответ одной строкой:

| Ответ | Что делать |
|---|---|
| «Готово» | Проект в Idea: переводи в Discovery. Проект вернулся со следующего этапа: статус не меняй. |
| «Нужно новое «да»: …» | Текст изменился после одобрения. Покажи владельцу новую версию. |
| «Стоп: …» | В строке причина и что сделать. Устрани и запусти `verify` снова. |

Машинный код ответа печатается в техническом хвосте. В чат владельцу его не выноси.

## Если что-то прервалось

- Проект создан, комментария нет: найди id проекта, повтори шаг 2 с тем же
  `approved.md` и опубликуй. Новое «да» не нужно.
- `approved.md` пропал (новая сессия): возьми одобренную версию дословно из сообщения,
  на которое владелец сказал «да». Нет такого сообщения: покажи версию заново на «да».
- Комментарий есть, `verify` не запускался: сразу к шагу 3.
- `verify` сказал «Готово», статус не сменился: для проекта в Idea смени статус и прочитай обратно; вернувшийся проект статус не меняет.
- Запись в Linear «прошла», но при чтении её нет: повтори запись. Linear иногда
  молча не сохраняет.
- «Стоп: в пакете не задана дата начала проверки»: это ошибка установки, а не этапа.
  Сообщи и остановись. Дату не придумывай.
