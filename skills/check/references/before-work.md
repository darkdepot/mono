# Режимы до работы

`idea`, `discovery`, `design`, `tech`, `handoff`, `repair`. Согласие владельца —
ясные слова на показанную версию или историческое нажатие кнопки.

## Цепь записей

Для `discovery`, `tech`, `handoff` и `delivery` по проекту всегда сначала, даже без
утверждения PRD: свежие сырые `project.json` и все комментарии, затем
`node <корень>/scripts/idea-gate.mjs route --mode fresh --dump <папка> --config <путь>`.
Только после `pass` решай, какие этапы пропускать, и применяй послабления старого
пути (одобренный пакет без PRD, PRD без `design=` или `next=`). Команда проверяет
поля и словари, не свежесть и не завершённость этапа. `bad-record` — жёсткий стоп у
писателя из поля `stage`, никогда не `no-record`. Исправлять запись входит только
этот писатель: Design по `<корень>/skills/design/references/approval.md`, Tech
Evaluation по `<корень>/skills/tech-evaluation/references/spec.md`, раздел «Вход
для исправления записи». Повреждённая нижняя запись не портит текущий PRD, а
полная проверка цепи остаётся FAIL: вход исправления не превращается в PASS.

Бриф для `discovery`, `design`, `tech`, `handoff`: есть строка `Бриф:` в записи
утверждения идеи — прочитай документ по этой ссылке и требуй в конце блок
`mono-brief` с UUID этого проекта. Нет документа, не читается, нет или чужой блок:
FAIL → `mono:idea`, без замены. Нет строки — бриф не требуется. Свежесть брифа не
проверяется.

## idea

Прими результат `verify`, который выдал `mono:idea` по
`<корень>/skills/idea/references/record.md`; снимок руками не собирай. Нужны exit 0,
«Готово» и JSON `pass` по ожидаемым проекту и комментарию. Ещё для PASS: согласие
владельца на показанную версию из четырёх разделов (точный ответ, только названная
поправка), ссылка или id проекта, статус подтверждён чтением, нет раньше времени
документа «Исследование», PRD, Tech Spec, задач или плана реализации (PRD, Tech
Spec или задача, созданные во время Idea без явного контекста ремонта: FAIL). Второй показ
итога не нужен. Новый проект после «Готово» остаётся в Idea; проект дальше по
этапам в Discovery не возвращается. Нет записи или пропущено согласие: FAIL →
`mono:idea`. Нет вывода или чтение не удалось: стоп с проектом и кодом.
Работа на один PR без проекта, верно отправленная в `mono:issue`, тоже PASS: её
утверждённый отпечаток заменяет запись проекта, проект не требуется.

## discovery

Идея: `node <корень>/scripts/idea-gate.mjs check --mode fresh --dump <папка> --config <путь>`
допускает `pass`, `stale`, `legacy-migrate`. Ведёт владелец: stale или legacy едет
показанной идеей в Handoff и старт (найденные Research неизвестные сохраняются).
Делегированный stale или legacy останавливает самостоятельные Research и работу до
согласия владельца на идею, подтверждённой записи и свежей проверки; оркестратор
снимок не переутверждает. `no-record` на новом проекте → `mono:idea`. Discovery не
создавал Tech Spec и задач реализации (уже существующие поздние артефакты не FAIL).
Код по этому результату не стартует. После Research старый путь идёт в
`mono:handoff`, если владелец явно не просит Discovery; остальное в `mono:discovery`.

Исследование проверяй независимо от старого пути и от старта; после старта
снимается только требование «да» на PRD. Документ ищи по блоку `mono-research`
проекта, не по названию. Кандидатов несколько: бери связанный строкой
`Исследование: <ссылка>` в комментарии решений, а для закрытия или отсрочки до
выбора решения ссылку из журнала задачи этапа. Нет ссылки выбора: FAIL, попроси
назвать действующий документ, удалять другие не требуй. В выбранном ровно один
разбираемый блок `mono-research` с UUID этого проекта, `outcome` из
`ready|hold|not-required` и непустой `reason` для `hold` и `not-required`; иначе
FAIL → `mono:research`. Без документа можно, только если у последнего старта или
утверждения пакета (того, по которому был запуск) `approval.createdAt` строго
раньше `researchGate.since` из конфига, иначе `RESEARCH_GATE_DEFAULT_SINCE` из
`<корень>/scripts/idea-gate.mjs`. Иначе FAIL → `mono:research`.

Старый путь: ни одной записи `mono-prd: approved` и одобренный старый пакет —
комментарий утверждения прежнего Handoff, который принимает запуск (ровно один
`approval_status=approved` или без метки и строго раньше `ideaGate.since`), и нет
`mono-package: recorded` на проекте. Решают записи, не даты; `discoveryGate.since`
больше не действует. Проект без одобренного пакета на старом пути не бывает. Старый
путь снимает только «да» на PRD, задачу Discovery и комментарий решений; Research
остаётся. Любая запись «да» исключает старый путь.

Новый путь до старта владельца: PRD — `document` из последней записи
`mono-prd: approved`; её `project` и `document` совпадают с проверяемыми, `updatedAt`
равен свежему чтению документа. Нет записи или устарела: FAIL → `mono:discovery`.
Записи нет, а PRD-кандидатов несколько: попроси назвать документ, удалять другие не
требуй. Комментарий решений в задаче Discovery, задача Done. Закрытие или отсрочка:
закрытая задача с решением, причиной и условием возврата; PRD и «да» не нужны.

После старта владельца (у старого пакета — утверждения пакета) «да» на PRD не
перепроверяй. Нет контекста: BLOCKED. Любое невыполненное условие: назови
незавершённое и его владельца.

## design

После цепи записей добавь в сырой набор `prd.json` и запусти
`node <корень>/scripts/idea-gate.mjs design --mode fresh --dump <папка> --config <путь>`.
PASS только по `pass`. `no-record`, `stale-prd`, `stale-images` → Design; `bad-record`
→ его писатель.

## tech

Обычный вход требует PASS `mono:check discovery`; вход исправления — по правилу
писателя выше. После цепи записей нужен предшественник: PRD с
`next=tech-evaluation` или годная запись Design с этим `next`; явно запрошенный
владельцем старый путь Tech Evaluation сохраняется. Каждую нужную запись `design`
сначала проверь её командой. До команды в папке выгрузки должны быть сырой `prd.json`
и сырой `tech-spec.json` — ответ `get_document` документа из поля `spec` действующей
записи `mono-tech`, а также все комментарии. Файл не выгружен или JSON не читается —
дособери выгрузку и запусти снова: такой `bad-record` не отправляет к Tech Evaluation.
Для настоящей сломанной записи остаётся стоп у писателя из `stage`. Затем запусти
`node <корень>/scripts/idea-gate.mjs tech --mode fresh --dump <папка> --config <путь>`;
PASS только по `pass`. Нет или устарели PRD или Spec, `stale-design`: стоп у этапа-владельца.
Документа нет в Linear — это отсутствие PRD или Spec по этому правилу, а не недособранная выгрузка.

Старый путь Tech Evaluation: утверждение PRD без `next=`. Годную по текущему PRD
`mono-tech`, проходящую `tech`, прими без нового предложения. Размер читай через
соответствие в `skills/discovery/references/prd.md`, без переоценки старого PRD.
Иначе для среднего или большого проекта нужен текстовый вопрос о старте Tech Evaluation; согласие владельца
или делегированного оркестратора и есть запрос, без него нет ни пакета, ни
продолжения. Небольшой может пропустить. `next=handoff` пропускает техоценку.

## handoff

Вход: один раз `mono:check discovery` (Handoff переиспользует свой результат входа в
том же прогоне); FAIL возвращает к названному владельцу: PRD → `mono:discovery`,
Research → `mono:research`. После цепи записей проверь по порядку каждую запись из
`requiredRecords` командами `design` и `tech`. Нет или устарел нужный Design → Design,
нужный Tech Evaluation → туда; один не пропускается из-за другого. Пустой список —
старый путь или небольшой проект, но не обход цепи записей. Для PRD без `next=` проверь любую
действующую `mono-tech` независимо от `design=` и `requiredRecords`: годная
принимается, нет или негодная — правило старого пути из `tech`. Повтори перед первой
записью старта. После старта свежесть ведут ремонт и принятый дрейф до PR, но цепь
записей по-прежнему идёт первой.

PASS: текущая запись пакета (`mono-package: recorded`, прочитана байт в байт, `sha256`
совпадает с SHA-256 строк между ограждениями блока `mono-package` после снятия `\r`
в конце строк, каждая строка с завершающим LF, включая последнюю, как в
`scripts/skills-records.mjs`) называет текущее утверждение PRD и Research; в ней нет
`approval_status`, `mono-idea:` и `mono-idea-snapshot`; у deep и risky хотя бы одно
общее решение `U`; задачи реализации совпадают со списком в записи, их не больше
трёх без разрешения владельца (в «веди до Handoff»/«веди сам» — оркестратора с причиной, без отдельной встречной проверки), у каждой ID PRD и «Готово, когда»;
`mono:review handoff` и второй голос прошли до первой записи, каждая находка
исправлена или отклонена по `skills/handoff/references/review.md`, блокирующих нет.
Решения Spec в U; одна задача — номера без пересказа.
Одна задача любого риска: оба, один круг, формулировки без нового круга, P0/P1
по сути перепроверены автором точечно или опровергнуты источником. Только при
нескольких задачах tiny допускает записанную причину advisory; ничего не начато. Старт владельца и уже стоящий Ready не требуются; нет
Ready — сообщи: остаётся Discovery. Старый пакет: Tech Spec или исключение
без Spec (PC-016) и записанное утверждение пакета.

## repair

PASS только когда точный diff по стабильным ID и доказательства подтверждают
записанный класс, у `mono:review artifact` нет блокирующей находки и каждое
последствие из `<корень>/references/repair-machine.md` записано. Класс 1 сохраняет
утверждение и задачи. Класс 2 доказывает синхронизацию снимков с пересчитанным
отпечатком, судьбу устаревших сертификатов preflight и остановку устаревших
исполнителей. Класс 3 доказывает остановку исполнителей, замену старта или
утверждения, снятие зависимых записей и откат: у старого пакета Delivery или Ready
назад в Discovery и ожидающее или полученное новое утверждение владельца в старом
формате; у записи пакета Ready сохранён или возвращён и ожидается или получен новый
разрешённый старт. Неясность или рост риска под записанным более низким классом: FAIL.
Ремонт check не применяет и не завершает.
