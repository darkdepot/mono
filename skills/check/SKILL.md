# Mono Check

Отчётная проверка перехода, по мере сил, не доказательство. Смотрит свежее
состояние Linear и говорит, можно ли идти дальше. Ничего не правит: проект,
документы и задачи не меняет, расхождение молча не чинит, скиллы процесса не
ставит и не удаляет. Попросили синхронизировать или исправить: назови этап-владельца.
Находки, предложения и решения пишет `mono:review`; check сообщает только готовность.

Прочитай сразу:
1. `<корень>/references/readiness-gates.md`
2. `<корень>/templates/check-output.md`

Прочитай, когда:
- `references/before-work.md` — режимы `idea`, `discovery`, `design`, `tech`, `handoff`, `repair`.
- `references/delivery.md` — режимы `delivery`, `issue`, `pre-ship`, `project-config`; для `delivery` по проекту ещё `references/before-work.md`.
- `<корень>/references/execution-quality.md` — проверяемое включает diff, реализацию или доказательства проверки.
- `<корень>/references/human-friendly-output.md` — вердикт видит человек или он уходит текстом в Linear.
- `<корень>/references/artifact-rules.md` — проверяемое включает тело артефакта Linear или комментарий для Linear.
- `<корень>/references/repair-machine.md` — проверка питает или пропускает ремонт пакета.

Статусы:

- `PASS`: нужное состояние осмотрено, блокирующего расхождения нет.
- `FAIL`: нарушен жёсткий договор процесса или пропущен обязательный артефакт.
- `BLOCKED`: проверить нельзя, нет контекста или прав.

Режимы:

- `idea`
- `discovery`
- `tech`
- `delivery`
- `issue`
- `handoff`
- `design`
- `pre-ship`
- `project-config`
- `repair`

## Общие правила

- Перед вердиктом прочитай свежие проект, PRD, Tech Spec, запись пакета и задачи.
  Linear — источник правды; GitHub — только ветка, PR, ревью, CI и история вливаний.
- Команды: `<корень>` — `../..` от папки этого скилла, найди его до запуска из
  репозитория продукта; справки `references/before-work.md` и `references/delivery.md`
  из «Прочитай, когда» лежат в папке скилла. Сырые ответы Linear сохраняй как есть: `project.json`, все
  `comments-N.json` и `comments-N.request.json` (`{}` первым, затем
  `{"cursor":"<cursor прошлого ответа>"}`) и нужные документы. Для `verify`, `route`,
  `design` и `tech` PASS только при exit 0, «Готово» и JSON `pass`; у `check` свои
  допустимые исходы в правилах режима. Чтение вместо команды не проверка.
- Форму документа суди по смыслу, не по написанию заголовка. FAIL, когда у документа
  чужая ответственность: PRD придумывает КАК, Tech Spec придумывает ЧТО, задача
  копирует PRD или Spec целиком, проект превращён в панель процесса.
  Проект — короткое описание, связи и статус в метаданных Linear. PRD — ЧТО: кто,
  проблема, нужный сценарий, требования (у standard и deep стабильные ID `R`), что не
  делаем, приёмка, успех, а при условном поведении примеры приёмки. Tech Spec — КАК: решения со ссылками на требования PRD,
  договоры, границы, проверка, применимые сбои, выпуск и откат без пустых разделов.
  Задача — договор на один PR с конкретной проверкой и приёмкой.
- Задачи реализации (нарезка, состав пакета) не включают задачи с меткой `Этап`.
- Ворота ревью: для standard, deep и risky FAIL, если нужного `mono:review` нет, он не
  закрыт или заменён незаписанным исключением. tiny пропускает ревью только с
  записанной причиной advisory в поле ворот ревью проекта или задачи. Нарезка
  одной задачи: оба проверяющих, один круг при любом риске; диспозиция по
  `skills/handoff/references/review.md`, совета вместо ревью нет.
- Апдейты проектов не ворота; приёмку ревью ищи в комментариях Linear.
- FAIL, если долговечное тело проекта, PRD, Tech Spec или задачи несёт механику
  процесса: `mono:check`, договоры скиллов, ворота, указания агенту.

## Отчёт

По `<корень>/templates/check-output.md`, коротко. В строке статуса точный режим и
`PASS`, `FAIL` или `BLOCKED` как есть, сразу за ней строка смысла по-русски. FAIL
начинается с `FAIL - Linear <mode> not ready`; BLOCKED называет самый малый шаг,
который снимет блок. Граница «проверено / не проверено» обязательна: PASS не
подразумевает ручную проверку, браузер, прод, выкладку или приёмку владельца.
