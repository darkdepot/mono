# Tech Spec и запись результата

Черновик до проверки помощником и второй моделью; документ Linear только после
утверждения страницы. Один `Tech Spec: <проект>` на проекте. Есть: обнови;
нет: создай. Только короткие решения, которые нельзя угадать и дорого менять,
стабильные `U` с покрытием `R`/`AE`. На каждый открытый вопрос PRD к Tech Evaluation
явный ответ с решением и причиной. Пустых разделов нет, PRD не пересказывай.
Контракт и шаблон из условного чтения этапа обязательны перед черновиком.

Важны границы, влияние на соседние места и как доказать поведение. Для реального
API: наблюдаемые формы ответов, значения, крайние случаи, дата/версия; доступа
нет, не угадывай, проба первой. Отказы, выпуск и откат только по делу. Прикидка
для Handoff: примерно сколько PR, что первым, где риск; окончательно нарезает
он. «Проверить не на чем» требует первую пробу и ожидание её результата зависимыми.
В теле нет механики этапов, команд готовности или стенограммы.

## Порядок записи

1. Утверждение показанной страницы по режиму; перечитай PRD, смена версии по `run.md`.
2. Есть отложенный пункт: Discovery, обратное чтение PRD и новой записи утверждения.
3. Запиши Tech Spec, прочитай тело обратно. SHA-256 считай по этому точному телу,
   не локальному черновику; хеш страницы по точному показанному тексту.
4. Комментарий проекта: первая строка в заборе `text`, затем точная страница
   в заборе `mono-tech-page`. Формат из `<корень>/references/lifecycle.md`,
   «Tech approval record», не дополняй машинную строку своими полями:

```text
mono-tech: approved project=<uuid> prd=<uuid PRD> prd-updatedAt=<updatedAt утверждённого PRD> spec=<uuid Tech Spec> spec-sha256=<sha256 тела Tech Spec> page-sha256=<sha256 страницы> by=owner|orchestrator
```

5. Прочитай комментарий обратно, точный текст и поля сверь. Вне заборов строка
   «Владелец: нажал «Утвердить»» или «Оркестратор: <причина>»; при повторном входе
   без показа ссылка на прежнее утверждение и причина сохранения страницы.
6. Свежие ответы Linear как есть в `<папка>/linear/`: `project.json`, все
   `comments-N.json` и `comments-N.request.json` ({} первой, фактический
   предыдущий cursor дальше), `prd.json`, `tech-spec.json`. Без обрезки страниц.

```bash
node <корень>/scripts/idea-gate.mjs tech --mode fresh --dump <папка>/linear --config <конфиг>
```

Только exit 0, «Готово», JSON `pass`, затем `mono:check tech` PASS дают выход.
`no-record`, `stale-prd`, `stale-spec`, `stale-design`, `bad-record`: исправь причину по владельцу
артефакта, не переписывай хеш под устаревший вход. Недоступное чтение это стоп,
чтение вместо команды не проверка. Запиши результат в задаче этапа, закрой её,
финал отдельно и окно Handoff. Реализацию и статус Delivery здесь не начинай.

## Поле дизайна (спит до MONO-228)

Текущую строку `mono-tech` не меняй. После общего включения по `design.md`
добавляется `design=<id последней mono-design>|none`: без поля читается как
`none`, но при наличии дизайна нужен его id. Проверка даёт `stale-design` при
несовпадении; повторный вход техлида нужен и при смене записи дизайна. После
откладывания пункта вне экранов сначала новая запись дизайна с прежними PNG
и новым PRD, затем Tech Spec и `mono-tech` с новым id, без второй остановки.
