# Tech Spec и запись результата

Черновик до проверки помощником и второй моделью; документ Linear только после
утверждения страницы. Один `Tech Spec: <проект>` на проекте. Есть: обнови;
нет: создай. Только короткие решения, которые нельзя угадать и дорого менять,
стабильные `U` с покрытием `R`/`AE`. На каждый открытый вопрос PRD к Tech Evaluation
явный ответ с решением и причиной. Пустых разделов нет, PRD не пересказывай.
Контракт и шаблон из условного чтения этапа обязательны перед черновиком.

Важны границы, влияние на соседние места и как доказать поведение. Для реального
API: наблюдаемые формы ответов, значения, крайние случаи, дата/версия; доступа
нет, не угадывай, проба первой. Отказы, выпуск и откат только по делу. Прикидка
для Handoff: примерно сколько PR, что первым, где риск; окончательно нарезает
он. «Проверить не на чем» требует первую пробу и ожидание её результата зависимыми.
В теле нет механики этапов, команд готовности или стенограммы.

## Вход для исправления записи

`route` вернул `bad-record` с `stage=mono:tech-evaluation`: техлид может войти
только для замены своей негодной записи. Полный `mono:check discovery` пока
остаётся FAIL из-за этой записи; не требуй его PASS для такого входа и не
объявляй цепь годной. Сохрани исходный отказ и отдельно проверь все входы
Discovery по его условиям: утверждённые идея и выбранное Research, последняя
запись PRD и свежий документ с совпадающими id/updatedAt, годные поля маршрута
PRD. Исправление существующей записи не требует обычного входа в этап и не
добавляет этап в маршрут. Нужен дизайн: его запись тоже должна
быть годной.
Неизвестный писатель, повреждение или устаревание выше по цепи — стоп к его
владельцу; отсутствие данных не заменяй предположением о годности.

Такой вход разрешает только восстановление результата техлида. Повреждённая
запись и её страница не доказывают прежнее утверждение: восстанови точную
утверждённую версию по независимому подтверждению либо пройди проверку и новое
утверждение страницы по обычным правилам. Старый комментарий не переписывай,
хеш под отредактированную страницу без согласия не подгоняй. После старта работы действуют
Handoff/ремонт пакета и принятый дрейф Ship, а не самовольная замена входов.

Запиши новый результат по порядку ниже, затем на свежих сырых ответах повтори
`route`, `tech` и полную проверку Discovery. Пока они не прошли, запись не даёт
выхода из этапа, Handoff, Ready или старта работы. Отказ другого писателя
передай ему; вход исправления не пропускает ни один этап цепи.

## Порядок записи

1. Согласие на показанную страницу; молча перечитай PRD. Версия
   сменилась: «Было / Стало» и страница, позиция и вопрос заново, без записи, кроме случаев `run.md`.
2. Есть отложенный пункт: Discovery, обратное чтение PRD и новой записи утверждения.
3. Внеси только названную мелкую поправку в Tech Spec до записи утверждения.
   Запиши Tech Spec, прочитай тело обратно. SHA-256 считай по этому точному телу,
   не локальному черновику; хеш страницы по точной согласованной версии: показанное плюс только
   названная мелкая поправка.
4. Комментарий проекта: первая строка в заборе `text`, затем точная согласованная страница
   в заборе `mono-tech-page`. Формат из `<корень>/references/lifecycle.md`,
   «Tech approval record», не дополняй машинную строку своими полями:

```text
mono-tech: approved project=<uuid> prd=<uuid PRD> prd-updatedAt=<updatedAt утверждённого PRD> spec=<uuid Tech Spec> spec-sha256=<sha256 тела Tech Spec> page-sha256=<sha256 страницы> by=owner|orchestrator design=<id последней mono-design>|none
```

5. Прочитай комментарий обратно, точный текст и поля сверь. Вне заборов строка
   «Владелец: ответил «<его слова дословно>»» и, если была, «Поправка: <изменение>» или «Оркестратор: <причина>»; при повторном входе
   без показа ссылка на прежнее утверждение и причина сохранения страницы.
   Затем обнови бриф по разделу «Бриф после утверждения», включая отложенное
   с причиной и ссылкой на согласие со страницей.
6. Свежие ответы Linear как есть в `<папка>/linear/`: `project.json`, все
   `comments-N.json` и `comments-N.request.json` ({} первой, фактический
   предыдущий cursor дальше), `prd.json`, `tech-spec.json`. Без обрезки страниц.

```bash
node <корень>/scripts/idea-gate.mjs tech --mode fresh --dump <папка>/linear --config <конфиг>
```

Только exit 0, «Готово», JSON `pass` разрешают записать результат в задаче этапа,
закрыть её и прочитать Done обратно. Затем `mono:check tech` PASS даёт выход.
`no-record`, `stale-prd`, `stale-spec`, `stale-design`, `bad-record`: исправь причину по владельцу
артефакта, не переписывай хеш под устаревший вход. Недоступное чтение это стоп,
чтение вместо команды не проверка. После обеих проверок одна строка о записи
и выбранный переход, без повтора страницы.
«Продолжу позже» без старта; позднее «начинаем Handoff» после сверки версии без
нового утверждения. Записанную часть той же версии переиспользуй без дубля;
после одного повтора запись или проверка не удалась: назови, что не сделано,
Handoff не стартует. Реализацию и статус Delivery здесь не начинай.

## Бриф после утверждения

Дописывай только в пять разделов из `<корень>/references/brief.md` (решения этапа в «Решения и повороты»); дата строки ДД.ММ.ГГГГ, ссылка согласия это полный Linear URL записи с `#comment-<uuid>`, без голого id или URL проекта.

Если запись Idea содержит «Бриф:», по общей справке брифа после обратного чтения
записи согласия внеси утверждённое решение и повороты: суть на месте, история
со ссылкой на эту запись, устаревшее в «Отброшено». Без согласия суть не меняй,
предложение оставь в «Открыто». Новые мысли владельца из своего разговора
перескажи в «Как это видит владелец» со ссылкой на запись; ответы оркестратора
туда не идут. Прочитай бриф обратно до завершения этапа. Без строки «Бриф:»
этот шаг пропусти. Расхождение назови строкой в итоге или вопросе, без отдельной
остановки; в делегированном проекте отвечает оркестратор.

## Поле дизайна

В строку `mono-tech` по `design.md` добавляй `design=<id последней mono-design>|none`: без поля читается как
`none`, но при наличии дизайна нужен его id. Проверка даёт `stale-design` при
несовпадении; повторный вход техлида нужен и при смене записи дизайна. После
откладывания пункта вне экранов сначала новая запись дизайна с прежними PNG
и новым PRD, затем Tech Spec и `mono-tech` с новым id, без второй остановки.
