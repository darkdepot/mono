# Вход и подготовка

## Девять условий

До создания и повторного входа:
4. Риск `tiny` или `standard`; `deep` и `risky` требуют проекта.
5. Самостоятельное тело: цель, объём, желаемое поведение, стабильные AC,
   проверка, исключения, непустой поведенческий эталон.
6. Результат целиком принимается одним PR, нет зависимых частей.
7. Только задача несёт истину и состояние; нет Project, PRD, Tech Spec и ссылок на них.
8. Нет рискованной области, новых акторов, нескольких поверхностей, сквозного
   изменения, нерешённого выбора или критического сигнала.
После ответа владельца перед стартом:
1. Свежий корректный маркер ровно из пяти полей.
2. Проверенная точная метка `issue-only`.
3. Отпечаток живого тела, Approval маркера и подтверждённое одобрение совпадают.
9. Явные слова владельца; автор комментария сверяется со стабильным ID
   `issueOnlyLane.ownerPrincipal`, один автор без решения недостаточен.

Нет любого входного условия или ясности — причина, Idea для неоформленного
запроса, Handoff для проектного контекста; без создания задачи. Project relation
или ссылки на проект/PRD/Spec запрещают путь сразу, в том числе с названием по
`<корень>/references/linear-links.md`. Нарезка и несколько PR тоже.
Принятый дрейф перед PR ведёт Ship. Название скилла в просьбе не доказательство.
`Тематический проект:` в тексте «Связи» не relation и не chip; допустим завершённый
проект или `нет — <почему>`. Конфиг включается только явным решением продукта:
`issueOnlyLane.enabled: true` и непустой `ownerPrincipal`, не включай сам.

## Тело до старта

Договор IS-001…IS-034 применяется целиком, шаблон даёт форму. Состояние типа
`triage`, `backlog` или `unstarted`; сначала без метки и маркера. Прочитай записи
обратно. Ревью `standard` должно дать `ready`, `tiny` допускает записанное
консультативное исключение с причиной. Только затем короткий итог владельцу.
Не создавай Project/PRD/Tech Spec и ссылки на них внутри пути.

До показа владельцу проверь перечитанное живое тело установленным
`scripts/resolve-issue-context.mjs`: получи `Scope fingerprint` через
`--issue <живое-тело> --emit-fingerprint` по этому же телу, создай отдельный
временный файл чернового маркера `mono-issue-only marker` ровно из пяти полей:
`Marker version: 1`, `Scope fingerprint: <полученный отпечаток>`,
`Acceptance IDs: <AC тела>`, `Risk class: <класс задачи>`, `Approval: none`.
Вызови резолвер с `--issue <живое-тело> --marker <черновой-файл> --config <конфиг>`;
успех — выход 0 и `package_kind: project-first`: метки и согласия ещё нет.
Любой `broken marker` или `stale marker` требует правки тела и повторной проверки
до показа. «Ревью-гейт» называет ровно один класс; отрицания, историю и сравнения
с другими классами перенеси в другие разделы. Черновой маркер не пиши ни в тело,
ни в Linear.

UI: в «Прочитать сначала» «Дизайн: нет»; выдуманной записи Design нет. Прочитай
существующие правила вкуса владельца и продукта, применимые целиком перенеси
в снимок (причина, верно/неверно, источник, вес), включая случай без макета.
Нет правил — назови отсутствие, нет доступа к существующим — подготовка стоит.
Исполнитель может не видеть домашнюю папку.

Правка одобренного тела только через новое согласие по `references/decisions.md`.
Изменение манифеста `# Предприменение` после остановки исполнителя требует нового
согласия и NEW dispatch с `--preapply`, не resume. До кода выход из
пути: останови исходную задачу, отзови разрешение, затем новый проектный пакет,
без прикрепления исходной задачи к Project. Только после сертификата
`mono:preflight` со значением `ready` заморозь независимую
часть: неизменной до выпуска или отмена; расширение в отдельном проекте.
