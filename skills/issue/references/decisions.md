# Ответ владельца и восстановление

## Запись и доверие

Договор задачи, шаблон и общая справка пути читаются по условиям SKILL.md.
Здесь порядок ответа; формат машинной записи не меняется.
Дату решения для владельца бери в его часовом поясе, а если он не задан —
в часовом поясе хоста; дата UTC не подменяет локальную. Порядок решений
сверяй по полным временным меткам записи Linear, не по этой дате. Решения упорядочены
по времени записи в Linear, действует последнее. Читай всё нужное для порядка,
не только последнее одобрение. Выбирай последний комментарий с маркером, не
самый новый произвольный комментарий. Отпечаток только командами:

```bash
node '<pack-root>/scripts/resolve-issue-context.mjs' --issue <issue-body> --emit-fingerprint
node '<pack-root>/scripts/resolve-issue-context.mjs' --issue <live-issue-body> --emit-fingerprint
```

Одобрение — отдельный комментарий с точным отпечатком и дословными строками:

```text
Владелец: ответил «<его слова дословно>»
Старт: сейчас
```

Для отложенного вместо последней строки `Старт: по слову «запускай»`.
Слова должны отвечать на показанный итог и вопрос о согласии/старте, а не на
уточнение. Автор комментария — стабильный ID из `issueOnlyLane.ownerPrincipal`;
комментарий коннектором без предшествующих слов владельца не одобрение.
Оркестратор хранит показанный итог, вопрос и дословный ответ и передаёт этапу.
Утверждать за владельца запрещено. Запись проверяется обратным чтением.

Маркер ровно из пяти полей: `Marker version: 1`, `Scope fingerprint`,
`Acceptance IDs`, `Risk class`, `Approval`. Заголовок `mono-issue-only marker`;
перед блоком короткая человеческая строка, внутри ни слова сверх пяти полей.
Шестое поле (включая `route_revision`, `assurance_vector`, `required_artifacts`)
ломает маркер. Обновляй его отдельным комментарием, тело этим не меняй.

Команда проверки контекста принимает живое тело и последний маркер:

```bash
node '<pack-root>/scripts/resolve-issue-context.mjs' --issue <live-issue-body> --marker <marker-comment> --config <project-config> --label issue-only --approval-verified <fingerprint>
```

`--label` только после чтения метки; `--approval-verified` только после проверки
автора и последнего решения. Резолвер не проверяет ни автора, ни время решений.
Нет метки или свежего разрешения — не передавай соответствующий аргумент.
Маркер с `Approval: <отпечаток живого тела>`, метка и одобрение того же отпечатка
вместе разрешают старт; отдельный успех записи этого не доказывает.

## Разрешающая последовательность

Для «да», «запускай», нового согласия после правки и восстановления прерванного
согласия выполняй все шаги по порядку. Метки шагов машинные; каждый шаг отдельный,
пропуск запрещён. Подтверждённую запись не дублируй, чтение выполняй заново.

1. `issue-start:label` — поставь метку `issue-only`, перечитай её.
2. `issue-start:approval-comment` — запиши отдельный комментарий одобрения с
   отпечатком показанного тела, словами владельца и «Старт: сейчас».
3. `issue-start:linear-readback` — после записи комментария заново получи из
   Linear задачу с полным живым телом и комментарии с авторами и временем записи,
   включая только что записанное одобрение. Локальный файл, прежний снимок,
   результат записи или вырезка через sed не заменяют это чтение. Нет чтения —
   не переходи дальше и не пиши маркер.
4. `issue-start:owner-author` — в полученных комментариях сверь стабильный ID
   автора одобрения с `issueOnlyLane.ownerPrincipal`, слова и последнее решение
   по времени. Новый запрет закрывает старое согласие. Нет совпадения — старта нет.
5. `issue-start:live-fingerprint` — сохрани полное живое тело именно из шага
   чтения выше и вычисли его отпечаток только через `--emit-fingerprint`.
   Сверь с отпечатком одобрения и показанной версии. Не считай по локальной
   заготовке или отредактированному снимку. Несовпадение — маркер запрещён,
   ревью, «Было / Стало» и новое согласие.
6. `issue-start:permit-marker` — только после успешных чтения и совпадений
   запиши разрешающий маркер последним; перечитай запись.
7. `issue-start:readiness-check` — отдельным действием вызови `mono:check issue`
   в issue-only режиме после маркера и получи `PASS`. Собственный прогон резолвера
   не заменяет эту проверку. До её `PASS` нельзя сообщать «проверка прошла» или
   передавать старт; при другом результате старта нет.
8. `issue-start:handoff` — после `PASS` передай проверенное разрешение на старт.
   Сам этап не меняет состояние на started. В сессии владельца только теперь,
   после подтверждённой записи «Старт: сейчас» и разрешающего маркера, читай mono:implement и продолжай в той же
   сессии; в сессии оркестратора он запускает исполнителя. Не читай этот скилл
   заранее. Владельцу говори о начале работы, без имён скиллов и служебных слов.

## Живое тело после правки

После запрещающей записи и снятия метки по правилам ответа ниже:

1. `issue-edit:body-write` — запиши изменённое тело в Linear.
2. `issue-edit:linear-readback` — заново перечитай полное живое тело задачи из
   Linear после записи, не используй локальную заготовку или результат записи.
3. `issue-edit:live-fingerprint` — только по телу из этого чтения вычисли новый
   отпечаток через `--emit-fingerprint`; несостоявшееся чтение блокирует шаг.
4. `issue-edit:superseded-marker` — запиши `superseded` с новым живым отпечатком,
   составом AC и риском; затем ревью, «Было / Стало» и новое согласие. Новое «да»
   проходит всю разрешающую последовательность выше с повторным чтением автора
   и живого тела после комментария одобрения.

## Ответы по порядку

Каждый шаг с записью читай обратно; подтверждённое той же версии не дублируй.
Перед разрешающей записью заново сверь живое тело и последнее решение; новое
запрещающее решение закрывает старое согласие.

- **«Да».** Метка → комментарий одобрения «Старт: сейчас» → обратное чтение
  из Linear → сверка автора → отпечаток перечитанного живого тела → маркер
  последним → отдельный `mono:check issue` в issue-only режиме `PASS` → старт.
  Каждый шаг развёрнут в обязательной разрешающей последовательности выше.
  Этап не меняет состояние на started: mono:implement проверяет и активирует.
- **«Да, но позже» впервые.** Только комментарий одобрения с отложенным стартом,
  без метки и маркера. Не запускай. То же тело позднее не требует нового показа.
- **«Да, но позже» после «да».** При маркере с разрешением сначала снять метку →
  маркер `Approval: superseded` → комментарий одобрения с отложенным стартом.
  Без маркера с разрешением, в том числе после прерванного «да», первым запиши
  комментарий одобрения «Старт: по слову «запускай»», затем сними метку, если есть.
  Прежний запрещающий маркер оставь; разрешение не пиши.
- **«Запускай».** При последнем отложенном одобрении того же тела проверь автора
  и версию, затем разрешающая последовательность как для «да»: метка → новый
  комментарий с дословным ответом и «Старт: сейчас» → обратное чтение → маркер
  последним → проверка. Новое одобрение должно быть новее последнего `superseded`.
  После отзыва старое «да» не оживает: «запускай» само его не восстанавливает,
  нужен новый показ и новое согласие. Смена версии тоже требует нового показа.
- **«Стоп»/«отменяю».** С разрешающим маркером: снять метку первой → маркер
  `Approval: superseded` → комментарий отзыва с дословными словами владельца.
  Без разрешающего маркера: комментарий отзыва первым → снять метку, если есть →
  `superseded` с живым отпечатком. Отзыв отложенного согласия идёт этим же путём.
- **Правка после «да».** С разрешающим маркером: снять метку → `superseded`
  со старым отпечатком → правка тела → чтение живого тела из Linear →
  новый отпечаток → `superseded` с ним, AC и риском → ревью → «Было / Стало», короткий итог и новое согласие.
  Без разрешающего маркера сначала запиши `superseded` со старым отпечатком,
  затем сними метку, правь тело и продолжай тем же порядком. Не делай даже
  мелкую поправку внутри прежнего согласия. Новое «да» идёт полной разрешающей
  последовательностью, одобрение новее `superseded`.
  Смена состава AC или класса риска до нового маркера даёт `broken marker`
  раньше сверки отпечатка; восстанавливай как `stale marker`, старта нет.
  Риск выше `standard` выводит из пути: старта нет, причина и Idea или Handoff,
  исходную задачу к проекту не прикрепляй. Обычная правка после ready — у Ship
  в границах замороженной части по общей справке пути.
- **Вопрос/сомнение.** Ответь, ничего не утверждай и не запускай. Последний
  ответ на уточнение не подменяет согласие на итог.

Сбой записи: устрани причину и повтори один раз, затем владельцу
«не записано, старта нет». Особый случай — несостоявшийся отзыв при ещё живом
разрешении: «отзыв не записан, задача может стартовать, повторю». Оркестратор
в этой сессии не запускает задачу и перед любым запуском повторяет запись отзыва.
После перезапуска незаписанный отзыв неизвестен: принятое ограничение.
Другое принятое ограничение — окно от последней проверки до перевода в работу:
«стоп» в это время останавливает уже начатую работу оркестратор.

## Повторный вход

В сессии владельца этап замечает обрыв из живых метки, маркеров и комментариев;
оркестратор после перезапуска ищет не начатые задачи без проекта с меткой
`issue-only`, которые не дают `approved-fresh`, и возвращает каждую в mono:issue.
Это не разрешение стартовать. Начатые идут по старым правилам Resume.
Отложенные и отозванные не запускаются. Нет метки — поиск по ней не находит
задачу; текущий ответ и известную задачу восстанавливай в той же сессии.

С переданным ответом дописывай именно его. Без ответа можно дописать прерванное
«да» только при сохранённой метке `issue-only`, если последнее записанное
одобрение разрешает старт, тело то же,
автор верен и нет более нового запрещающего решения. Метка без одобрения не
согласие. `superseded` новее одобрения закрывает его: старое разрешение больше
не писать; допиши отзыв/правку по текущему ответу, а без него «старта нет» и
жди нового показа. Свежий ответ «да» новее `superseded` позволяет дописать его.
Разрешающий маркер при снятой метке — неоднозначный запрещающий переход:
это мог быть обрыв «позже», отзыва или правки после первого шага. Без текущего
ответа метку не возвращай и прежнее «да» не дописывай, даже если последнее
записанное одобрение разрешает старт; «старта нет», жди нового показа. Текущий
дословный ответ позволяет дописать именно его, а не отменённое намерение.
При сомнении сторона без старта. Не дописал — оркестратор сообщает «старта нет».
