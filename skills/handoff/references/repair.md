# Ремонт пакета

Правила классов и их последствия: `<корень>/references/repair-machine.md`.
Ремонт не запускает обычную сборку пакета.

## Маршрут

Принятый дрейф перед PR: `mono:ship`. Правка тела задачи без проекта: `mono:issue`.
Правка PRD до старта: `mono:discovery` с новым утверждением, затем новая версия
записи. После старта сначала ремонт здесь: «было / стало», класс, остановка
исполнителей, снятие разрешений и откат по классу; только потом Discovery
записывает и утверждает PRD (до остановки он может лишь готовить черновик), и ты
заканчиваешь пересборку и проверки. Остальное, включая находку исполнителя и `scope-drift-needs-handoff`:
ремонт здесь. Правка описания идеи при записанном пакете (из `mono:idea`): класс по
смыслу, обычно 3; после ремонта ход возвращается в Idea для записи и проверки.
Неясно, чей маршрут: ремонт здесь; неясно внутри ремонта: класс 3.

Опора ремонта: запись пакета. Старый пакет (одобрение без записи пакета): Tech
Spec, раздел «Старый пакет».

## Находка к странице техлида

Есть `mono-tech`: Tech Spec не правишь. Меняется любая строка утверждённой
страницы (включая проверенные случаи и риск): до старта верни в Tech Evaluation
за новой страницей и записью; затем заново сверь и запиши версию пакета.
После старта сначала класс 3: остановка исполнителей, снятие старта, откат,
затем Tech Evaluation, пересборка, проверка и новый старт владельца.
Дыра без изменения страницы решается в записи пакета через «Решил сам».
Изменение PRD до старта без изменения страницы: Tech Evaluation обновляет запись
под новый PRD без повторного показа владельцу; иначе новая страница.
Это не ремонт старого Tech Spec: его по-прежнему правит Handoff по классам.

## До старта

Записи старта нет: отменять нечего. Перенарезка в пределах трёх задач, новое
общее решение, правка задачи: новая версия записи (`previous`, класс по таблице),
проверка черновика по `review.md`, задачи обновлены, лишние отменены, `mono:check
handoff`. Проект остаётся в Ready, владелец получает обновлённый итог с тем же
окном, без отдельного вопроса. Четвёртая задача: вопрос владельцу, как в нарезке.

## После старта

1. Свежие данные: текущая версия записи, запись старта, задетые задачи и их
   снимки, работающие исполнители и их запуски, последние сертификаты preflight.
2. Точное «было / стало» по устойчивым ID (`R`, `AE`, `U`, `C`, `S`, `T`)
   и предложенный класс с доказательством. Побеждает старший; неясность и рост
   риска это класс 3.
3. `mono:review artifact` по предложенному классу, только отчёт. Пока есть
   блокирующая находка, ничего не меняешь.
4. Транзакция класса:
   - старт привязан к версии, которую он назвал, и не переписывается; новая
     версия держит его в силе только через непрерывную проверенную цепочку
     версий классов 1-2 с прежними защищёнными поверхностями и набором задач;
   - класс 1: новая версия `class=1` или правка только в заметках; старт
     действует, задачи не трогаешь;
   - класс 2: сначала остановить или заморозить задетых исполнителей; новая
     версия `class=2`; снимки задетых задач синхронизированы, отпечатки пересчитаны,
     прежние сертификаты preflight помечены устаревшими; набор задач и итог
     прежние, поэтому старт действует; дальше новый запуск, не продолжение;
   - класс 3: остановить исполнителей; новая версия `class=3` снимает прежний
     старт; снимки, сертификаты и лишние задачи недействительны; Delivery
     возвращается в Ready; проверка черновика, проверки, новый итог с «Начать
     работу» и новая запись старта по слову владельца.
5. `mono:check repair`. В заметках новой версии: «было / стало», класс,
   доказательство, старый и новый `sha256`, что с сертификатами и исполнителями,
   статус проекта.

## Находка в предприменении

Манифест живёт в своём пункте `U` записи (у старого пакета в единице Tech Spec).
Исполнитель паркуется `blocked` с точными байтами замены. Класс по смыслу: класс 2,
только если требования, примеры приёмки, «Что не входит», видимое поведение,
риск и набор задач прежние; иначе класс 3. После ремонта новый запуск
`dispatch.mjs --preapply`, никогда не amend и не resume.

## Старый пакет

Шаги те же, опора Tech Spec и прежний формат одобрения во всех классах. Классы
1 и 2 сохраняют одобрение. Класс 3: остановить исполнителей, снять прежние
разрешения, Delivery или Ready в Discovery, после ремонта новое разрешение
владельца в прежнем формате: комментарий одобрения пакета с одной строкой
`approval_status=approved`, ссылкой на «Исследование» и, при идее `stale` или
`legacy-migrate`, записью идеи, как у записи старта. Запись пакета сама не появляется: старый пакет
не переводишь и не пересобираешь в новый.
