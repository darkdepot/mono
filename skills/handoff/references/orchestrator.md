# Когда этап ведёт оркестратор

Шаги те же: сверка, взгляд в код, нарезка, проверка черновика, запись, Ready,
итог. Handoff начинается сам после последнего этапа цепи записей: Discovery,
Design, затем Tech Evaluation, когда они нужны; без окна. Владельца в разговоре нет, но есть его
слова: решения в Linear, цитаты с датами, правила статусов, прошлые проекты.

- Свой план не заменяй: вызов плана переписывает весь список. Одна строка:
  «Handoff «<проект>»: <пункт>».
- Конфликт сверки без денег, данных пользователей и необратимого решаешь сам:
  в «Сверке» записи строка с ответом и причиной (цитата владельца с датой, ссылка
  или «суждение»), владельцу это идёт строкой «Ответил сам» в итоге. Цитаты
  спорят: действует поздняя, но правило самого владельца сильнее PRD, который
  утверждал ты.
- Деньги, данные пользователей, необратимое, больше трёх задач: бриф владельцу по
  `<корень>/templates/orchestrator-brief.md`, этот проект ждёт ответа, другие
  волны идут. По тому, что Tech Evaluation уже утвердил `by=orchestrator`,
  отдельного брифа нет: итог ниже несёт эти решения владельцу. Новая находка,
  меняющая страницу, возвращается в этап по `record.md`.
- Нужна правка PRD: Discovery в режиме оркестратора, утверждение `by=orchestrator`
  с причиной, Handoff продолжает с того же места.
- Вторая модель: протокол Second Voice для проверки пакета до записи, не больше
  трёх раундов.

## Итог владельцу

После Ready одно сообщение, в «Статусе» строкой проекта. Работу начинает только
владелец, поэтому «Нужно от тебя» не «ничего». Строка «Техлид решил за тебя:»
называет принятое этапом необратимое, отложенный пункт PRD и строку против
прежнего решения владельца, каждое с причиной; таких решений нет: «нет».
Рядом строка «Дизайнер решил за тебя:»: направление, причина по эталонам и
вкусу, ссылка на запись и Paper; без макета «дизайн не требуется» или прежний
путь. Это часть итога перед стартом, не отдельный бриф.

```text
Лист ожидания готов к работе, статус Ready: <ссылка>.
Что делаем: освободилось окно, его сразу берёт следующий из листа.
Задачи (1): лист ожидания с заменой у мастера.
Дизайнер решил за тебя: лист с быстрым действием, по эталонам продукта; <Paper>.
Техлид решил за тебя: у окна один записанный, иначе два человека придут в одно
время; выбор любимого мастера отложен, чтобы сначала заполнить пустые окна.
Ответил сам: PRD давал мастеру кнопку «принять», твоё правило от 03.10.2026
против лишних нажатий; оставил замену по факту, PRD поправил.
Решил сам: одна задача: лист и замена проверяются только вместе.
Сверено: описание, исследование и PRD с правкой; у каждого требования есть задача.
Нужно от тебя: начать работу: скажи «начинаем лист ожидания». Перевернуть:
«мастер подтверждает замену».
```

Окно «Начать работу» / «Ещё обсудить» показывай, только когда живых волн нет:
окно держит ход, и пока владелец не ответил, ты не следишь за волнами. Есть живые
волны: только строка «Нужно от тебя», ход продолжается, проект ждёт в Ready.

## Старт

Нажатие «Начать работу» или слово владельца «начинаем <проект>»: свежая сверка
входов перед первой записью старта и сама запись по `record.md` с `by=owner`, обратное чтение, затем запуск по правилам
оркестрации. В снимке `approval.md` это запись старта, а `tech-spec.md`
содержимое забора текущей записи пакета. Перед каждым запуском: старт `by=owner`,
называет эту задачу и версию записи; текущая версия та же или получена из неё
проверенной цепочкой версий классов 1-2; после версии класса 3 запуска нет до
нового старта владельца. Задачи по порядку зависимостей: проба
и общая основа первыми, задачи с общими местами строго цепочкой.

Сам работу не начинаешь никогда: проект в Ready без записи старта не запускается,
даже если владелец давно не отвечает. Переворот «мастер подтверждает замену»:
правка по `repair.md` до старта и новый итог тем же образцом.
