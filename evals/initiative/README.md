# Инициатива: срабатывание и проверка поведения

По образцу `evals/tech-evaluation/README.md`: три положительных запроса — сырая
идея на несколько проектов, черновая инициатива, повторный вход; четыре близких
отрицательных — один проект, одна доработка без проекта, Research проекта,
Idea проекта карты. Каждый `<случай>/prompt.md` имеет тег `initiative` и
`graders/initiative-invocation.md` с `tool_used` для `Skill`. У отрицательных
`min: 0`, `max: 0`. Синтетические примеры без личных данных.

Это только срабатывание, не доказательство записей и разговора. Оркестратор
запускает из версии пака с ветки на хосте после preflight:

```bash
claude plugin validate . --strict
claude plugin eval . --ablation none --runs 3 --threshold 0.8 --no-publish --trust-plugin
```

Случаи входят в общий набор при изменении описания или evals. Каталог поведения
шести этапов `evals/scenarios/index.json` не меняется; Initiative, как Issue и QA,
остаётся `uncovered` при выборе сценариев. Успех срабатывания не доказывает
ни одного из случаев ниже. Структуру и чтение проверяют `validate-workflow` и
`node scripts/read-budget.mjs --skill initiative --mandatory` (до 20 480 байт).

## Как проверить

Каждый случай проверяется на версии пака с ветки в сессии владельца с полным
Linear. Сохраняй показанный текст, вопрос, дословный ответ и обратное чтение
изменённых сущностей с `id`; сравнивай до/после. Не засчитывай намерение,
инструкцию в скилле или вывод валидатора за поведение агента.

1. **Сырая идея.** Дано: идея на несколько проектов без исследований и похожей
   инициативы. Когда владелец начинает этап и проходит выборы, тогда поиск
   предшествует созданию Proposed, цель сформулирована, пробелы исследованы,
   модель выбрана владельцем; одно согласие на показанную версию даёт Planned,
   проекты в Idea с владельцем, привязкой, приоритетами и зависимостями.
   Итог называет порядок, приоритеты и зависимости и не запускает проекты.
2. **Похожая уже есть.** Дано: подходящая инициатива с другим названием.
   Когда приходит сырая идея, тогда этап читает кандидата и продолжает его;
   число инициатив не растёт. При двух кандидатах спрашивает до записи.
3. **Черновик с исследованием.** Дано: исследование в документе и встроено в
   старое описание, модель не выбрана. Когда этап входит, тогда называет
   сделанное, читает все документы через list_documents, сохраняет прежнее
   описание с обратным чтением; исследование не повторяет, добирает только
   различающие варианты пробелы. Старые материалы остаются по ссылкам.
4. **Незакрываемый пробел.** Дано: для модели важен недоступный источник.
   Когда добор не удался, тогда пробел, его последствия и граница уверенности
   видны владельцу до вопроса о модели; выдуманного факта нет.
5. **Выбор модели.** Дано: цель выбрана, исследование проверено. Когда этап
   предлагает модель, тогда два-три разных варианта, позиция и сильнейший
   довод против совета видны в разговоре; до вопроса один проход второй
   семьи, замечания разобраны. Решение делает владелец, отметка выбора
   сохраняется сразу и читается обратно. Без ответа выбора нет.
6. **Прерывание.** Дано: выбранная модель с отметкой сохранена, карты нет.
   Когда новую сессию начинает владелец, тогда этап читает части и продолжает
   карту без пересказа и повторного выбора модели; нового учёта состояния нет.
7. **Правка после показа.** Дано: цель, модель и карта показаны, хеши запомнены.
   Когда владелец просит поправить, в том числе «да, но поправь приоритет К2»,
   тогда снимается отметка затронутого выбора, правка читается обратно,
   новый показ и вопрос; прежнее согласие не создаёт запись или проекты.
   Повтори с внешней правкой после показа: свежий хеш даёт «Было / Стало».
8. **Ответ без согласия.** Дано: итог и вопрос об утверждении показаны.
   Когда владелец задаёт вопрос, сомневается или отказывает, тогда разговор
   продолжается без mono-initiative approval и создания проектов. «Да» на
   уточняющий вопрос не заменяет согласия на итог.
9. **Повтор после сбоя.** Дано: утверждение годно, часть проектов создана;
   прерви после save_project до строки «Заведён». Когда этап повторяется,
   тогда свежая проверка инициативы проходит, проект находится по номеру
   и ссылке среди привязанных, создаются только недостающие. Повтори после
   переноса исходного тела в «Отброшено» брифа: найден тот же id, дубля нет.
   Измени решение без нового согласия: создание останавливается до показа.
10. **Новая карта между проходами.** Дано: все проекты созданы, зависимости
    ещё не записаны; один пункт существующий, с последним комментарием о
    зависимости. Когда после сбоя владелец меняет карту, снимает пункт и
    последнюю зависимость, видит новый показ и вновь утверждает, тогда второй
    проход всех оставшихся пунктов использует новую карту: старые составы id
    переписаны, последняя строка зависимости нового проекта удалена,
    существующий получает новый комментарий «Зависит от: нет». Проект снятого
    пункта не меняется и назван в итоге. При ещё одном повторе число проектов
    и одинаковых комментариев не растёт. До показа цикл К1→К2→К1 и ссылка на
    отсутствующий номер останавливают карту, утверждения нет.
11. **Признанный проект.** Дано: владелец признал существующий проект пунктом
    карты. Когда согласие записано, тогда «Есть проект» было в показанном хеше;
    по тому же id добавлены привязка и приоритет, зависимость комментарием.
    Тело и статус побайтно/по id не изменены, новый проект не создан. Переименуй
    проект: утверждение остаётся годным, сверка по id, не названию.
12. **Состояния S10.** Дано: пункты без проекта и проекты в Canceled,
    Completed, Discovery, Ready, Delivery, Idea без записи Idea, Idea с годной
    записью, Idea с негодной записью и неизвестном статусе. Когда этап входит
    повторно, тогда сначала статус: отменён, завершён, в работе; Idea без
    записи — утверждён, с годной — разрешён к запуску; без проекта — предложен.
    Иные сочетания названы как есть, без разрешения. Порядок внутри приоритета
    по номерам и id в «Есть проект»/«Заведён». Статус инициативы после Planned
    не меняется; даже все Completed не закрывают её и не доказывают цель.

## Живой прогон до вливания

Обязательная проверка T2 с владельцем в команде Mono, на версии пака с ветки:
сырая тестовая идея до утверждения и проектов в Idea; тестовая черновая
инициатива с документом; прерывание и продолжение в новой сессии; повтор после
утверждения без дублей. `monotest` годится только для репетиции, если
оркестратор подтвердит чтением, что там есть инициативы. Поведение проверяется
в обоих поддержанных хостах по возможности; непроверенный хост назови явно.

Оркестратор пишет итог комментарием «Живой прогон: …» в MONO-260. До него
готовности к вливанию нет. Тестовую инициативу и проекты карты сохрани до
прогона T3; ссылки комментарием в MONO-261 пишет оркестратор. Остальное тестовое
в Canceled; после T3 оркестратор отменяет и сохранённое. На Zeni не проверяем.
По запросу оркестратора mono:qa проверяет сценарии/след независимо; это не
подмена участия владельца. Worker не делает прямых записей Linear.
