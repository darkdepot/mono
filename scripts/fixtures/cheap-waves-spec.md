# Tech Spec: Дешёвые волны — ожидание на месте, короткий профиль, команды оркестратора, предприменение `.agents/`

## Кратко

Четыре изменения пака при неизменных воротах: (1) рукопожатие без выхода процесса — исполнитель ждёт запись о применённых ходах в окне сторожа, запасной путь — сегодняшний перезапуск; (2) профиль `short` для tiny/standard без открытых решений — один сбор вместо локального прогона плюс сбора, сведения о старте в человеческой части комментария сертификата, снимок по ссылкам; (3) команды `dispatch`/`accept`, адаптер Linear с сеансами сверки и сборщик с восстановлением по квитанциям — в паке; (4) предприменение изменений под `.agents/` по мандату владельца, по перечню из утверждённой задачи, с записью в журнале.

## Исходные требования

PRD R1–R10, AE1–AE15. Неизменные: проверка идентичности пака, `gate.mjs start|preflight|ship`, `validatePreflight`, подписи квитанций и порядок их записи, подтверждение очередей, порядок фаз code → preflight → ship, правило «ход только после gate-ack», маркер `mono-preflight certificate\nPreflight: <…>`, окно подавления сторожа «порог × 4» от затишья журнала, legacy-форма потребления с `last_resume` и её тексты ошибок.

## Цели и не цели

Цели: R1–R10. Не цели: смысл ворот, помощник ревью, запись в Linear из скриптов, транспорт claude-code-desktop, выкладка/cutover, проверка входа Claude.

## Архитектура

Сегодня: «ack → выход процесса → ход в Linear → файл возобновления + запрос + потребление (требует регистрации возобновлённого писателя) → `codex exec resume`». Целевое (режим `wait`): «ack → блокирующее ожидание записи `consumed/<KEY>-gate-ack-a<N>.json` с `outcome: applied` и read-back по каждому ходу, не дольше `ackWaitSec` от записи ack → продолжение в том же процессе». Режим рукопожатия (`handshake: wait | resume`, default `resume`) пинится на попытку в запросе запуска и реестре независимо от профиля. Каталог `consumed/` вне грантов записи исполнителя; чтение собственной записи разрешается явно.

Часы и сторож. Порог простоя `orchestration.delivery.stallSec` (default 120) объявляется в общей конфигурации доставки; сторож берёт его по умолчанию (флаг `--stall-sec` остаётся переопределением), `ackWaitSec` (default 420) валидируется как `≤ stallSec × 4 − pollSec`; сторож при запуске проверяет то же неравенство против своего эффективного порога (включая переопределение `--stall-sec`, минимум 90) и отказывает при несовместимой конфигурации. Запись ack — последнее событие журнала исполнителя (команда записи попадает в jsonl), поэтому окно ожидания и часы подавления стартуют от одной точки. Пока исполнитель ждёт, журнал молчит; при потреблении в режиме `wait` оркестратор пишет в реестр `last_wait.consumedAt`; сторож для попытки с `handshake = wait` и надгробием `.applied` продолжает подавление, пока mtime журнала < `consumedAt`, но не дольше одного `stallSec` от `consumedAt`; после этого действуют обычные правила. Исполнитель после возврата `wait-ack` немедленно продолжает: следующее событие jsonl (завершение команды ожидания) сдвигает mtime.

Воплощение писателя. При регистрации потока (`thread.started`) реестр получает `procStart` (время запуска процесса, `ps -p <pid> -o lstart=`). Потребление `applied` в режиме `wait` требует: pid жив, `procStart` совпадает, `thread_id` совпадает, в потоке jsonl этой попытки (после `thread.started` текущего потока) есть событие начала команды `delivery-state.mjs wait-ack` с аргументами этой попытки, и события завершения с тем же `item.id` нет — сообщения о ходе работы между ними не мешают (исполнитель в ожидании), `ackDigest` = digest ack; записывает `last_wait {pid, procStart, thread_id, gateAckDigest, consumedAt}`; `consumedAt` пишется один раз до надгробия и при восстановлении не обновляется; сторож принимает только конечное непрошедшее время и возраст `0 ≤ age < stallSec`. Иначе — отказ «waiting writer not verified»; восстановление = обычное возобновление (регистрирует `last_resume`), затем legacy-форма потребления без изменений.

Профиль `short | full`: `short` только при risk ∈ {tiny, standard}, `critical = null`, готовность AFK, отсутствии открытых решений; оркестратор может задать `full`. Профиль меняет обязательность локального прогона (U3), очередь фазы кода (U4), состав снимка (U5). Ворота `gate.mjs` профиль не читают.

Пины попытки. Неизменяемая идентичность запуска `pins.json` (modelRoutes, base, product, evidenceRoot, skillsRoot, verification, handshake, profile) с digest в реестре; версии поправок `pins.v<n>.json` (risk/critical — только вверх, версия reviewDataset, workerWritableRoots) пишет только `accept amend`, регистрирует в реестре (`pinsVersion: n`); при допуске запроса сбора сборщик под той же блокировкой, что и `amend`, пишет запись допуска `{collectionId, reportDigest, pinsVersion, manifestDigest}`; квитанция сравнивается по фактическим полям привязки (risk/critical, reviewDataset, workerWritableRoots, verification) с этой записью; новый запрос со старой версией отклоняется, ранее допущенный восстанавливается из записи.

Команды оркестратора — обёртки над `spawn.mjs`, `gate.mjs start`, `resume.mjs`, `consume-gate-ack.mjs`, `delivery-state.mjs confirm` и адаптером пака. Записи в Linear выполняет оркестратор через коннектор.

```
orchestrator                                          worker (один процесс, режим wait)
  dispatch.mjs ──spawn──▶ ворота ── gate-ack (jsonl event) ──▶ wait-ack (≤ ackWaitSec)…
  accept.mjs ack: validate → [нет записи] план ходов → (коннектор) → --readback → consume(live incarnation)
                              [есть та же запись] завершить переименование/снятие gates, плана нет
  accept.mjs report: сеанс сверки → записи+сертификаты → (коннектор) → --observe(session) → adapter → confirm
  collector.mjs: сбор по запросу (history-first, head reconcile под per-head lock), автоподтверждение очередей без коннекторных записей
```

## Контракты и границы

- Запись потребления ack (существующая): `{issue, attempt, outcome, gates, ack, ackDigest, readback:[{moveDigest, evidence}]}`. Исполнитель ждёт `outcome: applied`, проверяет `issue/attempt`, `ackDigest` = digest своего ack, `readback.length` = число ходов диспатча, каждый `moveDigest` = digest хода (тот же канонический digest, что у `lifecycle_moves`). `blocked|rejected` — завершение как сегодня.
- `delivery-state.mjs wait-ack --root <root> --issue <KEY> --attempt <N> --ack <path> --moves <json> --config <cfg>`: дедлайн = mtime ack + `ackWaitSec`; выход 0 при валидной записи; ненулевой с текстом `write-unconfirmed` при истечении (исполнитель паркуется с отчётом и выходит); отказ при чужой попытке/подделке digest/неверном числе ходов.
- `deliveryConfig`: `stallSec` (default 120), `ackWaitSec` (default 420, проверка `≤ stallSec × 4 − pollSec`); сторож: `--stall-sec` default = `stallSec` конфига продукта (передаётся `--config`).
- Запрос запуска/реестр: `handshake`, `profile`, `pins {file, digest}`, `pinsVersion`, `procStart` (после `thread.started`), `last_wait` (при потреблении в режиме wait).
- Потребление (`consume-gate-ack.mjs`): `applied` принимается либо legacy-формой (`last_resume` с digest ack; текст ошибки без изменений), либо формой «живой ожидающий писатель» (см. «Архитектура»). Прежняя одинаковая запись `consumed/` → завершение переименований и снятия `gates` без повторной проверки писателя (как сегодня); противоречащая → отказ.
- Сторож: правило продолжения подавления после `.applied` для `handshake = wait` (см. «Архитектура»); остальное без изменений.
- Очередь фазы кода на `short`: пустая; отчёт публикуется и подтверждается (`results: []`). Сведения о старте — в `capsule.decisions` и в человеческой части комментария сертификата готовности перед неизменным машинным блоком; идентификатор записи сертификата не меняется.
- Снимок на `short`: `issue-<KEY>.md`, `approval.md`, `project-brief.md`, `prd-extract.md`, `spec-extract.md`. Грамматика идентификаторов `(A|F|R|AE|U)\d+(′|'|[а-я])?` (суффиксы-штрихи и кириллические буквы, как `AE3а`); ссылки покрытия распознаются и в форме «Покрывает …», и во встроенной форме `(…; R1, R3; I1)`; диапазоны `R8–R9`/`R8-R9` раскрываются; определение = пункт списка (`- `/`* `) или заголовок (`##`/`###`), начинающийся с идентификатора (после него `.`, `(`, пробел или конец); определение длится до следующего определения того же семейства на том же уровне списка или до следующего заголовка; всегда включаются: PRD «Кратко», «Что не входит в MVP», «Допущения»; Tech Spec «Кратко», «Архитектура», «Контракты и границы», «Риски и защита», «Что может сломаться и как защищаемся», «Валидация», «Релиз и откат»; отсутствующие необязательные разделы пропускаются; транзитивное замыкание по ссылкам «Покрывает …» внутри выбранных определений, защищённое от циклов; несуществующий идентификатор → отказ запуска; дубликат определения → полные документы с пометкой; issue-only → задача, утверждение, маркер, метка; повышение класса исполнителем → парковка `blocked` с запросом полного снимка, `accept amend --full-snapshot`. Фикстуры: шаблоны PRD/Tech Spec, реальные документы MONO-92 (маркер `* `, диапазоны, `U5′`) и документы этого пакета (`AE3а`, встроенная форма покрытия).
- `dispatch.mjs --issue <KEY> --root <root> --config <cfg> --snapshot <dir> [--risk …] [--critical <text>] [--profile short|full] [--handshake wait|resume] [--role … --reason …] [--preapply] [--full-snapshot]`: тела в снимке; рабочее дерево от `origin/main`; предприменение по разделу задачи (U7); выписки (U5); `pins.json` + digest; запросы ворот старта и запуска; рендер диспатча из шаблона (все подстановки, иначе отказ); `spawn.mjs`; строка `ledger.md` через `date -u`. Отказ до `spawn.mjs` — без регистрации попытки.
- `accept.mjs ack --issue <KEY> --attempt <N>`: единственное допустимое место ack; корреляция с реестром; полнота покрытия `registryEntry.gates`; исход. Без записи `consumed/` — печать плана `{planDigest, moves:[{moveDigest, entity, key, from, to}]}`; `--readback <json>` требует `planDigest`, по одному наблюдению на ход с `observedAt` ≥ времени печати плана («уже в целевом состоянии» допустимо) → `consume-gate-ack.mjs`. С одинаковой записью — завершение потребления, плана нет; с противоречащей — отказ.
- `accept.mjs report --report <file>`: открывает сеанс сверки `{sessionId, openedAt, reportDigest}` в `consumed/<KEY>-a<N>/sessions/`, делая прежние наблюдения этого отчёта недействительными; печатает записи с развёрнутыми сертификатами и, при повторе, сначала список для перечитывания (поиск комментария по маркеру перед любой повторной публикацией); `--observe <id>=<json>` записывает наблюдение `{sessionId, writeId, reportDigest, writeDigest, observedAt, evidence}`; при полном наборе вызывает `delivery-state.mjs confirm` с окружением `MONO_ACCEPT_SESSION`, `MONO_ACCEPT_REPORT`.
- Адаптер `scripts/orchestrator/linear-adapter.mjs` (stdin/stdout контракт `delivery-state.mjs` без изменений): корень из окружения/аргумента, без личных путей; `reconcile` возвращает `present` только при наблюдении текущего сеанса (`MONO_ACCEPT_SESSION`) с `reportDigest` = digest отчёта из `MONO_ACCEPT_REPORT` и совпадающим `writeDigest`, иначе `unknown`; `missing` — только при наблюдении «отсутствует» текущего сеанса; `apply` печатает инструкцию и возвращает без результата — печать никогда не считается успехом; ветка `apply` при этом дизайне обычно недостижима, потому что оркестратор собирает наблюдения до `confirm`.
- `collector.mjs start|stop|status --root <root> --issue <KEY> --attempt <N>`: блокировка `reports/<KEY>-collector-a<N>.lock` с `{pid, procStart}`; при существующей блокировке — забирает только если воплощение держателя мёртво и нет живого дочернего процесса ворот для этой головы, иначе отказ. Per-head `<head>.collect.lock` (пишется `withLock` в `gate.mjs`): запись блокировки дополняется `procStart`; устаревшая блокировка (держатель и его дочерние процессы мёртвы по воплощению) забирается сборщиком через маркер `reclaim` перед приведением головы; живой держатель — отказ. Фикстура: падение процесса ворот между записью истории и головы с ОБЕИМИ блокировками на диске. Корреляция отчёта фазы: `validatePhase` + идентичность реестра (issue/attempt/pack) + ровно одно допустимое место отчёта + digest + предшественники (`requirePredecessors`); `correlatedDeliveryReport` — только для терминальных отчётов. Перед сбором: поиск в `<evidenceRoot>/history/` подписанной квитанции с этим `collectionId`, проверка подписи и пинов версии запроса; при наличии — под `<head>.collect.lock` приведение квитанции версии кода `<head>.json` к найденной (переписать из истории, если отсутствует или другая) и фиксация результата без повторного ревью; иначе сбор через `gate.mjs preflight collect:true`. Очереди без коннекторных записей (пустые, только сборы) подтверждает сам; журнал `reports/<KEY>-collector-a<N>.log`.
- Предприменение (только при `orchestration.preapply.mandate` в конфиге продукта — ссылка на комментарий владельца, текст которого покрывает и процедуру исправления): утверждённая задача несёт раздел «Предприменение»: таблица `{path, sha256}` и полное содержимое каждого файла в ограждённом блоке; `dispatch.mjs --preapply` разбирает раздел из снимка задачи, проверяет пути (только `.agents/`, обычные файлы, без `..`, символические ссылки отклоняются), sha256 содержимого = перечню, чистое дерево; коммит `<KEY>: pre-applied .agents changes (orchestrator)` до ворот старта; блок диспатча «Предприменённые изменения: коммит, файлы, sha256»; строка `ledger.md` «PREAPPLY <KEY> <sha> per mandate <url>»; повтор с тем же перечнем идемпотентен. Перечень предприменения для Project-first живёт в Tech Spec как часть единицы реализации и попадает в снимок задачи; для issue-only — в самой задаче. Исполнитель на воротах сверяет `git show <sha>` с перечнем и не меняет эти файлы; замечание ревью по ним → парковка `blocked` с точными байтами → исправление только через владельца артефакта по `repair-machine.md`: Project-first — ремонт `mono-handoff` с классификацией по смыслу (класс 2 только если охраняемые поверхности не изменились, со всеми эффектами класса: синхронизация снимка, перевычисление отпечатков, устаревание сертификатов; класс 3 при изменении риска/объёма — с повторным утверждением владельца), issue-only — обновление через `mono-issue` (create-then-approve); затем НОВЫЙ запуск (свежая попытка `dispatch.mjs --preapply` по обновлённому перечню), не возобновление. База ревью `origin/main` — сбор проверяет коммит.

### Реальные ответы бэкенда

Не применимо: внешнего API нет; формы записей Linear известны из сегодняшних `consumed/` и `confirmations/`.

## Влияние на остальную систему

Сторож: окно подавления не меняется; добавлено продолжение после потребления для wait. Подтверждения очередей: без изменений. Ворота `gate.mjs`: без изменений (сборщик использует существующий per-head lock). Другие продукты: `handshake`/`profile` по умолчанию `resume`/`full`, `stallSec` по умолчанию 120 — поведение как сегодня. claude-code-desktop: без изменений.

## Риски и защита

- Ожидание без активности → сторож: окно ожидания < подавления, общий порог, продолжение после потребления в пределах порога, парковка по истечении.
- Подмена записи `consumed/`: проверки digest/числа ходов; каталог вне грантов записи.
- Переиспользование pid: воплощение (pid + время запуска) + поток + незавершённая команда ожидания в журнале.
- Смерть между обратным чтением и потреблением: потребление отказывает; ходы уже применены и прочитаны — обычное возобновление с амендментом, legacy-потребление.
- Профиль `short` на неподходящей задаче: отказ; повышение класса → локальный прогон обязателен, полный снимок по парковке, версия поправок.
- Выписка теряет контекст: общие разделы (включая «Архитектура») всегда; двусмысленность → полный; несуществующий ID → отказ.
- Наблюдения адаптера устарели: сеансы сверки; прежние недействительны.
- Двойной сбор после падения сборщика: history-first по `collectionId` с подписью и пинами; голова приводится под per-head lock.
- Предприменение как «оркестратор пишет код»: мандат, перечень с хешами в утверждённой задаче, журнал, сверка исполнителем и сбором, исправления только через ремонт задачи.

## Что может сломаться и как защищаемся

Legacy-попытки: форма и тексты ошибок сохранены, тест без изменений. Сертификат с `0 local passes`: фикстура нарратива; ворота читают квитанцию. Пустая очередь: `results: []` валидно. Личный адаптер оркестратора: совместим по stdin/stdout, пак ссылается на свой. Сторож на старых записях без `handshake`: правило продолжения не применяется.
