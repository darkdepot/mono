# PRD: Ревью по доказательствам: предсказуемая цена авто-ревью без потери дефектов

## Кратко

Авто-ревью в паке — длинные последовательности ревью и правок с полной проверкой каждой новой версии кода и без памяти о принятых решениях; расход самого ревьюера не измеряется, а ревьюер и исполнители сгорают в лимитах Claude и Codex. Проект вводит честный учёт ревью, журнал решений по замечаниям, матрицу поведения при повторной находке и диагностический чекпойнт — при неизменных воротах выпуска; сравнивает кандидатов в ревьюеры со своими лимитами с нынешним на замороженных версиях наших задач; даёт владельцу выбор моделей по ролям в конфиге продукта; после пилота встраивает доказанные правила и бюджет попытки в пак. Цель: заметно меньше времени и расхода ревьюера при прежнем обнаружении дефектов и ревьюер в отдельном лимите.

## Акторы

* A1 — владелец: ждёт готового PR, платит лимитами Claude (ревьюер и оркестратор) и Codex (исполнители), принимает решения по бюджету, качеству, провайдерам и передаче кода; на время этого проекта делегировал решения по бюджету и качеству оркестратору; решение о передаче кода внешним провайдерам принял сам.
* A2 — оркестратор: запускает сборы доказательств, решает по представленным доказательствам, применяет решения по замечаниям в журнал, ведёт учёт и цену волны, паркует и возобновляет доставки, проводит стенд.
* A3 — исполнитель (worker): чинит код, запускает локальное ревью, предлагает диспозиции по находкам с доказательствами, составляет матрицы поведения, отвечает на чекпойнт.
* A4 — ревьюер (внешний помощник autoreview) с движком и моделью по маршруту.
* A5 — провайдер ревьюера: Anthropic (сейчас) или внешний со своим лимитом (Z.ai, Moonshot, DeepSeek, xAI, MiniMax); получает диф, набор данных задачи с разделом решений и подготовленные помощником доказательства.

## Проблема

Источники подтверждают длинные последовательности ревью и правок, но не дают сверенных чисел. Волна MONO-75 (14–15.09.2026): доставка 8 ч 58 мин; отчёт перечисляет 30 попыток локального ревью и сборов, включая один отказ до ревью (11 локальных с порогом P3, 3 локальных P2, 2 по ветке, 14 сборов оркестратора); прежний счётчик цены показал 61 объявленный проход — число фактических вызовов требует сверки; около 6 часов — предварительная оценка интервала петель, не измеренное время ревьюера. Часть сборов находила одно новое замечание в предыдущей правке, часть — два, финальный — ноль; поздние сборы находили реальные дефекты. У App (прежняя поверхность) задачи проходили до 12 кругов ревью на Sol с правками между кругами; в нескольких кругах — по две P1. Расход самого ревьюера не измеряется: помощник печатает его только в потоковом режиме, который сбор не включает. Решения по замечаниям живут в прозе; ревьюер о них не знает и повторяет их. Ревьюер (Opus 5) делит лимит Claude с оркестратором, исполнители — лимит Codex; отдельного лимита у ревью нет. Порог P3 в раннем preflight уже устранён в MONO-75 — это не заслуга проекта.

## Текущий процесс

Исполнитель после правок запускает локальное ревью до чистого результата без предела кругов, затем запрашивает сбор; оркестратор на каждой новой версии кода выполняет полную проверку и полное ревью в песочнице; находка → правка → новая версия → новый полный сбор. Опровергнутые замечания повторяются. Цена волны показывает объявленные проходы и «н/д» по расходу ревьюера. Маршрут ревьюера один для всех продуктов и задан только таблицей политики пака.

## Целевой процесс

Каждый запрос сбора, каждый вызов ревьюера и каждый внутренний проход записываются с причиной запуска и предшественником; роль в сертификации — отдельное поле; расход ревьюера виден по провайдеру с полнотой покрытия. Перед каждым запуском ревьюер получает актуальные решения этой задачи в неизменяемой версии набора данных; опровергнутая находка без нового факта не ведёт к правке кода. Повторная находка по одному инварианту требует матрицы поведения; два круга без подтверждённого прогресса — диагностической сводки; оркестратор решает по доказательствам и не запрашивает сбор, пока их нет. Владелец задаёт в конфиге продукта модели по ролям, а ворота запускают ревьюера по этому маршруту и записывают его в квитанцию. Кандидаты в ревьюеры сравниваются на стенде до любого выбора. Исчерпание бюджета попытки — парковка с остатком. Ворота выпуска неизменны.

## Сценарии

* F1. Оркестратор закрывает задачу; строка цены показывает запросы сборов, вызовы ревьюера по причинам, объявленные и подтверждённые проходы, расход ревьюера по провайдеру и полноту покрытия.
* F2. Сбор нашёл замечание по инварианту, по которому в этой попытке уже была правка; исполнитель составляет матрицу поведения, проверяет её адресно и прикладывает к отчёту фазы; оркестратор запрашивает сбор только с матрицей.
* F3. Ревьюер повторяет замечание, ранее опровергнутое с доказательством; исполнитель не меняет код, отвечает ссылкой на решение; если ворота продолжают его требовать, доставка паркуется как требующая решения.
* F4. Два круга подряд без подтверждённого прогресса; исполнитель отвечает на пять вопросов чекпойнта; оркестратор проверяет ответы до следующего сбора.
* F5. Бюджет попытки исчерпан при оставшихся подтверждённых дефектах; доставка паркуется с перечнем дефектов и запросом продления.
* F6. Оркестратор прогоняет кандидатов в ревьюеры на замороженном манифесте, размечает вслепую и получает отчёт с рекомендацией, включая исход «оставить нынешнего».
* F7. Владелец задаёт в конфиге продукта ревьюера из числа проверенных маршрутов; следующая доставка этого продукта идёт с новым ревьюером, квитанция несёт маршрут, а запущенные ранее потоки хранят свои пины.

## Требования

* R1 (учёт). Для каждой попытки ведётся реестр событий ревью с тремя раздельными счётчиками — запросы сборов, вызовы ревьюера, внутренние проходы; каждое событие имеет каноническую идентичность и список источников-псевдонимов, привязку к попытке, версию кода и маршрут, статус, число находок, объявленные и подтверждённые проходы, причину запуска из словаря (правка, новая версия, перезапуск, финальная проверка, самопроверка, неизвестно) и отдельно роль в сертификации. Неоднозначная корреляция источников даёт запись «покрытие не разрешено», а не двойной счёт; отклонённый запрос сбора считается в спросе и даёт ноль выполненных сборов и вызовов. Повторный локальный запуск признаётся самопроверкой только по наблюдаемой идентичности содержимого; подтверждённые проходы — из проверенных отчётов помощника.
* R2 (расход ревьюера). Для каждого вызова, где помощник сообщает расход, сохраняются сырые счётчики движка и нормализованные вход, чтение кэша, запись кэша, выход; каждый вызов учитывается один раз; цена волны показывает расход ревьюера в токенах по провайдеру с полнотой покрытия и причинами пропусков, отдельно от исполнителя. Токены не выдаются за остаток лимита.
* R3 (сверка базы). Волны MONO-72…78 и задачи APP-342, APP-363 сверены по R1; для продолжений записана отдельная классификация происхождения с доказательством; итог опубликован в Linear как базовая линия «до» с указанием того, что источники не позволяют определить.
* R4 (архив для воспроизведения). Набор данных каждого сбора хранится как неизменяемая версия с отпечатком вместе со ссылками на версию кода и базу и происхождением маршрута и помощника; случаи без восстановимых входов признаются невоспроизводимыми.
* R5 (журнал решений). Каждое разобранное замечание имеет запись с проблемой, условием срабатывания, доказательством, влиянием, происхождением, решением, условиями актуальности и проверкой; матрицы поведения и результаты адресной проверки — типизированные записи; записи не перезаписываются, новое решение ссылается на заменённое; ключ инварианта записи назначает оркестратор.
* R6 (кто решает). Исполнитель предлагает диспозицию с доказательством в отчёте фазы; оркестратор проверяет и применяет её в журнал; замечание, которое ворота продолжают выдавать, остаётся нерешённым и паркует доставку как требующее решения. Журнал никогда не превращает находку ревьюера в «чисто».
* R7 (память ревьюера). Перед каждым запуском ревьюер получает актуальные решения этой задачи одним детерминированным разделом неизменяемой версии набора данных; версия закрепляется за сбором, его проверкой и локальными запусками исполнителя, для которых оркестратор материализует её обычным файлом внутри рабочего дерева; новая версия публикуется только перед следующим ревью. Опровергнутое замечание повторно открывается только по новому факту; переформулировка — дубликат; новое условие срабатывания — новая находка.
* R8 (матрица поведения). Повторная находка по одному инварианту в одной попытке — по связям, установленным оркестратором в журнале, — требует до следующего сбора матрицу поведения, адресную проверку и запись матрицы; оркестратор не запрашивает сбор без матрицы.
* R9 (чекпойнт). После двух кругов подряд без признанного оркестратором прогресса исполнитель до следующего сбора отвечает на пять вопросов; прогресс — подтверждённое устранение дефекта, доказательство, разрешившее спор, или новая конкретная причина; решение о прогрессе записывается; оркестратор не запрашивает сбор без ответов.
* R10 (пилот как эксперимент). Правила R8–R9 действуют в пилоте как явно утверждённый эксперимент на конкретных задачах через их диспатч и решения оркестратора; правилами стадий для всех задач становятся только после отчёта пилота.
* R11 (бюджет попытки). Доставка имеет накопительный операционный бюджет по классу риска в вызовах ревьюера и во времени петли ревью с устойчивой идентичностью через перезапуски и попытки; исчерпание запрещает новый запуск ревьюера, не прерывая идущий, и паркует доставку с причиной «бюджет ревью», остатком дефектов, доказательствами, следующим шагом и запросом продления; продление — записанное решение; рост класса риска переводит доставку на бюджет нового класса без обнуления потраченного; отсутствие телеметрии считает вызовы по реестру, а время — по журналу оркестратора, и помечает бюджет как «оценочный»; пределы стадии выпуска действуют независимо; значения по умолчанию экспериментальные, из R3; для крошечного класса бюджет не применяется.
* R12 (ворота неизменны). Сертификат preflight, зелёный сертификат PR, правило «тесты не править ради зелёного», правило о способности ревьюера не ниже исполнителя и финальная проверка точной версии кода сохраняются; новые исходы отображаются на существующие статусы и причины парковки.
* R13 (стенд ревьюеров). Кандидаты — GLM-5.3, Kimi K3, DeepSeek V4 Pro, Grok 4.6, MiniMax и контроль Terra (medium и high, если позволяет квота) — сравниваются с нынешним ревьюером на замороженном манифесте (восстановимые версия кода и база, байты набора данных, версия и копия помощника, отпечатки подготовленных доказательств, разбиение, одинаковые настройки инструментов и веб-поиска для всех маршрутов; отдельно — базовая линия с настройками боевого маршрута); выборка объявлена до прогона: число случаев по классам и серьёзности дефектов, независимые семейства задач, пары «дефект/исправление», чистые изменения, повторы, правила остановки; версии одной задачи считаются связанными наблюдениями; разметка и позднейшие решения скрыты от ревьюера; маршруты анонимизированы для разметчика; новые находки разбираются прежде, чем считаться ложными; сбои и таймауты — в операционных знаменателях; золотой набор заморожен с отложенной частью; находки нынешнего ревьюера — доказательство, не истина. Маршрут допускается к живому прогону только после проверки совместимости (схема, усилие, выбор модели, изоляция) и только по разрешённому провайдером каналу оплаты. Отчёт: полнота по известным P0–P2 по серьёзности, точность, регрессии, нерешённые исходы, время, расход с покрытием, различия обвязки отдельно от различий моделей; исход «оставить нынешнего» полноценен; малая выборка может отклонить кандидата, но не доказать равноценность. Стенд не выдаёт сертификатов.
* R14 (корпус исполнителя, структурное). Корпус исполнителя в репозитории и плагине остаётся в потолке пака в обоих инструментах; правки справочников политики и маршрутизации — вытеснением; байты диспатча и отрисованного набора данных измеряются отдельно как накладные расходы пилота.
* R15 (модели по ролям в конфиге продукта). Конфиг продукта переопределяет роли таблицы политики в пределах матрицы «роль × поддерживаемый транспорт»: роли исполнителей Codex — только транспорт Codex; исполнитель Claude — транспорт Claude; ревьюер — движки claude, kimi, pi, codex; Второй голос — Codex с сохранением кросс-вендорного правила; оркестратор не переопределяется. Для ревьюера усилие задаётся по классу риска с допустимыми значениями движка; провайдер описан нерекретной идентичностью (идентификатор, адрес) и именем переменной с ключом; значения ключей никогда не в конфиге. Ворота, запуск исполнителя, запуск Второго голоса и генератор диспатча берут маршрут из разрешённой роли на момент запуска и закрепляют его отпечатком в диспатче, запросе сбора и квитанции; изменение конфига в диффе исполнителя не меняет ревьюера этой же доставки; запущенные потоки хранят пины. Квитанции и реестр несут движок и провайдера; старые квитанции трактуются как движок claude с неизвестным провайдером.
* R16 (запись о паре). Переопределение, при котором способность ревьюера не ниже исполнителя не установлена таблицей, принимается только с записью владельца, привязанной к точным парам (движок, модель, усилие по классу риска, провайдер обеих сторон) и ссылающейся на решение владельца в Linear; изменение любой части пары делает запись недействительной; проверка конфига проверяет привязку, не способность модели. Таблица политики от 06.09.2026 остаётся значениями по умолчанию; граница «только таблица» явно заменена этим требованием.

## Примеры приемки

* AE1 (учёт). Покрывает R1, R2. Дано: попытка, в которой исполнитель трижды вызвал помощник локально, оркестратор выполнил сбор, его перезапуск после сбоя провайдера и финальный сбор, и каждый раз помощник запускался; когда оркестратор закрывает задачу; тогда реестр показывает 3 запроса сборов и 6 вызовов ревьюера (причины: правки 3, новая версия 1, перезапуск 1, финальная проверка 1; роль в сертификации — только у последнего), объявленные и подтверждённые проходы раздельно, расход — измеренным для вызовов со строками расхода и «н/д» с причиной для остальных, с полнотой «измерено 3 из 6».
* AE2 (сверка базы). Покрывает R3. Дано: журналы, квитанции и история MONO-75; когда выполнена сверка; тогда для каждого из 14 сборов и каждого локального запуска записаны событие реестра и классификация происхождения с доказательством или «не определимо по источникам», объявленные проходы отличены от подтверждённых, итог опубликован.
* AE3 (память ревьюера). Покрывает R5, R6, R7. Дано: замечание опровергнуто с доказательством, следующая версия набора данных содержит решение и материализована в рабочем дереве; когда следующий запуск ревьюера выдаёт то же замечание без нового факта; тогда исполнитель не меняет код, отвечает ссылкой на решение, находка помечается дубликатом; если ворота продолжают её требовать — доставка паркуется как требующая решения, не как «чисто».
* AE4 (пересмотр). Покрывает R5, R7. Дано: замечание опровергнуто; когда появляется противоречащее воспроизведение; тогда новая запись подтверждает замечание и ссылается на заменённую; при неизменных решениях повторная отрисовка даёт те же байты и версия не меняется.
* AE5 (матрица). Покрывает R8, R10. Дано: оркестратор связал два события с находками по одному инварианту; когда исполнитель просит следующий сбор без матрицы; тогда оркестратор не запрашивает сбор, записывает отказ, и сбор выполняется только после отчёта фазы с матрицей и результатом адресной проверки.
* AE6 (чекпойнт). Покрывает R9, R10. Дано: два круга без признанного прогресса; когда исполнитель просит следующий сбор; тогда сбор выполняется только после ответов на пять вопросов, проверенных оркестратором.
* AE7 (бюджет). Покрывает R11, R12. Дано: бюджет исчерпан, остаётся подтверждённый дефект, идёт вызов ревьюера; когда вызов завершается; тогда новый запуск не выполняется, доставка паркуется с причиной «бюджет ревью», сертификат готовности не выдаётся; после записанного продления запуск возможен.
* AE8 (стенд). Покрывает R4, R13. Дано: замороженный манифест и предобъявленная выборка; когда кандидаты и контроль прогнаны по общему протоколу доказательств; тогда отчёт содержит полноту по P0–P2 по серьёзности, точность, регрессии, нерешённые исходы, время, расход с покрытием, различия обвязки отдельно, список исключённых случаев и рекомендацию, среди исходов которой — «оставить нынешнего».
* AE9 (допуск маршрута). Покрывает R13. Дано: маршрут, у которого проверка совместимости не прошла или канал оплаты не разрешает автоматизацию; когда стенд формирует прогон; тогда маршрут исключён с причиной и не получает ни одного вызова.
* AE10 (маршрут из конфига). Покрывает R15. Дано: конфиг продукта переопределяет ревьюера проверенным маршрутом с провайдером в отдельном лимите; когда начинается новая доставка; тогда диспатч, запрос сбора и квитанция несут отпечаток маршрута с движком и провайдером, ворота запускают ревьюера этим маршрутом, а поток, запущенный до изменения, хранит прежние пины; дифф, меняющий конфиг, проверяется ревьюером, закреплённым при запуске.
* AE11 (запись о паре). Покрывает R16. Дано: переопределение ревьюера, не установленное таблицей; когда запись владельца отсутствует или привязана к другой паре; тогда проверка конфига отказывает с указанием пары; с записью, привязанной к этой паре и ссылающейся на решение в Linear, — принимает.

## Что должна доказать проверка

Что закрытие задачи показывает три счётчика ревью, причины, подтверждённые проходы и расход ревьюера по провайдеру с полнотой; что опровергнутое замечание не ведёт к повторной правке и не превращается в «чисто»; что одинаковые решения дают одинаковую версию набора данных и локальные запуски получают её же; что без матрицы или ответов чекпойнта сбор не запрашивается; что исчерпание бюджета паркует доставку; что стенд не выдаёт сертификатов, исключает неподходящие маршруты и допускает исход «оставить нынешнего»; что конфиг продукта меняет маршрут только для новых запусков, квитанции несут маршрут, а запись о паре привязана к точным парам; что корпус исполнителя не превышает потолок на обоих корнях.

## Критерии успеха

* Порог качества: ни одного потерянного известного актуального замечания P0–P2 на выборке стенда при оценке вмешательства и при оценке модели.
* Протокол измерения объявляется после сверки базы и до пилота: цели экономии (гипотеза — минус треть времени петли ревью и минус половина повторных сборов на сравнимых волнах), критерии отбора волн, контрольная волна текущей политики, метод сравнения, границы интервала петли и пересечений, полнота учёта расхода, учёт сбоев и парковок; кроме экономии ревьюера считаются общее время доставки, накладные расходы диагностики и вмешательства владельца. Две волны пилота — доказательство выполнимости и направления, не равноценность.
* Разгрузка лимитов: расход ревьюера показывается в лимите провайдера; после выбора внешнего ревьюера в конфиге продукта доля ревью в лимите Claude на волнах этого продукта стремится к нулю, что видно в цене волны.
* Для пакета: спецификация и задачи выполнимы без домысливания; ворота и статусы не меняют смысла; каждая задача — один PR.

## Что не входит в MVP

Активация конкретного нового ревьюера (отдельное записанное решение по результату стенда); переиспользование квитанций между разными запросами сбора; новые транспорты исполнителей; изменения помощника autoreview; ослабление ворот; новый набор статусов; дашборд; готовность для App и DemoApp без измеренной прикладной волны; сравнение «после» по протоколу «Лёгкого пака».

## Допущения

Набор данных задачи — единственный канал памяти ревьюера. Решения по бюджету и качеству делегированы оркестратору и записываются вместе с пакетом (ожидают записи до утверждения). Владелец разрешил передачу кода внешним провайдерам, включая размещённые в Китае, для всех продуктов (16.09.2026); ревьюеру передаются диф, набор данных задачи с разделом решений и подготовленные помощником доказательства. Живые доказательства принадлежат оркестратору после установки и не входят в приёмку кода.

## Открытые вопросы

Доля времени и расхода ревью на прикладном коде — первая волна App на новой поверхности. Значения бюджета по классам — после сверки базы. Класс «регрессия правки» в отчёте внешнего ревьюера PR — по итогам пилота. Достаточность архива для предобъявленной выборки — по факту манифеста; при нехватке стенд даёт только отчёт о выполнимости.
