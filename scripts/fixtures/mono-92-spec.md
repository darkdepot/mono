# Tech Spec: Ревью по доказательствам — учёт, журнал решений, стенд ревьюеров, модели по ролям

## Кратко

Утверждённый набор — четыре среза. I1 (учёт): реестр событий ревью с канонической идентичностью, расход ревьюера из потокового вывода помощника в квитанции, архив неизменяемых версий наборов данных, строка цены по реестру. I2 (пилот): журнал решений с типизированными записями, детерминированная отрисовка в неизменяемую версию набора данных, материализация версии в рабочем дереве для локальных запусков, обязанности пилота через диспатч и решение оркестратора до запроса сбора. I4 (стенд): замороженный манифест и общий протокол доказательств, прогон кандидатов без сертификатов, слепая разметка, отчёт. I5 (модели по ролям): раздел `models` конфига продукта в матрице «роль × транспорт», провайдер как нерекретная идентичность, отпечаток маршрута в диспатче, запросе сбора и квитанции, запись о паре с привязкой. Кандидат: I3 — встраивание правил, бюджета и исходов. Отложенный кандидат: переиспользование квитанций между запросами (U5′). Ворота и контракты артефактов не меняются.

## Исходные требования

R1–R16, AE1–AE11 PRD. I1: R1–R4 (AE1, AE2). I2: R5–R10, R12, R14 (AE3–AE6). I4: R4, R13 (AE8, AE9). I5: R15, R16, R12, R14 (AE10, AE11). I3: R11, R12, R14 (AE7).

## Цели и не цели

Цели: наблюдаемость петли ревью без изменения её правил; воспроизводимость сборов; проверка гипотез журнала, матрицы и чекпойнта на живых волнах при неизменной сертификации; честное сравнение ревьюеров; выбор моделей по ролям на уровне продукта с сохранением правила о паре; встраивание только доказанного. Не цели: изменения помощника autoreview; возобновление проходов внутри него; новый набор статусов; активация конкретного ревьюера; новые транспорты исполнителей; ослабление `gate.mjs`.

## Архитектура

Точки опоры: `scripts/gate.mjs` — сбор `preflight collect:true` запускает проверку и помощник в песочнице (`runSandboxed`, окружение из `safeGitEnv`, которое сегодня передаёт неигитовые переменные как есть) с фиксированным вызовом, пишет подписанную квитанцию `<evidenceRoot>/<head>.json` и неизменяемую `history/<runId>.json`; `collect:false` сверяет квитанцию с привязками запроса и выполняет проверки корректности, остатков, статуса, песочницы, согласованности и происхождения помощника. `scripts/wave-cost.mjs` — строка цены. `scripts/delivery-state.mjs` — отчёты фаз, `PARKED_REASONS`, `confirm`. `scripts/runtime.mjs` — конфиг доставки. `scripts/orchestrator/{spawn,launch}.mjs` — запуск исполнителей Codex по ролям `worker-default|worker-complex`. `references/model-policy.md` — таблица ролей; `references/autoreview-routing.md` — усилие по классу риска. `templates/orchestrator-dispatch.md` — генерируемый диспатч (адаптер аудитории). Набор данных задачи — единственный канал контекста ревьюера; помощник требует репозиторно-относительный обычный файл.

```text
потоки попыток ─┐
квитанции/история ├─► review-ledger.mjs ─► <evidenceRoot>/reviews/<KEY>.json (+ -adjudications.json) ─► wave-cost.mjs
отчёты фаз/ship ─┘
отчёт фазы ─► decisions.mjs record ─► decisions/<KEY>.json ─► render ─► datasets/<KEY>-review-scope.v<N>.md (+.sha256)
                                                              └─► materialize ─► <worktree>/.orchestrator/review-dataset-<d8>.md (локальные запуски)
конфиг продукта models ─► resolveRole ─► маршрут {engine, model, effort, provider} + отпечаток ─► диспатч / запрос сбора / gate.mjs (окружение из маршрута) / квитанция
архив (I1) ─► review-bench.mjs manifest ─► прогон маршрутов без сертификатов ─► bench/<runId>/ ─► score (слепо) ─► report
```

## Контракты и границы

* Реестр `<evidenceRoot>/reviews/<KEY>.json`: `{issue, attempts:[{attempt, events[], unresolvedCoverage[]}]}`. Событие: `{id (канонический: attempt + kind + collectionId|runId|порядковый номер вызова), kind: collection-request|helper-invocation|internal-pass, sources:[{type: history|receipt|report|stream|ledger, ref}], parent, stage, head, base, route{engine,model,effort,provider}|null, threshold, datasetVersion|null, status: scoped-clean|findings|filtered|incorrect|incomplete|reviewer_unavailable|withheld|unknown, findings|null, announcedPasses|null, confirmedPasses|null, launchCause: fix|head-change|retry|final-request|self-check|unknown, certificationRole: none|certified|superseded, startedAt|endedAt|null, usage|null}`. Корреляция: сбор ↔ история по `runId` ↔ квитанция головы по `head`+`collectionId`; вызов помощника ↔ элемент потока ↔ побочный статус по порядку и голове; отчёт ссылается на идентификаторы сборов. Неоднозначность — запись в `unresolvedCoverage` с причиной, никогда двойной счёт и никогда слияние по догадке. `withheld` — запрос, отклонённый оркестратором: считается в спросе, ноль выполненных сборов и вызовов. Причина запуска и роль в сертификации — разные поля.
* Классификация происхождения — `<evidenceRoot>/reviews/<KEY>-adjudications.json`: записи `{eventId, origin: original|incomplete-fix|fix-regression|scope-decision|preparation-failure|provider-retry|undeterminable, evidence, links:[decisionId], progress: fixed|evidence|new-cause|none|null, recordedBy}` — вносятся оркестратором; связи событий с записями журнала (ключ инварианта) — здесь, скрипты их только читают.
* Расход: сбор запускает помощник с `--stream-engine-output`; вывод разбирается потоково с ограниченным хранением: полностью сохраняются все строки, которые потребляет существующая проверка, строки расхода и хвост фиксированной длины; отсутствие или неоднозначность потребляемых строк — отказ сбора; JSON-отчёт и побочный статус проверяются как прежде. `receipt.review.usage = {engine, raw, normalized{input, cacheRead, cacheWrite, output}}|null` + `usageReason`; заполняется до подписи; исторические квитанции не изменяются. Проверка вызова принимает ровно две формы (фиксированная; фиксированная + `--stream-engine-output`) до I5, а после I5 — формы по движку из маршрута.
* Архив наборов данных: `datasets/<KEY>-review-scope.v<N>.md` + `.sha256`; неизменяем; квитанция ссылается на версию и отпечаток.
* Журнал `decisions/<KEY>.json`: только добавление; записи `decision` (`{id, findingKey (назначает оркестратор), problem, trigger, evidence, impact, origin, decision, validity{head, base, contracts[], assumptions[]}, verification, supersedes, proposedBy, recordedAt}`), `matrix` (`{id, invariant, states[{state, expected}], verification, recordedAt}`), `verification` (`{id, forId, method, result, recordedAt}`).
* Отрисовка и материализация: `render` — один управляемый раздел «## Ранее принятые решения — не повторять без нового факта», детерминированный; одинаковые решения → одинаковые байты; новая версия только при изменении и только перед следующим ревью. `materialize --version N --worktree <path>` — оркестратор пишет обычный файл `<worktree>/.orchestrator/review-dataset-<d8>.md` (каталог исключён из Git через `info/exclude` главного чекаута), проверяет отпечаток, возвращает путь; пин диспатча несёт путь и отпечаток; исполнитель запускает локальный помощник с `--dataset` по этому пути и не редактирует файл; новая версия — повторная материализация оркестратором до следующего ревью с записью в реестр; при завершении попытки файл удаляется. Сбор по-прежнему делает собственную копию.
* Отчёт фазы: необязательные поля `review_dispositions[]`, `behaviour_matrices[]`, `checkpoint`, `progress_claim`; `validatePhase` проверяет форму и ссылки; смысл решает оркестратор.
* Решение оркестратора до запроса сбора: по связям в `adjudications` (два события с находками одного `findingKey` в попытке) и по записанным решениям о прогрессе (два круга подряд `none`) — при отсутствии матрицы или ответов запрос адаптеру не делается, в реестр пишется `collection-request` со статусом `withheld`. `review-ledger.mjs decide` печатает подсказку только из этих записей.
* Раздел конфига `models` (I5): `{ roles: { <role>: { transport|engine, model, effort | effortByRisk{tiny,standard,deep,risky,riskyCritical}, provider{id, endpoint, credentialEnv} } }, pairingAccepted: [ { producer{role, engine, model, effort}, reviewer{engine, model, effortByRisk, provider.id}, riskClasses[], linearDecision, by, date } ] }`. Матрица «роль × транспорт»: `worker-default|worker-complex` → codex; `worker-claude` → claude; `autoreview` → claude|kimi|pi|codex; `second-voice` → codex (кросс-вендорное правило сохраняется); `orchestrator` — не переопределяется. Допустимые усилия по движку: claude low|medium|high|xhigh|max; codex low|medium|high|xhigh|max; kimi on|off; pi — как поддерживает модель. Неподдерживаемая комбинация или эскалация — отказ проверки конфига до запуска. Значения ключей — только в окружении оркестратора; в конфиге только имя переменной.
* Разрешение роли: `resolveRole(role, config)` в `runtime.mjs`: таблица политики → переопределение продукта → маршрут `{engine, model, effort|effortByRisk, provider{id, endpoint}, credentialEnv}` + отпечаток (sha256 канонического маршрута и отпечатка конфига). Ворота собирают окружение вызова из маршрута: снимают внешние `ANTHROPIC_*`/провайдерские переменные, ставят адрес и ключ по маршруту (для `claude`: `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_API_KEY` по провайдеру; для `pi`/`kimi` — их переменные). Отпечаток закрепляется в пинах диспатча, запросе сбора и квитанции (`route{engine, model, effort, provider, fingerprint}`); `collect:false` сверяет. Маршрут разрешается при запуске из конфига базовой ветки; дифф, меняющий конфиг, проверяется закреплённым маршрутом; новые маршруты — новым запускам. Старые квитанции без движка — `engine: claude`, `provider: unknown`.
* Запись о паре: проверка конфига требует запись, привязанную к точным парам, когда переопределение касается ревьюера или исполнителя и пара не установлена таблицей; сравнение по всем полям пары; отсутствие/несовпадение — отказ с указанием пары. Таблица от 06.09.2026 остаётся значениями по умолчанию; `model-policy.md` получает раздел «Переопределение продуктом» с явной заменой границы «только таблица».
* Стенд (I4): `review-bench.mjs manifest|run|score|report`; манифест `{cases:[{id, head, base, datasetVersion, datasetDigest, helperVersion, helperArchive, evidenceDigests, partitioning, toolSettings{webSearch:false}, gold: <отдельный файл>, cluster: <семейство задачи>}], routes:[{id (анонимный для разметчика), engine, model, effort, provider, credentialEnv, eligibility{compatibilityPreflight, billingChannelAllowed}}]}`; прогон — тот же вызов помощника, что в сборе, плюс маршрут, с `--no-web-search`/выключенными инструментами для всех маршрутов, во временной копии репозитория; результаты в `<evidenceRoot>/bench/<runId>/`; никаких записей в квитанции и сертификаты; базовая линия боевого маршрута с его настройками — отдельный прогон. Разметка: `score` сопоставляет находки с золотыми при скрытом отображении маршрутов; спорные — перекрёстно; новые находки разбираются до отнесения к ложным. Отчёт по PRD R13.
* Бюджет (I3, кандидат): `orchestration.review.budget` по классам; идентичность — доставка Issue через попытки и перезапуски; эскалация класса — новый предел без обнуления; отсутствие телеметрии — оценочный режим по реестру и журналу; парковка `review-budget`; пределы ship независимы.
* U5′ (отложено): переиспользование квитанции при новом collectionId — проверка по всем текущим привязкам и проверкам, новая подписанная квитанция с `reusedFrom`, ноль новых вызовов; фикстуры на каждое расхождение.

### Реальные ответы бэкенда

Внешних API пака нет. Образцы: квитанция `cb218ce9….json`; строки помощника (цель, `review passes:`, вердикты, побочный статус); строки расхода `claude usage: input_tokens=… cache_read_input_tokens=… cache_creation_input_tokens=… output_tokens=…` и `codex usage: …` под `--stream-engine-output` (живое подтверждение — оркестратор после установки I1). Помощник: `ENGINES = codex, claude, amp, pi, kimi`; `claude_allowed_exact` сохраняет `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`; `run_pi` — `--no-tools`, `--model`, `--thinking`; `run_kimi` — изолированный TOML-конфиг, `--thinking on|off`. Провайдеры (по документации на 16.09.2026, проверка совместимости обязательна перед живым прогоном): Z.ai `https://api.z.ai/api/anthropic` (план Z.ai; Claude Code поддерживается); Moonshot pay-per-token `https://api.moonshot.ai/anthropic` (`kimi-k3`; план Kimi Code исключает неинтерактивную автоматизацию — для стенда не используется); DeepSeek Anthropic-формат; xAI API (`grok-4.6`, усилие low…xhigh) через `pi` (`XAI_API_KEY`; вход по подписке через Pi — проверить); MiniMax Token Plan (Anthropic-совместимый — проверить); Gemini через `pi` при установленном Pi.

## Единицы реализации

* U1 (реестр и классификация; R1, R3; I1). `review-ledger.mjs build|print|adjudicate`: источники, каноническая идентичность и псевдонимы, корреляция, три счётчика, причины, роли, `unresolvedCoverage`, `withheld`; `adjudicate` — записи происхождения, связей и прогресса. Фикстуры: каждый класс причины, один вызов в трёх источниках → одно событие, неоднозначность → покрытие не разрешено, перезапуск, `withheld`, роль сертификации.
* U2 (расход и хранение вывода; R2; I1). `gate.mjs`: флаг, потоковый разбор, `usage` до подписи, две формы вызова, fail closed. Фикстуры: старая квитанция принята; расход Claude и Codex; потеря заголовка — отказ; третья форма — отказ.
* U3 (архив версий; R4; I1). Версии и отпечатки в квитанции; воспроизводимость в реестре.
* U4 (строка цены; R1, R2; I1). `wave-cost.mjs`: реестр — приоритет; строка «авто-ревью: сборов N (отклонено K), вызовов M (…), проходов объявлено A / подтверждено C, расход по провайдеру X (измерено k из M)»; выбор отчёта по `stage`+`issue`; фикстуры; README.
* U5 (журнал, отрисовка, материализация; R5–R7; I2). `decisions.mjs record|render|version|materialize|list`; фикстуры: добавление, `supersedes`, отказ перезаписи, три типа, идемпотентность, версия только при изменении, материализация с проверкой отпечатка и удалением.
* U6 (пилот: диспатч и решение оркестратора; R8–R10; I2). Блок диспатча «Дисциплина ревью в этой задаче (эксперимент по проекту …)»; поля отчёта фазы с проверкой формы; `review-ledger.mjs decide` по записям `adjudications`; `references/orchestration.md` — раздел о журнале, версиях, материализации и решении до запроса сбора. Фикстуры: скелет разделов блока диспатча (наличие разделов и полей, без пинов формулировок), `decide` на записях, `withheld`.
* U7 (встраивание; R11, R12, R14; I3, кандидат). Правила в скиллах стадий вытеснением; `review-budget` в `PARKED_REASONS`; конфиг бюджета с эскалацией и оценочным режимом; `worker-contract.md`; README; `MACHINE_TOKENS` только для машинных токенов.
* U8 (стенд; R13; I4). `review-bench.mjs manifest|run|score|report`, `docs/review-bench-protocol.md` (выборка, слепая разметка, критерии, остановка, кластеры, отложенная часть, различия обвязки), проверка совместимости маршрута (`--dry-run` помощника с маршрутом, схема/усилие/модель/изоляция) и признак разрешённого канала оплаты; фикстуры с поддельным помощником; отсутствие записей в квитанции; ключи только из окружения.
* U9 (модели по ролям; R15, R16; I5). Схема `models`, `project-config.mjs --check` (форма, матрица, усилия, пара с привязкой), `resolveRole` + отпечаток, потребители (`gate.mjs` — окружение из маршрута, формы вызова по движку, `route` в квитанции; `spawn.mjs`/`launch.mjs` — пины из роли в матрице; запуск Второго голоса; генератор диспатча), `model-policy.md` («Переопределение продуктом»), `autoreview-routing.md` (движок из роли) — оба вытеснением с проверкой потолка на исходниках и обоих установленных корнях; README. Фикстуры: неизвестная роль/движок/усилие, пара без записи → отказ, с привязанной записью → принято, изменение пары → отказ; квитанция с движком и провайдером; старая квитанция принята как claude/unknown; окружение вызова без внешних переменных провайдера; отпечаток в диспатче и запросе сбора; изменение конфига в диффе не меняет закреплённый маршрут.

## Влияние на остальную систему

Смысл `scoped-clean` и `ready` не меняется; проверка вызова расширяется по движку из маршрута. Реестр, классификация, журнал, версии, манифесты стенда — новые файлы в evidence root; подписи квитанций не затрагиваются. Строка цены сохраняет прежний формат для старых волн. Диспатч несёт обязанности пилота; корпус исполнителя не растёт до I3, а правки справочников в I5 идут вытеснением. Запущенные потоки хранят пины; новые маршруты — новым запускам. App/DemoApp получают изменения обычной установкой.

## Риски и защита

Ложная причина/двойной счёт → каноническая идентичность, корреляция, `unresolvedCoverage`, фикстуры. Журнал закрепляет ошибку → только добавление, `supersedes`, доказательство, находка ворот остаётся нерешённой. Потеря доказательств при ограниченном хранении → полное сохранение потребляемых строк, fail closed. Утечка ключей → в конфиге только имена переменных, в квитанциях и отчётах — только идентификатор провайдера; фикстура на отсутствие значений. Нарушение условий подписок → допуск маршрута только по разрешённому каналу (план Z.ai — Claude CLI; Kimi — pay-per-token). Передача кода внешним провайдерам → разрешена владельцем 16.09.2026 для всех продуктов; объём передачи описан в PRD. Подмена ревьюера правкой конфига в диффе → маршрут закреплён при запуске. Потолок корпуса → вытеснение с проверкой на трёх поверхностях. Второй каркас ревью → правила только у владельцев стадий.

## Что может сломаться и как защищаемся

Проверка вызова с новым флагом/движком — фикстуры на все формы. Помощник не печатает расход — `usage:null`, «измерено 0 из M». `validatePhase` с новыми полями — необязательные. Материализованный файл попал в дифф — каталог исключён из Git, фикстура на отсутствие в `git status`. Провайдер несовместим по схеме/усилию — проверка совместимости исключает маршрут. Отрисовка меняет байты при тех же решениях — фикстура идемпотентности.
