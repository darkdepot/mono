# PRD: Дешёвые волны — короткий путь мелкой задачи, команды оркестратора, предприменение `.agents/`

## Кратко

Мелкая задача (tiny/standard) сегодня платит ту же церемонию, что и глубокая: выход и перезапуск исполнителя на рукопожатии, два прогона ревью на одну версию кода, подтверждение каждой записи по одной, десятки файлов, собранных оркестратором руками, и повторяющиеся парковки по известным причинам. PRD задаёт короткий путь для tiny/standard при неизменных воротах, команды оркестратора с адаптером и сборщиком в паке, узкое правило предприменения изменений под `.agents/` по мандату владельца и замороженное измерение на двух сопоставимых волнах Mono.

## Акторы

- A1. Владелец продукта — ставит задачи, принимает решения по продукту, риску и полномочиям; хочет, чтобы мелкие задачи закрывались быстро без его участия, а качество не падало.
- A2. Оркестратор (сессия Claude) — единственный писатель в Linear во время оркестрации; запускает исполнителей, подтверждает записи, выкладывает; сегодня тратит время на ручную сборку файлов и на парковки.
- A3. Исполнитель (сессия Codex под mono-deliver) — проходит ворота, пишет код, проходит preflight и ship в одном контексте; сегодня выходит из процесса на рукопожатии и повторяет проверки после перезапуска.
- A4. Сборщик оркестратора — фоновый процесс, выполняющий сборы ревью и подтверждающий очереди; сегодня это личный помощник оркестратора вне пака.
- A5. Сторож — фоновый процесс пака, следящий за живостью исполнителей; подавляет тревоги на время рукопожатия в ограниченном окне.

## Проблема

Базовая линия (измерения 30.09.2026): правка в три строки — 39 минут от запуска до закрытия (34 мин 10 с до подтверждённого зелёного PR), 11,4 млн входных токенов исполнителя, 21 файл, собранный оркестратором руками, 7 ручных записей в Linear через коннектор и 2 фиксации изменений, сделанных интеграцией GitHub, одна парковка по известной причине. Неизбежная часть (CI, ревью PR, тихий период, установка) — около 10 минут. Остальное — рукопожатие с выходом процесса (≈5 мин, ≈1,3 млн токенов), парковка на `.agents/` (≈4–7 мин, в четырёх из девяти последних волн), дублирующий локальный прогон ревью (≈2 мин), подтверждения по одной записи, полный снимок документов (97 КБ) для трёхстрочной правки.

## Текущий процесс

F1 (сегодня). Оркестратор руками пишет пины, запрос ворот старта, параметры и рендер диспатча, запрос запуска; исполнитель проходит ворота, пишет gate-ack и выходит; оркестратор двигает задачу в Linear, пишет файл возобновления и запрос, потребляет ack, перезапускает; исполнитель повторяет проверку идентичности и проверку доставки, пишет код, публикует отчёт с комментарием о старте и ждёт; оркестратор публикует комментарий, фиксирует, подтверждает; исполнитель делает локальный прогон ревью, коммитит, запрашивает сбор; сборщик собирает и подтверждает; исполнитель проверяет квитанцию, публикует сертификат готовности и ждёт; далее PR, In Review и ссылка, зелёный сертификат — каждая запись отдельным кругом; оркестратор мержит, выкладывает, закрывает.

## Целевой процесс

F2 (короткий путь, tiny/standard). Оркестратор запускает задачу одной командой пака: она собирает снимок из переданных тел документов (задача, утверждение, бриф проекта, выписки PRD/Tech Spec по ссылкам задачи и общие разделы), считает и записывает пины, проходит ворота старта, рендерит диспатч, запускает исполнителя, пишет строку журнала. Исполнитель проходит ворота, пишет gate-ack и ждёт на месте, в пределах окна сторожа, запись о применённых ходах с обратным чтением; оркестратор проверяет ack, применяет ходы и фиксирует их одной командой; исполнитель продолжает в том же процессе без повторной проверки идентичности, но с проверкой доставки по обновлённому состоянию. Если окно истекло, исполнитель паркуется с отчётом, и применяется обычный перезапуск. Код, затем коммит и запрос сбора без обязательного локального прогона ревью; сборщик пака выполняет сбор и подтверждает очередь сам. Сертификат готовности публикуется одним комментарием, где сведения о старте стоят в человеческой части перед неизменным машинным блоком; оркестратор принимает отчёт одной командой (команда показывает записи, оркестратор записывает через коннектор и сообщает свежие наблюдения, команда фиксирует и подтверждает). Далее PR, In Review, зелёный сертификат — как сегодня, приём каждого отчёта одной командой. Пустые очереди подтверждаются сборщиком автоматически.

F3 (изменения под `.agents/`, только по мандату владельца). Если утверждённая задача несёт перечень и содержимое файлов под `.agents/`, оркестратор сверяет байты и применяет ровно их отдельным коммитом на ветку задачи до ворот старта, с записью в журнале; диспатч называет коммит и хеш; исполнитель на воротах сверяет и не меняет эти файлы. Если ревью требует исправить эти байты, исполнитель паркуется с точными байтами, перечень меняется через ремонт владельцем артефакта по его правилам классификации (или обновление issue-only задачи), затем следует новый запуск с новым коммитом.

F4 (deep/risky и задачи с открытыми решениями). Полный снимок и обязательная локальная петля ревью — как сегодня; ожидание на месте применяется и здесь, потому что не зависит от класса риска.

## Сценарии

- S1. Владелец просит вернуть одну строку конфига (как MONO-92). Оркестратор оформляет задачу, запускает её одной командой; исполнитель проходит ворота и продолжает без перезапуска; одна проверка кода сбором; PR зелёный; закрытие. Оркестратор пишет через коннектор шесть раз вместо семи и не собирает файлы руками.
- S2. Задача меняет `.agents/mono-workflow.config.json`, мандат владельца записан, задача несёт перечень и содержимое файла. Оркестратор сверяет, применяет коммитом до запуска, пишет строку журнала; исполнитель не паркуется на старте. Ревью просит поправить одну строку конфига: парковка с точными байтами → ремонт пакета по классу (новый перечень в Tech Spec и снимке задачи) → новый запуск с новым коммитом оркестратора.
- S3. Сбор ревью нашёл замечание P2 в коде мелкой задачи. Исполнитель чинит, коммитит, запрашивает новый сбор под новым идентификатором; локальный прогон не обязателен, но разрешён.
- S4. Оркестратор недоступен во время ожидания ack. Окно ожидания истекает раньше, чем сторож поднимет тревогу; исполнитель паркуется «запись не подтверждена» с отчётом и выходит; оркестратор после восстановления применяет ходы, потребляет ack и возобновляет обычным путём.
- S5. Ответ коннектора потерян после публикации сертификата. Команда приёма при повторе сначала печатает, что нужно перечитать в Linear; оркестратор ищет комментарий по маркеру и сообщает свежее наблюдение; повторной публикации нет.
- S6. Задача deep. Всё как сегодня, кроме ожидания на месте вместо выхода и перезапуска.

## Требования

- R1 (ожидание на месте в окне сторожа). После записи gate-ack исполнитель на codex-cli ждёт запись оркестратора о применении ходов с обратным чтением и продолжает в том же процессе; окно ожидания отсчитывается от записи ack и короче срока подавления тревог сторожа, порог которого задаётся в одном месте конфигурации для сторожа и для окна; истечение окна паркует исполнителя с отчётом, после чего действует сегодняшний перезапуск; после потребления ack сторож не поднимает тревогу, пока исполнитель не продолжил запись в журнал, в пределах одного порога. Потребление в режиме ожидания требует живого писателя той же попытки (тот же процесс по времени его запуска, тот же поток, в его журнале начатое и не завершённое собственное ожидание; сообщения о ходе работы не мешают). Ход применяется только после gate-ack. Наблюдаемо: журнал исполнителя — один поток без записи о возобновлении; реестр хранит режим рукопожатия, воплощение писателя и время потребления.
- R2 (одна проверка кода на коротком пути). На коротком пути (tiny/standard, `critical` пуст, готовность AFK, открытых решений нет) локальный прогон помощника ревью до запроса сбора не обязателен; один вызов установленного помощника сбором оркестратора — сертифицирующая проверка точной версии для любого класса. Оркестратор может назначить полный путь явно. Наблюдаемо: сертификат готовности мелкой задачи показывает ноль локальных прогонов и один сбор при отсутствии замечаний, ворота preflight принимают квитанцию.
- R3 (старт в комментарии сертификата). На коротком пути отдельный комментарий о старте не публикуется: сведения о старте стоят в человеческой части комментария сертификата готовности перед неизменным машинным блоком; отчёт фазы кода публикуется с пустой очередью и подтверждается. Наблюдаемо: в задаче Linear один комментарий с сертификатом preflight, в его начале — сведения о старте.
- R4 (снимок по ссылкам). На коротком пути снимок диспатча содержит задачу, утверждение, бриф проекта, выписки PRD и Tech Spec по определениям идентификаторов из «Покрытие PRD/Spec» задачи и всегда включаемые общие разделы; несуществующий идентификатор — отказ запуска; двусмысленность — полные документы с пометкой; issue-only — без документов проекта; повышение класса риска исполнителем — запрос полного снимка через парковку. Наблюдаемо: состав и размер снимка в журнале запуска.
- R5 (команда запуска). Одна команда пака собирает снимок, считает и записывает пины попытки (файл и хеш в реестре), проходит ворота старта, рендерит диспатч из шаблона без пустых подстановок, запускает исполнителя и пишет строку журнала; отказ любого шага останавливает запуск без регистрации попытки. Наблюдаемо: полный набор артефактов запуска без ручных файлов.
- R6 (команда приёма). Одна команда пака: для ack — проверяет корреляцию, полноту ворот и исход; при отсутствии записи потребления печатает план ходов «из → в», принимает обратные чтения, привязанные к плану, и потребляет ack; при существующей одинаковой записи — завершает прерванное потребление без нового плана; при противоречащей — отказывает; для отчёта фазы — открывает сеанс сверки, печатает записи с готовым текстом (при повторе — сначала что перечитать), принимает наблюдения этого сеанса и подтверждает очередь; для поправки — готовит версию поправок пинов и возобновление. Наблюдаемо: подтверждение очереди без ручных JSON; повтор идемпотентен; восстановление после сбоя на любом шаге завершает начатое.
- R7 (адаптер и сборщик в паке). Адаптер Linear пака принимает только наблюдения текущего сеанса сверки, привязанные к отчёту и записи; прежние наблюдения при новом сеансе недействительны; печать инструкции записи никогда не считается успехом. Сборщик пака выполняет сборы по запросам, подтверждает очереди без коннекторных записей, восстанавливается по подписанным квитанциям истории (включая неудачные) без повторного ревью и приводит в согласие текущую квитанцию версии кода, держит блокировку попытки с воплощением процесса и не перехватывает живой сбор, читает текущую версию пинов попытки из реестра. Наблюдаемо: журнал сборщика; повторный сбор по тому же идентификатору не запускается.
- R8 (предприменение по мандату). Только при записанном мандате владельца: утверждённая задача несёт раздел «Предприменение» с перечнем файлов под `.agents/` (путь, хеш содержимого) и полным содержимым каждого; оркестратор сверяет байты с перечнем, применяет отдельным коммитом до ворот старта и пишет строку журнала с ссылкой на мандат; пути вне `.agents/`, символические ссылки и выход за пределы дерева отклоняются; коммит и хеш названы в диспатче; исполнитель сверяет и не меняет эти файлы; перечень для Project-first живёт в Tech Spec и снимке задачи, для issue-only — в задаче; исправление по замечанию — через парковку и ремонт владельцем артефакта по его правилам классификации (или обновление issue-only задачи), затем новый запуск с обновлённым перечнем. Наблюдаемо: ноль парковок по EPERM на старте; исправление — одна парковка, ремонт и новый запуск.
- R9 (ворота неизменны). Проверка идентичности пака, ворота старта, обязательное ревью точной версии по классу риска, сертификаты preflight и green с неизменными машинными блоками, подтверждение каждой записи с обратным чтением, правило «ход только после gate-ack», запрет правки тестов ради зелёного — без изменений. Структурно: фикстуры этих ворот не правятся.
- R10 (замороженное измерение). Оркестратор измеряет две первые задачи Mono класса standard на коротком пути, запущенные после установки I3 (набор возможностей I1–I3 заморожен; I4 считается, если мандат дан, иначе следующая обычная задача), против базы MONO-92 (standard, одна парковка EPERM) с MONO-91 как справкой о многократных парковках: время от строки журнала о запуске до файла подтверждения зелёного сертификата и отдельно до Done; входные токены исполнителя по всем попыткам; записи через коннектор по описи (сегодня 7: старт, сертификат готовности, In Review, зелёный сертификат, закрытие, апдейт проекта, статус проекта); фиксации изменений интеграции отдельно; рукотворные артефакты в каталоге диспатча; парковки. Владелец измерения — отдельная операционная задача оркестратора без PR; она закрывается вручную после второй выборки, отчёт — комментарий на ней и апдейт проекта; проект завершается только после неё; на время измерения набор возможностей заморожен (мандат предприменения в конфиге не включается). Наблюдаемо: таблица «база — волна 1 — волна 2» с правилами счёта.

## Примеры приемки

- AE1 (ворота без перезапуска). Покрывает R1. Дано: попытка в режиме ожидания, ворота пройдены; когда исполнитель записал gate-ack; тогда процесс жив и ждёт, а после записи о применённых ходах с верными хешами тот же процесс продолжает фазу кода без повторной проверки идентичности и без записи о возобновлении, выполнив проверку доставки по обновлённому состоянию.
- AE2 (план только после проверки ack). Покрывает R1, R6, R9. Дано: ack отсутствует или не покрывает все ворота попытки; когда оркестратор вызывает приём ack; тогда команда отказывает и не печатает план ходов.
- AE3 (окно истекло). Покрывает R1. Дано: gate-ack записан, оркестратор недоступен; когда окно ожидания истекает (раньше срока подавления сторожа); тогда исполнитель паркуется «запись не подтверждена» с отчётом и выходит, тревога сторожа не поднимается до истечения окна, а после восстановления оркестратор применяет ходы и возобновляет обычным путём.
- AE3а (потребление между сканами сторожа). Покрывает R1. Дано: журнал исполнителя молчит дольше порога, ack потреблён как применённый; когда сторож сканирует до того, как исполнитель продолжил запись; тогда тревоги нет, а если журнал не ожил в пределах одного порога после потребления — сторож поднимает обычную тревогу.
- AE3б (чужой процесс с тем же pid). Покрывает R1. Дано: процесс исполнителя умер, его pid занят другим процессом; когда оркестратор потребляет ack в режиме ожидания; тогда отказ — время запуска процесса не совпадает с записанным.
- AE4 (мёртвый ожидающий). Покрывает R1. Дано: режим ожидания, процесс исполнителя умер; когда оркестратор потребляет ack как применённый; тогда команда отказывает, пока не зарегистрирован возобновлённый писатель.
- AE5 (одна проверка). Покрывает R2. Дано: короткий путь, сбор завершился чисто; когда исполнитель формирует сертификат; тогда сертификат показывает ноль локальных прогонов и один сбор, ворота preflight принимают квитанцию.
- AE6 (замечание на мелкой задаче). Покрывает R2. Дано: сбор нашёл P2; когда исполнитель исправил и закоммитил; тогда следующий сбор идёт под новым идентификатором, сертификат перечисляет оба.
- AE7 (один комментарий). Покрывает R3, R9. Дано: короткий путь; когда фаза preflight подтверждена; тогда в задаче ровно один комментарий с сертификатом preflight, сведения о старте стоят перед машинным блоком, а блок начинается строкой маркера и строкой `Preflight:` без вставок.
- AE8 (снимок по ссылкам). Покрывает R4. Дано: задача ссылается на R2 и U3; когда команда запуска собирает снимок; тогда в снимке есть определения R2 и U3, общие разделы, задача, утверждение, бриф, а полных документов нет. Дано: задача ссылается на R99, которого нет; тогда запуск отказан.
- AE9 (запуск одной командой). Покрывает R5. Дано: тела документов в каталоге снимка; когда оркестратор выполняет команду; тогда есть пины (и их хеш в реестре), запрос ворот старта, диспатч без пустых подстановок, запрос запуска, регистрация, строка журнала; при провале ворот старта попытка не зарегистрирована.
- AE10 (приём одной командой). Покрывает R6, R7. Дано: отчёт фазы с двумя записями; когда оркестратор открывает сеанс, сообщает два наблюдения этого сеанса; тогда создано подтверждение очереди; повтор с новым сеансом требует новых наблюдений, старые отклонены; повтор с теми же результатами после подтверждения идемпотентен.
- AE15 (восстановление потребления). Покрывает R6. Дано: запись потребления уже опубликована, переименование ack прервано; когда оркестратор повторяет приём ack; тогда команда не печатает новый план, завершает переименование и снятие ворот; при записи с другим исходом — отказ.
- AE11 (пустая очередь и сбор). Покрывает R7. Дано: отчёт фазы кода с пустой очередью; когда сборщик его видит; тогда подтверждение создано без оркестратора. Дано: сборщик упал между записью квитанции в историю и записью квитанции версии кода; когда он перезапущен; тогда он находит подписанную квитанцию истории по идентификатору сбора, восстанавливает квитанцию версии кода и фиксирует результат без повторного ревью. Дано: блокировка сборщика осталась от умершего процесса, живого сбора нет; когда сборщик запускается; тогда он забирает блокировку; при живом сборе — отказывает.
- AE12 (предприменение). Покрывает R8. Дано: мандат записан, задача несёт перечень и содержимое `.agents/mono-workflow.config.json`; когда оркестратор запускает задачу; тогда байты сверены с перечнем, на ветке есть коммит до ворот старта, диспатч называет его и хеш, строка журнала ссылается на мандат, исполнитель на воротах сверяет. Дано: файл вне `.agents/`, символическая ссылка, `..`, хеш не сходится или мандата нет; тогда отказ без коммита.
- AE13 (полный путь). Покрывает R2, R4, R9. Дано: задача deep или с открытым решением; когда исполнитель проходит preflight; тогда локальный прогон обязателен, снимок полный, а рукопожатие идёт с ожиданием на месте.
- AE14 (измерение). Покрывает R10. Дано: две волны на коротком пути завершены; когда оркестратор закрывает операционную задачу измерения; тогда её комментарий содержит таблицу с замороженными концами интервалов, токенами по всем попыткам, записями по описи и парковками, и только после этого проект завершается.

## Что должна доказать проверка

Что план ходов невозможно получить без проверенного ack и что потребление в режиме ожидания требует живого писателя; что ожидание ограничено окном сторожа и переживает недоступность оркестратора через парковку; что сертификат мелкой задачи с одним сбором проходит ворота preflight и ship при неизменном машинном блоке; что запуск и приём воспроизводят сегодняшний набор артефактов без ручных файлов, идемпотентны и отвергают устаревшие наблюдения; что сборщик подтверждает пустые очереди и восстанавливается по квитанциям без повторного ревью; что коммит предприменения виден исполнителю и ревью и ограничен `.agents/`; что фикстуры существующих ворот не изменились; что корпус исполнителя остался в пределах потолка.

## Критерии успеха

- Для владельца: две первые задачи standard на коротком пути после установки I1–I3 быстрее MONO-92 от запуска до подтверждённого зелёного PR не меньше чем на 25 % при тех же воротах; ноль парковок на старте по известным причинам; парковки и повторные попытки входят в счёт.
- Для оркестратора: рукотворных артефактов на задачу ≤ 4 (тела документов и вызовы команд); записей через коннектор 6 вместо 7 по описи; токены исполнителя записаны отдельно (ожидание ≈ −20 %, без жёсткой цели).
- Для качества передачи: Tech Spec и задачи выводятся из этого PRD без придумывания поведения; правила измерения заморожены до результата.

## Что не входит в MVP

Изменение правила «ход только после gate-ack»; ослабление ворот; короткий путь для deep/risky и для задач с открытыми решениями; прямая запись в Linear скриптами (нет ключа API); автоматизация выкладки и cutover, проверка входа Claude до запуска (отдельный срез); изменения помощника autoreview, стенда ревьюеров, моделей по ролям; транспорт claude-code-desktop.

## Допущения

- Сторож подавляет тревоги на время рукопожатия в окне «порог простоя × 4» от затишья журнала; порог берётся из общей конфигурации доставки; окно ожидания короче него и отсчитывается от записи ack.
- Исполнитель на codex-cli умеет блокирующе ждать файл так же, как ждёт подтверждение очереди.
- Исполнитель может читать собственную запись потребления ack (каталог вне его грантов записи); правило контракта исполнителя явно это разрешает.
- Записи в Linear выполняет оркестратор через коннектор; ключ API отсутствует и не требуется.
- Корпус правил исполнителя остаётся в пределах потолка чтения: новые формулировки замещают старые байт в байт или короче; новых рёбер чтения нет.

## Открытые вопросы

- Мандат владельца на узкое механическое исключение: оркестратор применяет байты под `.agents/` по перечню из утверждённой задачи до запуска, с записью в журнале на каждое применение; исправления — только через ремонт задачи. Без мандата задача I4 не создаётся, парковка на `.agents/` остаётся ручной.
